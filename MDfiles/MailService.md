# 9. MailClaw

수신한 메일에 대해서 자동화 서비스를 설정할 수 있다.

자동화 설정의 이름은 `MailClaw`로 한다.

`MailClaw`는 갯수에 제한 없이 등록할 수 있으며, 새로운 메일이 수신될 때마다 등록된 `MailClaw` 자동화 건수만큼 조건을 확인한다.

조건에 일치되는 항목이 있으면 등록된 자동화를 진행한다.

# 9.0 MailClaw UI 진입

메일 계정 관리 창에서 `MailClaw` 자동화 관리 화면으로 이동할 수 있다.

메일 계정 관리 PopUp 창의 메뉴는 아래와 같이 표시한다.

- 계정 추가
  - Gmail, 네이버, Apple 또는 기타 계정을 추가한다.
- 계정 관리
  - 등록된 메일 계정을 관리한다.
- MailClaw
  - 수신 메일 자동화 조건과 동작을 관리한다.

`MailClaw` 메뉴는 `계정 관리` 메뉴 밑에 배치한다.

`MailClaw` 메뉴에는 첨부 이미지의 캐릭터 부분을 오려서 만든 아이콘/캐릭터 이미지를 사용할 수 있다.

- 이미지 경로: `public/img/mail/mailclaw-character.png`
- 사용 위치: MailClaw 메뉴 아이콘, MailClaw 설정 화면 상단 캐릭터 이미지
- 표시 방식: 투명 배경 PNG로 표시하며, 메뉴에서는 작은 아이콘으로 축소해서 사용한다.

# 9.1 MailClaw 조건 설정

각 `MailClaw` 자동화 설정은 아래 조건을 가진다.

- 발신자 체크
  - 발신자 체크 == true 인 경우에만 발신자 조건을 확인한다.
  - 체크할 발신자 목록에 등록된 발신자와 수신 메일의 발신자가 일치하는지 확인한다.
  - 예: 발신자 #1, 발신자 #2, 발신자 #3, ...

- 참조자 체크
  - 참조자 체크 == true 인 경우에만 참조자 조건을 확인한다.
  - 체크할 참조자 목록에 등록된 참조자와 수신 메일의 참조자가 일치하는지 확인한다.
  - 예: 참조자 #1, 참조자 #2, 참조자 #3, ...

- 키워드 체크
  - 키워드 체크 == true 인 경우에만 키워드 조건을 확인한다.
  - 등록된 키워드가 메일 제목의 일부에 포함되어 있는지 확인한다.
  - 예: 키워드 == 제목중 일부 키워드

# 9.1.1 MailClaw 조건 판정 방식

각 `MailClaw` 자동화는 켜진 조건만 판정 대상으로 사용한다.

- 발신자 체크 == true 이면 발신자 조건을 판정한다.
- 참조자 체크 == true 이면 참조자 조건을 판정한다.
- 키워드 체크 == true 이면 키워드 조건을 판정한다.

켜진 조건이 여러 개이면 모든 조건을 만족해야 자동화를 실행한다.

즉, 각각의 켜진 조건에 따라서 `발신자 AND 참조자 AND 키워드`를 모두 만족해야 실행한다.

예:

- 발신자 체크 == true
- 참조자 체크 == true
- 키워드 체크 == true

위와 같이 세 조건이 모두 켜져 있으면 아래 조건을 모두 만족해야 한다.

`수신 메일의 발신자 일치 AND 수신 메일의 참조자 일치 AND 수신 메일의 제목에 키워드 포함`

각 조건 안에 여러 항목이 등록되어 있으면 해당 조건 내부에서는 하나 이상 일치하면 된다.

예:

- 발신자 조건: 발신자 #1 또는 발신자 #2 중 하나와 일치
- 참조자 조건: 참조자 #1 또는 참조자 #2 중 하나와 일치
- 키워드 조건: 키워드 #1 또는 키워드 #2 중 하나가 제목에 포함

조건 체크가 false 인 항목은 판정 대상에서 제외한다.

# 9.1.2 MailClaw 조건 설정 UI

`MailClaw` 조건 설정 화면은 등록된 자동화 목록과 자동화 상세 설정 영역으로 구성한다.

- MailClaw 목록
  - 등록된 `MailClaw` 자동화들을 리스트로 표시한다.
  - 각 항목에는 자동화 이름, 활성/비활성 상태, 주요 조건 요약을 표시한다.
  - `추가`, `수정`, `삭제` 기능을 제공한다.

- 기본 설정
  - 자동화 이름을 입력한다.
  - 자동화 활성/비활성 스위치를 제공한다.

- 발신자 조건 UI
  - `발신자 체크` 스위치 또는 체크박스를 제공한다.
  - `발신자 체크 == true` 인 경우 체크할 발신자 입력 영역을 활성화한다.
  - 발신자는 여러 개 등록할 수 있으며, `발신자 추가` 버튼으로 항목을 늘릴 수 있다.
  - 각 발신자 항목은 삭제할 수 있다.

- 참조자 조건 UI
  - `참조자 체크` 스위치 또는 체크박스를 제공한다.
  - `참조자 체크 == true` 인 경우 체크할 참조자 입력 영역을 활성화한다.
  - 참조자는 여러 개 등록할 수 있으며, `참조자 추가` 버튼으로 항목을 늘릴 수 있다.
  - 각 참조자 항목은 삭제할 수 있다.

- 키워드 조건 UI
  - `키워드 체크` 스위치 또는 체크박스를 제공한다.
  - `키워드 체크 == true` 인 경우 제목 키워드 입력 영역을 활성화한다.
  - 키워드는 메일 제목에 포함될 문자열로 입력한다.
  - 키워드는 여러 개 등록할 수 있으며, `키워드 추가` 버튼으로 항목을 늘릴 수 있다.

- 조건 표시 방식
  - 비활성화된 조건은 입력 영역을 흐리게 표시하고 편집할 수 없게 한다.
  - 활성화된 조건은 입력 영역을 즉시 편집할 수 있게 한다.
  - 발신자, 참조자, 키워드 중 하나 이상을 설정할 수 있다.

- 저장 버튼
  - 입력한 조건과 자동화 동작을 저장한다.
  - 필수값이 누락된 경우 저장하지 않고 누락 항목을 표시한다.

# 9.2 MailClaw 자동화 동작

`MailClaw` 조건에 일치되는 항목이 있으면 아래 자동화 동작을 실행할 수 있다.

1. AI 메일 분석
   - 메일 내용을 AI가 분석한다.
   - 할일 목록(ActionItem)을 추출한다.
   - 약속, 일정 등 날짜 등록이 필요한 항목을 추출한다.
   - 메일 내용을 요약해서 중요 메모로 생성한다.
   - 중요 메모를 텔레그램으로 사용자에게 전송한다.

2. 지정된 메일 주소로 발송
   - 사용자가 지정한 메일 주소로 원본 메일을 전달한다.
   - 발송의 의미는 AI 요약문 발송이 아니라 수신한 원본 메일의 전달이다.
   - 원본 메일의 제목, 본문, 주요 헤더, 첨부파일을 가능한 범위에서 유지해서 전달한다.

3. 지정된 폴더로 이동
   - 사용자가 지정한 폴더로 메일을 이동한다.

# 9.2.1 MailClaw 자동화 실행 순서

여러 자동화 동작이 동시에 켜져 있으면 아래 순서로 실행한다.

1. AI 메일 분석
2. 지정된 메일 주소로 원본 메일 전달
3. 지정된 폴더로 이동

예를 들어 `폴더 이동`과 `지정된 메일 주소로 발송`이 모두 켜져 있으면 먼저 원본 메일을 지정된 주소로 전달한 뒤 폴더를 이동한다.

`AI 메일 분석`과 `지정된 메일 주소로 발송`이 모두 켜져 있으면 AI 분석을 먼저 수행한 뒤 원본 메일을 지정된 주소로 전달한다.

각 동작은 독립적으로 실행한다.

- 특정 동작이 실패해도 다음 동작은 계속 실행한다.
- 실패한 동작은 실행 로그에 실패 상태와 실패 원인을 기록한다.
- 성공한 동작은 실행 로그에 성공 상태와 실행 시간을 기록한다.

# 9.3 MailClaw 실행 기준

새로운 메일이 수신되면 시스템은 아래 순서로 자동화를 처리한다.

1. 등록된 전체 `MailClaw` 목록을 조회한다.
2. 각 `MailClaw` 설정의 발신자, 참조자, 키워드 조건을 확인한다.
3. 조건에 일치하는 `MailClaw`가 있으면 해당 자동화 동작을 실행한다.
4. 여러 개의 `MailClaw` 조건에 일치할 수 있으며, 일치한 자동화는 각각 실행한다.

# 10. Mail 보내기 첨부파일 처리

현재 `메일 쓰기` 화면은 받는 사람/참조/숨은참조/제목/본문만 입력받아 `POST /mail/accounts/:id/send` 로 JSON을 전송한다. 첨부파일을 추가하는 UI가 없고, 발신 메일 저장 시에도 첨부는 항상 빈 목록(`attachments: []`)으로 저장된다. 이 장은 `메일 쓰기`에서 첨부파일을 추가·전송·저장하는 방식을 정의한다.

# 10.1 첨부 추가 UI (클립 버튼)

- `메일 쓰기` 상단 도구 영역(`보내기`, `임시 저장` 등이 있는 줄) 아래에 첨부 추가용 `클립` 버튼을 배치한다.
- 클립 버튼을 누르면 파일 선택 대화상자를 연다.
  - 숨겨진 `<input type="file" multiple>` 을 클립 버튼과 연결한다.
  - 여러 파일을 한 번에 선택할 수 있다.
- 선택한 파일은 즉시 업로드하지 않고, 전송(`보내기`) 또는 임시 저장 시점에 함께 서버로 보낸다.
- 같은 파일(파일명 + 크기 동일)을 중복 선택하면 한 번만 추가한다.

# 10.2 Drag & Drop 추가 (옵션 검토)

- `메일 쓰기`의 본문 편집 영역을 Drag & Drop 대상으로 지정하여, 파일을 끌어다 놓아도 첨부에 추가되도록 한다.
- 동작 정의
  - 파일을 편집 영역 위로 끌어오면(`dragover`) 드롭 가능 상태를 시각적으로 표시한다(테두리 강조 등).
  - 파일을 놓으면(`drop`) 클립 버튼으로 선택한 것과 동일하게 첨부 목록에 추가한다.
  - 브라우저 기본 동작(파일을 새 탭으로 여는 것)을 막기 위해 `dragover`/`drop` 기본 이벤트를 취소한다.
- 본문에 이미지가 인라인으로 삽입되는 것과 혼동되지 않도록, 드롭한 파일은 본문 삽입이 아니라 첨부로만 처리한다.
- Drag & Drop은 편의 옵션이며, 클립 버튼(10.1)이 기본 진입점이다. 두 방식은 동일한 첨부 목록 상태를 공유한다.



# 10.3 첨부 목록 표시 및 삭제

- 추가된 첨부는 클립 버튼 아래에 목록으로 표시한다.
- 각 항목에는 파일명, 파일 크기를 표시한다.
- 각 항목에는 개별 삭제(`x`) 버튼을 제공한다.
- 첨부가 하나 이상이면 총 개수(`첨부파일 N개`)를 함께 표시한다.
- 목록이 화면을 넘어서면 첨부 목록 영역 안에서 스크롤한다.

# 10.4 첨부 제한

- 첨부 1건 및 합계 용량 상한을 둔다(예: 단일 25MB, 합계 25MB — SMTP 제공자 정책에 맞춘다).
- 상한을 초과하는 파일을 추가하면 추가를 거부하고 사유를 표시한다.
- 실행 파일 등 위험 확장자는 서버에서 차단할 수 있도록 정책을 둔다(선택).

# 10.5 전송 처리

- 첨부가 포함된 전송은 JSON 대신 `multipart/form-data` 로 보낸다.
  - 프론트는 `FormData` 에 `tenantId`, `to`, `cc`, `bcc`, `subject`, `html`, `text` 와 파일들(`attachments`)을 담아 `POST /mail/accounts/:id/send` 로 전송한다.
  - 백엔드는 `multipart/form-data` 파서(예: `multer` 메모리 스토리지)로 파일을 받는다.
  - 대안으로 파일을 base64로 인코딩해 JSON에 담는 방식이 있으나, 본문 크기 증가와 `express.json` 크기 제한 때문에 `multipart/form-data` 를 권장한다.
- 백엔드는 받은 파일을 `nodemailer` `sendMail` 의 `attachments` 옵션으로 전달한다.
  - `attachments: [{ filename, content: <Buffer>, contentType }]` 형태로 구성한다.
- 첨부만 있고 제목·본문이 비어 있는 경우의 유효성 검사 기준은 기존 규칙(제목 또는 본문 필요)을 유지하되, 필요 시 첨부 존재도 허용 조건에 포함할지 검토한다.

# 10.6 발신 메일 첨부 저장

- 전송에 성공하면 발신 메일과 첨부를 수신 메일과 동일한 구조로 저장한다.
  - 각 첨부 파일은 스토리지에 개별 오브젝트로 저장한다.
  - `object_key` 는 5원칙에 따라 `tenants/{tenant_id}/users/{user_id}/mail/{account_id}/messages/{provider_message_id}/attachments/{index}-{filename}` 형태로 만든다.
  - 첨부 메타데이터(파일명, content_type, 크기, `object_key`)는 `mail_attachments` 테이블에 저장한다.
  - DB 접근은 반드시 `mailRepository`(`saveSyncedMessage` 계열)를 통해 수행한다.
- 저장 후에는 보낸 메일함 상세에서 수신 메일과 동일하게 첨부 목록/다운로드(9장·상세 뷰 규칙)를 제공한다.

# 10.7 임시 보관함 첨부 (선택)

- 임시 저장(`POST /mail/accounts/:id/drafts`) 시에도 첨부를 함께 보관할 수 있도록 확장한다.
- 임시 보관 메일을 다시 열면 저장해 둔 첨부 목록이 복원되어 편집을 이어갈 수 있어야 한다.
- 1차 구현 범위에서 제외할 경우, 임시 저장에는 첨부가 포함되지 않음을 명시한다.

# 10.8 첨부파일 정책 관리 화면

## 10.8.1 배경 / 문제

현재 첨부 제한값은 코드 상수로 하드코딩되어 있어 운영 중 조정하려면 배포가 필요하다.

- 백엔드([server/routes/mail.js](../server/routes/mail.js)): `MAIL_ATTACH_MAX_BYTES = 25MB`, multer `files: 20`, 전송 시 합계 용량 재검증.
- 프론트([src/features/mail/MailPage.jsx](../src/features/mail/MailPage.jsx)): `MAX_ATTACH_TOTAL_BYTES = 25MB`.
- 위험 확장자 차단(10.4의 "선택" 항목)은 아직 구현되어 있지 않다.

SMTP 제공자마다 허용 용량이 다르고(예: Gmail 25MB, 일부 사내 서버는 10MB), 실행 파일 차단 필요 여부도 운영 환경마다 다르므로, 값을 **관리 화면에서 조정**할 수 있어야 한다.

## 10.8.2 설계 결정 (검토)

- **저장 위치**: 기존 전역 설정 테이블 `mail_service_settings`(key-value, 사이트 관리자용)를 재사용한다. 별도 테이블을 만들지 않는다. Google OAuth 설정과 동일한 방식이라 인프라(`getMailSetting`/`upsertMailSetting`)를 그대로 활용한다.
- **정책 범위(전역 vs tenant vs 계정)**:
  - 1차는 **전역 사이트 설정** 하나로 둔다. 현재 하드코딩 상수가 전역이므로 이를 그대로 대체하는 것이 가장 단순하고 회귀 위험이 없다.
  - tenant별/계정(SMTP 제공자)별 상한은 향후 확장 지점으로 남긴다. 계정별로 두면 제공자 정책에 정확히 맞출 수 있으나, 계정 스키마 확장·마이그레이션·UI 복잡도가 커지므로 1차 범위에서 제외한다. 5원칙(모든 메일 테이블 `tenant_id`)은 이 값이 **메일 데이터가 아니라 서비스 전역 설정**이므로 적용 대상이 아니다.
- **권한**:
  - **편집**은 사이트 관리자(`role === 'site_admin'`)만 가능하다. 기존 `PUT /mail/settings`가 `requireSiteAdmin`으로 보호되는 것과 동일한 기준.
  - **읽기**는 인증된 메일 사용자 모두 가능해야 한다. 메일 작성 화면이 서버 정책을 그대로 강제(용량/개수/확장자 안내 및 거부)해야 하기 때문이다. 따라서 정책 조회는 관리자 전용 `GET /mail/settings`와 분리한다.
- **강제 지점(이중 방어)**:
  - 프론트(작성 화면)는 UX를 위해 선제적으로 검증·안내한다(즉시 거부 + 사유 표시).
  - 백엔드(전송 라우트)는 신뢰 경계이므로 **항상** 최종 검증한다. 프론트 우회 요청도 서버에서 반드시 거부한다.
- **동적 multer**: multer 인스턴스는 모듈 로드 시 상수 limits로 만들어지므로, 정책을 반영하려면 요청 시점에 정책을 읽어 limits를 구성해야 한다. `handleMailSendUpload`를 정책 로드 후 multer를 생성하는 형태로 바꾼다. 확장자 차단은 업로드 후 파일명 기준으로 검사한다.

## 10.8.3 정책 항목

| 항목 | 설정 키(`mail_service_settings`) | 기본값 | 설명 |
|---|---|---|---|
| 단일 파일 최대 용량 | `attach_max_file_mb` | 25 | 첨부 1건 상한(MB) |
| 합계 최대 용량 | `attach_max_total_mb` | 25 | 첨부 전체 합계 상한(MB) |
| 최대 개수 | `attach_max_files` | 20 | 한 메일당 첨부 개수 상한 |
| 차단 확장자 | `attach_blocked_extensions` | `exe,bat,cmd,com,scr,pif,js,vbs,jar,msi,cpl,dll` | 업로드/전송 차단 확장자 목록 |

- 값은 정수(MB/개수) 및 확장자 목록(콤마 구분 문자열 → 소문자·`.` 제거 정규화)으로 저장한다.
- 유효성: 각 상한은 1 이상, 합리적 상한(예: 파일/합계 200MB, 개수 100) 이내로 clamp한다. 잘못된 값은 저장 거부 대신 기본값/직전값으로 보정한다.

## 10.8.4 API

- `GET /mail/attachment-policy` — 인증된 사용자면 조회 가능. 작성 화면이 이 값으로 검증한다.
  - 응답: `{ max_file_mb, max_total_mb, max_files, blocked_extensions: [] }`
- `PUT /mail/attachment-policy` — `requireSiteAdmin`. 위 4개 항목을 저장하고 정규화된 최신 정책을 반환한다.

## 10.8.5 관리 화면(UI)

- 진입: **메일 계정 관리 팝업**(`MailAccountManageModal`)의 메뉴에 `첨부파일 정책` 항목을 추가한다(`MailClaw` 아래).
- 구성:
  - 단일 파일 최대(MB), 합계 최대(MB), 최대 개수 숫자 입력.
  - 차단 확장자 입력(콤마 구분, 칩 표시).
  - `저장` 버튼.
- 권한 표시:
  - 사이트 관리자: 편집·저장 가능.
  - 비관리자: 값은 읽기 전용으로 보여주고, "사이트 관리자만 변경할 수 있습니다" 안내를 표시한다.

## 10.8.6 강제(검증) 규칙

- 작성 화면(프론트)
  - 파일 추가 시: 개별 파일 > 단일 상한 → 거부, 합계 > 합계 상한 → 거부, 총 개수 > 개수 상한 → 거부, 확장자 ∈ 차단목록 → 거부. 각 경우 사유를 표시한다.
- 전송 라우트(백엔드, 최종 방어)
  - multer `limits.fileSize = max_file_mb`, `limits.files = max_files`로 업로드 자체를 제한한다.
  - 업로드 후: 합계 > `max_total_mb` → 413, 파일명 확장자 ∈ 차단목록 → 415(또는 400)로 거부한다.
- 두 계층의 메시지는 동일한 정책값을 근거로 하여 사용자에게 일관되게 안내한다.

## 10.8.7 범위 밖(향후 확장)

- tenant별/계정(제공자)별 개별 상한.
- 확장자 **허용 목록(allowlist)** 모드(현재는 차단 목록(blocklist)만).
- MIME 스니핑 기반 실제 파일형식 검사(확장자 위장 차단). 1차는 확장자 문자열 기준.

# 10.8.8 메일 목록의 첨부 표시(클립 마크)

## 10.8.8.1 목적

메일 목록에서 **첨부파일이 있는 메일**을 한눈에 구분할 수 있도록, 목록 항목에 클립(📎) 마크를 표시한다. 현재 목록에는 보낸 사람/제목/미리보기만 있어, 메일을 열기 전에는 첨부 유무를 알 수 없다.

## 10.8.8.2 표시 조건

- 각 목록 항목의 데이터에 있는 **`has_attachments`** 값이 `true`일 때만 클립 마크를 표시한다.
  - 이 값은 목록 조회 쿼리가 이미 반환한다(`mm.has_attachments`, 예: [repository.js](../server/mail/repository.js) 의 `listUnifiedMessages`/폴더 목록 쿼리). **추가 조회나 상세 진입 없이** 목록 렌더 시점에 바로 판정한다.
- `has_attachments`가 `false`/없음이면 마크를 표시하지 않는다.
- 인라인 이미지만 있고 실제 첨부가 없는 메일은 `has_attachments` 기준을 따른다(별도 구분은 하지 않는다).

## 10.8.8.3 위치 / 모양

- **위치**: 목록 항목(카드)의 **오른쪽 아래** 모서리.
  - 대상 컴포넌트: 메일 목록 항목 렌더 블록([MailPage.jsx](../src/features/mail/MailPage.jsx) 의 목록 `button` 항목 — 보낸사람/날짜/제목/미리보기(snippet)를 그리는 영역).
  - 현재 항목 구조는 왼쪽 아이콘 열(체크/안읽음 점 + 발신자 로고) + 오른쪽 본문 열(상단: 보낸사람·날짜, 그 아래 제목, 그 아래 미리보기)로 되어 있다. 클립 마크는 **본문 열의 우하단**에 배치해, 날짜(우상단)와 세로로 겹치지 않게 한다.
- **아이콘**: 클립(paperclip). 상세 뷰의 `파일 첨부`/첨부 목록에서 쓰는 클립 아이콘과 동일 계열을 사용해 일관성을 유지한다.
- **크기/색**: 작고 은은하게. 미리보기 텍스트와 비슷하거나 한 톤 옅은 회색(예: `text-gray-400`), 아이콘 크기 12~14px 수준. 안읽음(굵게 표시) 항목에서도 과하게 튀지 않도록 한다.
- **정렬**: 우하단에 고정. 미리보기(snippet)가 길어도 마크가 텍스트에 가리지 않도록, 마크 영역을 별도 라인/우측 정렬로 확보한다.

## 10.8.8.4 동작 / 접근성

- 클립 마크는 **표시 전용**이며 클릭 동작은 없다(항목 전체 클릭은 기존대로 메일 열기).
- 접근성: 아이콘에 `aria-label`/`title`(예: "첨부파일 있음")을 부여해 스크린리더/툴팁에서 의미가 전달되게 한다.
- 개수 표시는 하지 않는다(유무만 표시). 정확한 개수/파일명은 상세 뷰의 첨부 목록(7.5 / 10.6)에서 확인한다.

## 10.8.8.5 범위 밖(향후 확장)

- 첨부 **개수 배지**(예: 📎 3) 표시.
- 첨부 **종류 아이콘**(이미지/문서/압축 등) 구분.
- 목록에서 마크에 마우스오버 시 첨부 파일명 미리보기 툴팁.

# 10.9 메일 전송 안정화 (SMTP 타임아웃 · 전송 로깅 · 오류 메시지)

## 10.9.1 배경 / 문제

실제 운영 중 다음 문제가 관찰되었다.

- **무한 "보내는 중"**: SMTP 전송(`transporter.sendMail`)에 타임아웃이 설정되어 있지 않아, 네트워크 지연/정지 시 요청이 끝나지 않고 매달릴 수 있다.
- **진단 불가**: 전송 시작/완료/소요시간/페이로드 크기를 남기는 로그가 없어, 느린 전송이 첨부 때문인지 네트워크 때문인지 사후 확인이 어렵다.
- **불친절한 오류**: 첨부 총량이 제공자 한도를 넘으면 Gmail이 SMTP `552-5.3.4`(message size exceeded)로 거부하는데, 이 오류가 그대로 전역 에러 핸들러로 넘어가 사용자에게는 **"서버 오류가 발생했습니다"** 로만 표시된다. (실제 사례: 첨부 합계 약 36MB, 단일 29MB mp4 포함 → Gmail 25MB 한도 초과 → 552)

핵심 원인: **앱 첨부 정책 상한(당시 100MB)이 제공자 실제 한도(약 25MB)보다 커서** 앱은 통과시키고 제공자가 거부. base64 인코딩으로 전송 크기가 약 +37% 늘어나는 점도 반영되지 않았다.

## 10.9.2 개선 항목 (검토 결과 채택)

### 1) SMTP 타임아웃

`nodemailer.createTransport`에 타임아웃 3종을 추가한다. 네트워크 문제 시 무한 대기 대신 명확히 실패시킨다.

| 옵션 | 값 | 의미 |
|---|---|---|
| `connectionTimeout` | 15초 | TCP 연결 수립 대기 |
| `greetingTimeout` | 15초 | 서버 인사(220) 대기 |
| `socketTimeout` | 60초 | 데이터 전송 중 무응답 허용치(대용량 업로드 고려해 넉넉히) |

### 2) 전송 로깅

전송 라우트(`POST /mail/accounts/:id/send`)에 구조적 로그를 남긴다.

- **시작**: 계정, 수신자 수, 첨부 개수, 본문/첨부 합계 크기, base64 반영 **예상 전송 크기**.
- **완료**: 소요 시간(ms), `messageId`, accepted/rejected 수.
- **실패**: 소요 시간(ms), `code`/`responseCode`, 원본 메시지.

이로써 "느린 전송"이 페이로드 크기 때문인지, 타임아웃 때문인지 로그만으로 즉시 판별할 수 있다.

### 3) 오류 메시지 개선

`sendMail`을 try/catch로 감싸 nodemailer 오류를 사용자 친화적 상태코드/메시지로 매핑한다(`mapSmtpSendError`). 전역 "서버 오류" 대신 원인을 안내한다.

| 조건 | 상태 | 메시지(요지) |
|---|---|---|
| `EMESSAGE` / `552` / size 초과 | 413 | 메일 크기가 제공자 한도를 초과. 첨부 용량을 줄이세요(원본 기준 정책 합계보다 작아야 할 수 있음). |
| `ETIMEDOUT`/`ESOCKET`/`ECONNECTION`/timeout | 504 | 메일 서버 응답 지연으로 전송 미완료. 네트워크 확인 후 재시도. |
| `EAUTH` / `535` | 401 | 메일 서버 인증 실패. 앱 비밀번호 확인. |
| `EENVELOPE` / `550` | 400 | 받는 사람 주소 거부. 주소 확인. |
| 기타 | 502 | 전송 실패. 잠시 후 재시도. |

### 4) 안전 기본값 하향 (즉시 조치)

- 첨부 정책 **기본값**의 단일/합계를 25MB → **20MB**로 낮춘다(백엔드 `DEFAULT_ATTACHMENT_POLICY`, 프론트 `DEFAULT_ATTACH_POLICY` 일치). Gmail 25MB에 base64 오버헤드를 감안한 안전선.
- 관리 화면(10.8.5)에 안내 문구 추가: "제공자 한도 약 25MB, base64로 약 +37%, 합계 원본 기준 20MB 이하 권장".
- 주의: 기본값 하향은 **신규/미설정 tenant에만** 적용된다. 이미 저장된 값(예: 100MB)은 **관리 화면에서 직접 낮춰야** 반영된다.

## 10.9.3 구현 위치

# 10.10 컴포즈 첨부 이미지 미리보기

## 10.10.1 배경 / 목적

- 메일 쓰기(컴포즈)에서 첨부한 파일이 이미지면, 지금의 이름·용량만 표시하는 칩 대신 **작은 썸네일**을 보여 어떤 이미지인지 즉시 확인하고 싶다.

## 10.10.2 가능성 / 전제 (프론트 전용, 저비용)

- 컴포즈 첨부는 **전부 로컬 `File` 객체**다([MailPage.jsx](../src/features/mail/MailPage.jsx) `addFiles`가 `File`을 그대로 state에 저장). 초안 편집도 `getDraftComposeData`가 첨부를 되불러오지 않아, 컴포즈 첨부는 **항상 방금 추가한 로컬 파일**뿐이다.
- 따라서 `URL.createObjectURL(file)`로 **서버 왕복 없이** 표시용 URL을 만들어 `<img>`에 물리면 된다. **100% 로컬 파일이라 안정적**이고, 서버/스토리지/API 변경이 전혀 없다.
- 이미지 판별: `file.type.startsWith('image/')`(MIME) + 확장자 폴백.

## 10.10.3 동작 / 범위

- 첨부 칩에서 파일이 이미지면 **작은 썸네일**(예: 40×40, `object-fit: cover`)을 앞에 표시하고, 이미지가 아니면 기존 클립/파일 아이콘·표기를 유지한다.
- (선택) 썸네일 클릭 시 **원본 확대(라이트박스)**. 1차는 썸네일만 필수, 확대는 옵션.
- 서버/스토리지/전송 로직 변경 없음(전송은 기존대로 `FormData`에 `File` 그대로 첨부).

## 10.10.4 구현 위치

- [MailPage.jsx](../src/features/mail/MailPage.jsx) 컴포즈 첨부 칩 렌더 부분(`attachments.map(...)`): 이미지 파일에 한해 `createObjectURL` 썸네일 추가.
- object URL 수명 관리: 첨부별 URL을 만들고, **삭제/컴포즈 종료 시 `URL.revokeObjectURL()`로 반드시 해제**(useEffect cleanup)한다.

## 10.10.5 주의점

- **메모리 누수 방지**: 만든 object URL은 반드시 revoke(첨부 제거·언마운트 시).
- **렌더 불가 포맷 폴백**: JPG/PNG/GIF/WebP/SVG는 정상 표시. **HEIC/HEIF·일부 TIFF**는 브라우저가 못 그리므로 일반 파일 칩으로 폴백.
- **SVG 보안**: `<img src=blob>`로만 렌더(샌드박스). SVG를 HTML로 인라인 삽입 금지(스크립트 실행 위험).
- **레이아웃**: 썸네일이 생기면 칩 높이가 커지므로 고정 크기 그리드로 정렬.
- 성능: 첨부 정책 상한(10.8)이 있어 부담은 미미하다.

## 10.10.6 범위 밖(향후 확장)

- 수신 메일(읽기 뷰) 첨부의 이미지 인라인 미리보기(그쪽은 서버 fetch URL `/api/mail/messages/:id/attachments/:attId` 기반이라 별도 설계).
- PDF·문서 미리보기, 썸네일 캐싱.

# 11. 메일 카드 Drag & Drop (폴더로 끌어 이동)

메일 목록의 카드를 왼쪽 사이드바의 **폴더 버튼**으로 끌어다 놓으면(Drag & Drop) 그 폴더로 메일이 이동한다. 컨텍스트 메뉴의 `이동`(7.x)과 동일한 결과를 마우스 제스처로 제공한다. 이 장은 구현 방식을 **설계/검토**한 결과이며, 실제 코드는 별도 작업으로 진행한다.

## 11.1 동작 개요

- 목록에서 카드를 잡아 사이드바의 대상 폴더 위로 드래그하고 놓으면, 해당 메일이 그 폴더로 이동한다.
- 놓는 순간, 원본 폴더 목록에서 카드가 사라지고 원본/대상 폴더의 카운트가 갱신된다(낙관적 업데이트).
- **다중 이동**: 여러 통이 선택된 상태(예: 상단 `N개 선택됨`)에서 그중 하나를 드래그하면 **선택된 전체**가 함께 이동한다. 선택에 없는 카드를 드래그하면 **그 한 통만** 이동한다.

## 11.2 기존 자산 재사용 (핵심)

새 이동 로직을 만들 필요가 없다. 다음이 이미 구현되어 있다.

- **이동 실행 함수**: [MailPage.jsx](../src/features/mail/MailPage.jsx) 의 `moveMessage(target, folder)`.
  - 내부에서 `getActionMessages(target)`로 대상 메일을 산출한다. `target.targetIds`가 있으면 다중, 없으면 단건. → 11.1의 다중/단건 규칙을 그대로 만족한다.
  - `PATCH /mail/messages/bulk`(`action: 'move'`, `targetFolderId`, `messageIds`)로 서버 이동을 수행한다.
  - 성공 시 목록에서 제거 + 선택 해제 + `adjustFolderCounts`로 원본/대상 카운트를 조정한다.
- **드롭 핸들러가 할 일**: `moveMessage({ targetIds: <드래그 대상 id 배열> }, folder)` 를 호출하는 것뿐이다.

즉 DnD 작업의 범위는 **① 카드에 드래그 시작을 붙이고, ② 폴더 버튼에 드롭을 붙여 `moveMessage`를 부르는 것** 두 가지다.

## 11.3 드래그 소스 (메일 카드)

- 대상: [MailPage.jsx](../src/features/mail/MailPage.jsx) 의 `MailMessageList` 목록 항목 `button`(발신자/제목/미리보기를 그리는 카드).
- 방식: HTML5 네이티브 DnD를 사용한다(메일 쓰기 첨부 Drag & Drop(10.2)에서 이미 네이티브 방식을 쓰므로 일관).
  - 카드에 `draggable` 지정, `onDragStart`에서 **이동할 id 목록**을 확정해 실어보낸다.
  - id 목록 산출 규칙: 드래그한 카드가 현재 선택(`selectedMessageIds`)에 포함되어 있으면 선택 전체, 아니면 그 카드 하나. (컨텍스트 메뉴의 `openMessageMenu`가 쓰는 규칙과 동일하게 맞춘다.)
  - 전달 수단: `dataTransfer.setData('application/x-mail-ids', JSON.stringify(ids))` 등 커스텀 MIME. 파일 드롭(10.2)과 구분되도록 별도 타입을 쓴다.
  - 드래그 이미지: 여러 통이면 "N개 이동" 배지 형태의 드래그 프리뷰를 고려(선택).
- 주의: 카드에는 기존 `onClick`(열기)·`onContextMenu`(메뉴)가 있으므로, 드래그와 클릭이 충돌하지 않게 한다(짧은 이동은 클릭으로 처리되는 네이티브 동작을 그대로 활용).

## 11.4 드롭 타깃 (사이드바 폴더 버튼)

- 대상: [MailPage.jsx](../src/features/mail/MailPage.jsx) 의 `MailMenuButton`으로 렌더되는 **계정별 폴더 항목**(`account.folders`의 각 folder, 실제 `folder.id` 보유).
- 붙일 것: `onDragOver`(기본 취소 → 드롭 허용), `onDrop`(id 파싱 후 `moveMessage` 호출), `onDragEnter/Leave`(하이라이트 토글).
- **유효 타깃 판정**:
  - 실제 폴더(계정 폴더, 받은 편지함, 사용자 지정 폴더, **휴지통**)만 유효.
  - **가상/통합 메뉴는 제외**: `모든 편지함`·`별표됨`·`검색`은 실제 폴더가 아니므로 드롭 대상에서 제외한다. (`보낸 메일`·`임시 보관함`은 이동 의미가 모호하므로 1차 제외; 필요 시 후속 검토.)
  - **원본과 동일 폴더**로의 드롭은 무시(이미 `moveMessage`가 `folder_id === folder.id`를 걸러냄).
  - `sync_status === 'missing'`(서버에 없는 로컬 표시 폴더)로의 드롭은 막거나 경고.
- **계정 간 이동**: 다른 계정의 폴더로 드롭하는 경우의 처리(허용/차단)는 서버 bulk 이동 및 `providerMove`의 계정 간 이동 지원 범위에 맞춘다. 1차에서 계정 간 이동을 제한한다면, 드래그 중 다른 계정 폴더는 유효 타깃에서 제외해 시각적으로 막는다.

## 11.5 시각 피드백

- 드래그 시작: 커서/드래그 프리뷰로 이동 중임을 표시.
- 유효 폴더 위 `dragover`: 해당 폴더 버튼을 강조(테두리 ring 또는 배경 하이라이트). 활성 폴더 스타일(indigo)과 구분되는 "드롭 가능" 스타일을 쓴다.
- 무효 타깃 위: 강조하지 않음(또는 not-allowed 커서).
- 드롭 완료: 강조 해제, 카드 제거 애니메이션은 선택.

## 11.5.1 개정 — 통합 메뉴 드롭 지원 + 파란색 "선택" 하이라이트

1차 구현을 실사용하며 발견한 두 가지를 반영한다. (본 절은 **설계/검토** 결과이며 실제 코드는 별도 작업으로 진행한다.)

### 1) 통합 메뉴로 드롭했을 때 "드롭이 안 됨" 문제

- **증상**: 상단 **통합 메뉴**(모든 편지함/받은 편지함/휴지통/사용자 지정 이름 폴더 등)로 카드를 끌면 드래그는 되지만, 놓아도 이동하지 않는다. 계정별 실제 폴더(하단 목록)로는 정상 이동한다.
- **원인**: 1차 구현은 계정별 폴더 버튼에만 드롭 핸들러(`onDragOver`/`onDrop`)를 배선했다. 통합 메뉴 버튼(`unifiedMenus`)에는 핸들러가 없어 브라우저 기본 동작상 드롭 자체가 불가하다. 또한 통합 메뉴 항목은 여러 계정을 **집계한 가상 항목**이라 단일 `folder.id`가 없어, 기존 `moveMessage(target, folder)`(단일 `folder.id` 필요)를 그대로 부를 수 없다.
- **해결 설계 — 통합 메뉴를 "계정별 실제 폴더"로 해석해 이동**:
  - 통합 메뉴 항목은 두 종류다.
    - **시스템 타입 집계**: `type`(`inbox`/`sent`/`drafts`/`trash`)으로 묶인 항목. `모든 편지함`(`all`)·`별표됨`(`starred`)·`검색`(`search`)은 `type`이 없다.
    - **사용자 지정 이름 집계**: `normalizeFolderName(name)`이 같은 폴더들을 이름으로 묶은 항목(`key: name:<이름>`).
  - 드롭 시 **드래그된 각 메일이 속한 계정(`message.account_id`) 안에서** 대상 폴더를 해석한다.
    - 시스템 타입 항목 → 그 계정의 `folders` 중 같은 `type` 폴더.
    - 사용자 지정 이름 항목 → 그 계정의 `folders` 중 `normalizeFolderName(name)`이 일치하는 폴더.
  - 선택이 **여러 계정에 걸쳐 있을 수 있으므로**, 해석된 대상 `folder.id` 기준으로 메일을 **그룹핑**해 그룹마다 `moveMessage({ targetIds }, 해석된_folder)`를 호출한다(계정/대상 폴더별 bulk 이동). 카운트·목록 제거·선택 해제는 기존 로직이 그대로 처리한다.
  - **유효 타깃 판정**(통합 메뉴):
    - **유효**: `받은 편지함`(inbox), `휴지통`(trash), 사용자 지정 이름 폴더. (각 계정에 해당 폴더가 실제로 있을 때만 그 계정 메일이 이동한다.)
    - **제외(무효)**: `모든 편지함`·`별표됨`·`검색`은 실제 대상이 없어 제외. `보낸 메일`·`임시 보관함`은 이동 의미가 모호하여 1차 제외(11.4와 동일 기준).
    - 특정 계정에 대상 폴더가 없으면 그 계정 메일은 **조용히 건너뛴다**(부분 이동 허용). 전부 해석 실패면 아무 동작도 하지 않는다.
- 이로써 11.6의 "통합 메뉴로의 드롭은 무동작" 방침은 **위 유효 타깃에 한해 이동 동작으로 개정**된다(가상 항목 all/starred/search는 여전히 무동작).
- **대치 예고(13장)**: 본 절의 "사용자 지정 이름 집계" 통합 폴더(`key: name:<이름>`)와 그 드롭(`moveMessagesToUnified`의 `folderName` 분기)은 **13장 태그 기반 스마트 폴더로 전면 대체·폐기**된다. 시스템 타입 항목(`받은 편지함`·`휴지통` 등)의 드롭 이동은 그대로 유지된다.

### 2) 드롭 하이라이트를 파란색 "선택" 스타일로 (인지성 강화)

- **요구**: 드래그 중 커서가 올라간 대상 폴더가 **눈에 띄게** "지금 여기로 놓인다"를 보여줘야 한다. 1차의 초록(emerald) 링은 약해서 인지성이 낮았다.
- **변경**: `dragover` 하이라이트를 **활성 폴더(선택)와 동일 계열의 파란색(indigo) "선택된" 스타일**로 바꾼다(초록 → 파랑). 즉 드롭 후보 폴더가 잠시 **선택된 항목처럼** 보이게 하여, 어디로 이동될지 즉시 인지되게 한다.
  - 활성 폴더와의 혼동을 줄이기 위해 파란 채움에 **링/굵기 등 미세 차이**를 더할 수 있으나(선택), 기본은 "선택된 UI로 보이게"를 우선한다.
- 무효 타깃 위에서는 강조하지 않는다(11.5 그대로). 드롭/드래그 종료 시 하이라이트를 해제한다.

## 11.6 예외 / 안정성

- 놓는 위치가 폴더가 아니면(빈 영역, 계정 헤더, 통합 메뉴 등) 아무 동작도 하지 않는다.
- 이동 실패 시 `moveMessage`의 기존 처리대로 `messagesError`에 사유를 표시한다(낙관적 업데이트는 서버 응답 실패 시 사용자에게 노출).
- DnD는 마우스 전용 편의 기능이다. **키보드/접근성 대체 경로로 컨텍스트 메뉴의 `이동`을 계속 유지**한다.
- 터치 환경: 1차는 데스크톱 마우스 기준. 터치 DnD는 후속 검토.

## 11.7 구현 범위 요약 (검토 결론)

| 구분 | 작업 | 신규/재사용 |
|---|---|---|
| 카드 | `draggable` + `onDragStart`(id 목록 dataTransfer) | 신규(소량) |
| 폴더 버튼 | `onDragOver`/`onDrop`/`onDragEnter/Leave` + 하이라이트 상태 | 신규(소량) |
| 이동 실행 | `moveMessage({ targetIds }, folder)` | **재사용** |
| 서버/카운트 | `PATCH /mail/messages/bulk` + `adjustFolderCounts` | **재사용** |

→ 신규 코드는 드래그 시작/드롭 배선과 하이라이트 UI로 국한되고, 이동·서버·카운트 로직은 전부 기존 자산을 재사용한다. 프론트 전용 변경으로 백엔드 수정은 불필요하다(계정 간 이동 정책을 새로 정할 때만 백엔드 확인 필요).

## 11.8 범위 밖(향후 확장)

- 통합 폴더(`별표됨` 등)로의 드롭을 "별표 지정" 같은 의미 동작으로 매핑.
- 계정 간 이동 정식 지원(프로바이더 간 이동, 5장·`providerMove` 정책과 정합).
- 터치/모바일 Drag & Drop.
- 드래그 중 폴더 자동 펼침(접힌 계정 위에 잠시 머무르면 펼치기).

# 11.9 다중 선택 드래그 앤 드롭 (텍스트 선택 하이잭 방지)

## 11.9.1 배경 / 문제

- 단건 카드 드래그는 정상 동작하지만, **여러 메일을 선택한 뒤 Drag & Drop을 하면 이동이 진행되지 않는** 증상이 있다.
- 원인은 이동 로직이 아니라 **브라우저의 네이티브 텍스트 선택이 드래그를 가로채기** 때문이다.
  - 다중 선택의 유일한 경로는 `selectMessage()`의 **Shift+클릭 범위 선택**이다(개별 토글용 Ctrl/Cmd 경로 없음). 카드의 체크(✓) 표시는 클릭 가능한 체크박스가 아니라 `selectedIds.has()` 결과를 그리는 **표시용 마크**일 뿐이다.
  - Shift+클릭은 선택과 동시에 카드들의 텍스트(보낸사람·제목 등)를 **네이티브 텍스트 선택 영역**으로 하이라이트한다.
  - 그 상태에서 카드를 끌면 브라우저가 `draggable` 요소 드래그보다 **선택된 텍스트 드래그**를 우선 처리한다. 결과적으로 `onDragStart`에서 심는 커스텀 페이로드 `application/x-mail-ids`가 드롭 쪽으로 제대로 전달되지 않는다.
  - 드롭 타깃의 `handleFolderDragOver`/`handleUnifiedDragOver`는 `types.includes('application/x-mail-ids')`가 아니면 `preventDefault()`를 하지 않고 return하므로, **드롭 자체가 허용되지 않아 "진행이 안 되는"** 것처럼 보인다.
- 단건 드래그가 정상인 이유: 단순 클릭은 텍스트 선택 영역을 남기지 않으므로 요소 드래그가 정상 성립한다.
- 참고: 이동 실행 로직(`moveMessage`의 배열 처리, `handleFolderDrop`/`handleUnifiedDrop`의 다중 id 파싱)은 **이미 다중을 지원한다**. 문제는 로직이 아니라 UI 계층의 텍스트 선택 하이잭이다.

## 11.9.2 설계 결정 (검토 결론)

**① `select-none`(`user-select: none`)로 선택 자체를 예방하는 것을 메인 처리로 채택하고, ② `onDragStart`에서 남은 선택을 지우는 것을 방어적 보강으로 겹쳐 둔다.**

| 관점 | ① `select-none` (선택 자체를 막음) | ② `removeAllRanges()` (생긴 선택을 지움) |
|---|---|---|
| 동작 성격 | 예방 — 텍스트 선택 영역이 애초에 안 생김 | 사후 처리 — 이미 생긴 선택을 드래그 직전에 제거 |
| Shift+클릭 UX | 파란 텍스트 하이라이트가 안 생겨 깔끔 | 선택하는 동안 파란 하이라이트가 그대로 노출 |
| 타이밍 의존성 | 없음 | `dragstart` 시점에 정확히 지워야 함. 브라우저가 이미 "텍스트 드래그"로 판정한 뒤면 늦을 수 있음 |
| 부작용 | 카드 텍스트를 드래그로 복사 선택 불가(메일 목록 카드는 조작용 UI라 손실 사실상 없음) | 없음(선택만 제거) |

→ ②는 "선택이 생긴 뒤 → 드래그 순간에 지운다"는 순서라 브라우저별로 타이밍이 늦어 간헐 실패 여지가 있다. ①은 **원인(선택 생성) 자체를 제거**하므로 견고하고, Shift+클릭 하이라이트도 사라져 선택 UX가 개선된다. 둘을 함께 두면 상위에서 선택이 새는 경우까지 커버된다.

## 11.9.3 구현 위치 (프론트 전용)

- **① 메인**: 메일 카드(`MailMessageList`의 `<button>`) 또는 목록 컨테이너에 `select-none`(Tailwind) / `user-select: none` 부여. 카드에 직접 주는 것이 범위가 명확하다.
- **② 보강(선택)**: 카드 `onDragStart` 도입부에서 `application/x-mail-ids`를 세팅하기 **전에** `window.getSelection()?.removeAllRanges()`를 한 번 호출.
- 이동·서버·카운트 로직(`moveMessage` → `PATCH /mail/messages/bulk` → `adjustFolderCounts`)은 **변경 없음**. 백엔드 수정 불필요.

## 11.9.4 범위 밖(향후 확장)

- Ctrl/Cmd 개별 토글 다중 선택 도입(현재는 Shift 범위 선택만).
- 터치/모바일에서의 다중 선택 드래그.

# 12. 휴지통 비우기

휴지통 폴더의 컨텍스트 메뉴에 **`휴지통 비우기`** 항목을 두고, 실행하면 그 휴지통 폴더에 있는 **모든 메일을 영구 삭제**한다. 일반 `메일 삭제`(7.x)가 메일을 휴지통으로 **이동**시키는 소프트 삭제인 것과 달리, 이 동작은 **복구 불가능한 하드 삭제**다. 그래서 반드시 확인 절차를 거친다. 이 장은 현재 구현된 동작을 정리한 것이다.

## 12.1 동작 개요

- 사이드바에서 **휴지통 폴더**를 우클릭하면 폴더 컨텍스트 메뉴가 열린다. 그 폴더가 `type === 'trash'` 일 때만 메뉴 하단에 **`휴지통 비우기`**(빨강, 위험) 항목이 **추가로** 나타난다. 일반 폴더에는 나타나지 않는다.
- 항목을 누르면 즉시 삭제하지 않고 **확인 다이얼로그**를 띄운다. 사용자가 `확인`을 눌러야 삭제가 실행된다.
- 삭제 성공 시 해당 휴지통 폴더의 카운트를 0으로 만들고, 그 폴더를 보고 있었다면 목록을 비운다(낙관적 업데이트).
- **대상 범위**: "그 계정의 그 휴지통 폴더" 한정. 계정마다 휴지통이 별도이며, 통합 메뉴의 `휴지통`(여러 계정 집계 가상 항목)에는 비우기를 노출하지 않는다.

## 12.2 확인 절차 (복구 불가 경고)

- `ConfirmDialog`를 `danger` 스타일로 띄운다.
- 문구: "휴지통에 있는 모든 메일을 영구 삭제합니다. / 이 작업은 복구할 수 없다. / 계속하시겠습니까?" (`확인`/`취소`).
- `취소` 또는 다이얼로그 닫기 시 아무 일도 하지 않는다. `확인` 시에만 서버 삭제를 호출한다.
- 상태값 `pendingEmptyTrash`(대상 `{account, folder}` 스냅샷)로 "확인 대기" 상태를 관리하고, 처리 후 항상 `null`로 되돌린다.

## 12.3 프론트 구현 위치

- [MailPage.jsx](../src/features/mail/MailPage.jsx)
  - `FolderContextMenu`: `menu.folder.type === 'trash'` 조건부로 `휴지통 비우기` 버튼 렌더 → `onEmptyTrash(menu)` 호출.
  - `openFolderMenu(event, account, folder)`: 폴더 우클릭 시 `{x, y, account, folder}`로 메뉴를 연다.
  - `onEmptyTrash = setPendingEmptyTrash`: 클릭 시 확인 대기 상태로 전환(즉시 삭제 아님).
  - `ConfirmDialog`(위험) → `onConfirm={() => emptyTrashFolder(pendingEmptyTrash)}`.
  - `emptyTrashFolder(menu)`: `DELETE /mail/accounts/:id/folders/:folderId/trash?tenantId=...` 호출 후 낙관적 카운트/목록 갱신, 실패 시 `messagesError` 표시, `finally`에서 `pendingEmptyTrash` 해제.

## 12.4 서버 구현

- 라우트: `DELETE /mail/accounts/:id/folders/:folderId/trash` ([server/routes/mail.js](../server/routes/mail.js))
  - `tenantId`/`accountId`/`folderId` 검증 → `canAccessTenant` 권한 확인 → 계정 조회.
  - `repo.purgeTrashFolder(...)` 실행. 대상 폴더를 못 찾으면(휴지통 아님/타 계정) 404.
  - 성공 후 `repo.recomputeUsage(...)`로 사용량 재계산, `{ ok: true, count, unread_count, folder }` 반환.
- 저장소: `purgeTrashFolder({ tenantId, accountId, folderId, userId })` ([server/mail/repository.js](../server/mail/repository.js))
  - **트랜잭션** 안에서 대상 폴더가 `type = 'trash'` 이고 `tenant_id`/`account_id`가 일치하는지 먼저 확인(가드).
  - `DELETE FROM mail_messages` 로 그 폴더의 메일을 **물리 삭제**하고 삭제 건수/미읽음 수를 반환.
  - 첨부(`mail_attachments`)는 `message_id ... ON DELETE CASCADE`([server/mail/schema.js](../server/mail/schema.js))로 함께 삭제된다.

## 12.5 데이터 / 멀티테넌트 정합 (5원칙 준수)

- 모든 쿼리에 `tenant_id`를 사용하고, DB 접근은 `mailRepository`(`purgeTrashFolder`)를 통해서만 수행한다(라우트·UI에 SQL 없음).
- 삭제 대상은 항상 `account_id` + `folder_id` + `type='trash'` 로 좁혀, 다른 계정/폴더 메일이 지워지지 않도록 한다.

## 12.6 검토 결론 및 주의 / 범위 밖

- **결론**: 트리거 조건(휴지통 한정), 위험 확인 다이얼로그, tenant 스코프 하드 삭제, 낙관적 UI 갱신까지 갖춰져 **동작상 완결**이다. 복구 불가 특성상 확인 절차가 필수이며 이미 반영되어 있다.
- **주의 — 스토리지 blob 잔존**: `purgeTrashFolder`는 `mail_messages`(+cascade로 `mail_attachments`) **DB 행만** 삭제한다. 메일 원본/본문/첨부의 **오브젝트 스토리지 blob**(`raw_object_key`, `body_*_object_key`, 첨부 object_key)은 지워지지 않아 **고아 객체**로 남는다. `recomputeUsage`는 DB 기준이라 표기 사용량은 줄지만 실제 스토리지는 감소하지 않는다. → 스토리지 정리(삭제된 object_key 수거)는 후속 과제.
- **주의 — 프로바이더 미반영**: 로컬 DB만 비우고 IMAP/Gmail 등 원본 서버의 휴지통은 그대로다(EXPUNGE/영구삭제 미수행). 휴지통이 재동기화되면 지운 메일이 다시 나타날 수 있으므로, 프로바이더 측 영구삭제 연동은 `providerMove`(5장) 정책과 함께 후속 검토.
- **범위 밖(향후 확장)**:
  - 통합 메뉴의 `휴지통`에서 여러 계정 휴지통을 한 번에 비우기.
  - 프로바이더 영구삭제 연동 + 스토리지 blob 회수(가비지 컬렉션).
  - "N일 지난 휴지통 자동 비우기" 정책.

# 13. 통합 메일함 — 태그 기반 스마트 폴더

## 13.1 배경 / 문제

- 통합 메일함에서 여러 계정의 메일을 계정과 무관하게 한 곳으로 정리하고 싶다는 요구가 있다(예: "A·B·C 계정에 흩어진 청구서를 통합 `청구` 폴더 하나로").
- 순진한 접근인 **계정 간 물리 이동**(B 계정 메일을 실제로 A 계정 폴더로 옮김)은 11장·`providerMove`에서 확인됐듯 **프로바이더 IMAP 복사+원본 정리**를 요구해 불안정하고, 5원칙(특히 4번 `account_id` 스코프 스토리지 키)·"프로바이더=진실" 동기화 모델과 충돌한다.
- **계정 없는 실체 컨테이너**(메일을 앱이 소유, B에서 삭제) 방식은 메일의 유일 사본이 앱DB가 되어 비가역·데이터 안전성 리스크가 크고 동기화 예외가 번진다.
- → 같은 UX를 **비파괴**로 얻기 위해, 통합 스마트 폴더를 **계정을 가로지르는 "태그(라벨)"의 저장된 뷰**로 구현한다. 메일 실체는 각자 계정에 그대로 두고, 스마트 폴더는 "그 태그가 붙은 모든 계정의 메일"을 모아 보여주는 **가상 뷰**다. (Gmail의 "폴더=라벨(비배타적)" 모델과 정합)

## 13.2 핵심 개념 / 모델

- **스마트 폴더 = (tenant, user) 스코프의 태그 이름**. 특정 `account_id`·`folder_id`에 묶이지 않는다.
- 메일 1건은 원래의 `account_id`/`folder_id`(프로바이더 미러)를 그대로 유지하면서, **0개 이상의 스마트 태그**를 추가로 가질 수 있다(다대다).
- 통합 메일함의 스마트 폴더 목록 = 해당 tenant/user가 만든 태그들의 집합.
- 스마트 폴더 "AA" 클릭 = `태그 AA가 붙은 모든 계정의 메일` 목록(계정·폴더 무관).
- **비파괴 원칙**: 태그 부여/해제는 로컬 메타데이터만 바꾼다. 프로바이더 메일함·원본 blob·다른 스마트 폴더 소속을 건드리지 않는다.

## 13.2.1 통합 사이드바 구성 (시각 구분 — 확정)

통합 사이드바는 **두 구역**으로 명확히 나눈다.

- **① 시스템 통합 항목(유지)** — `모든 편지함`·`받은 편지함`·`별표됨`·`임시 보관함`·`검색`·`보낸 메일`·`휴지통`.
  - 이들은 **태그가 아니라 type 집계/시스템 뷰**이므로 스마트 폴더로 대치하지 않고 **기존 그대로** 둔다(아이콘·동작 유지).
- **② 스마트 폴더 구역(신규, 이름 폴더 대치)** — 기존 통합 메뉴의 **"사용자 지정 이름 집계 폴더"를 제거**하고, 같은 이름의 **스마트 폴더로 대치**한다.
  - 별도 섹션 헤더(예: "스마트 폴더")로 ①과 시각적으로 분리한다.
  - 각 스마트 폴더는 **태그/라벨 아이콘 + 색 점**으로 표기해, 폴더 아이콘을 쓰는 ① 시스템 항목과 한눈에 구분되게 한다.
  - 이름 충돌(계정 폴더 AA vs 스마트 폴더 AA)은 이 구역 분리로 해소한다.

## 13.3 데이터 모델 (신규 테이블)

5원칙 준수. DB 접근은 전부 `mailRepository`를 통한다(라우트/UI에 SQL 없음).

- `mail_smart_folders`
  - `id`(uuid PK), `tenant_id`(NOT NULL), `user_id`(NOT NULL), `name`(태그 표시명), `color`(선택), `created_at`.
  - UNIQUE(`tenant_id`, `user_id`, `name`) — 같은 사용자 공간에서 이름 중복 방지.
- `mail_message_tags` (메일 ↔ 스마트 폴더 다대다)
  - `tenant_id`(NOT NULL), `smart_folder_id`(FK), `message_id`(FK, `ON DELETE CASCADE`), `user_id`(NOT NULL), `created_at`.
  - PK/UNIQUE(`tenant_id`, `smart_folder_id`, `message_id`).
  - 인덱스: (`tenant_id`, `smart_folder_id`)로 폴더별 조회, (`tenant_id`, `message_id`)로 메일 상세의 소속 태그 조회.
- 메시지가 삭제/휴지통 이동될 때 태그 행 처리: `mail_messages` 삭제 시 CASCADE로 태그도 제거. 휴지통 이동은 `folder_id`만 바뀌므로 태그는 유지(휴지통에서도 스마트 폴더 소속은 남되, 13.7의 표시 규칙으로 뷰에서 제외 판단).

## 13.4 이동 의미 — 통합 스마트 폴더로 드롭 (11장과의 관계)

- 11.5.1의 통합 메뉴 드롭 경로를 확장한다. **드롭 대상이 스마트 폴더면 "이동"이 아니라 "태그 부여"로 해석**한다.
  - `handleUnifiedDrop`/`moveMessagesToUnified` 옆에, 스마트 폴더용 분기 `tagMessagesToSmartFolder(ids, smartFolder)`를 둔다.
  - 동작: 선택된 각 메일에 `smart_folder_id` 태그를 부여(중복은 무시). **원본 계정/폴더·프로바이더는 그대로.**
- **계정 간 물리 이동 경로(`providerMove`)를 아예 타지 않는다** → 11장에서 진단한 cross-account 실패를 원천 회피.
- 낙관적 UI: 태그 부여 성공 시, 현재 보는 스마트 폴더 뷰라면 목록에 즉시 반영. 원 계정 폴더 뷰에서는 메일이 사라지지 않는다(비파괴이므로 정상).
- **드롭 출처별 의미 분기**:
  - **비-스마트 뷰(받은편지함/폴더/통합) → 스마트 폴더**: 태그 부여 + 각 계정 내 아카이브(13.5).
  - **스마트 폴더 뷰 → 다른 스마트 폴더**: **"이동"으로 처리** — 대상에 태그 부여 + **원본(현재 보던) 스마트 폴더에서 태그 해제**. 계정 폴더/프로바이더는 건드리지 않음(아카이브 없음). 같은 스마트 폴더로 드롭은 무동작.
  - 이미 대상에 태그돼 있으면(멱등) "이미 담겨 있습니다"로 안내(오해 방지).
- **드래그 효과 주의**: 카드 `onDragStart`의 `effectAllowed`는 `copyMove`여야 한다. 폴더=이동(`move`)과 스마트=태그(`copy`)의 `dropEffect`가 모두 허용되어야 브라우저가 `onDrop`을 발생시킨다(불일치 시 드롭이 조용히 막힘).

## 13.5 원본 처리 — 태그 부여 + 각 계정 내 아카이브 (1차 포함, 확정)

- 스마트 폴더로 드롭 시 **두 동작을 함께 수행**한다(1차 범위에 포함).
  1. **태그 부여**: 각 메일에 `smart_folder_id` 태그 부여(13.4).
  2. **각 계정 내 아카이브**: 각 메일을 **자기 계정 안의** Archive/보관 폴더로 이동해 받은편지함 등 원 위치에서 치운다.
- 아카이브 이동 구현: 같은 계정 이동이므로 기존 안전 경로 `moveMessage`→`moveMessageToFolder`를 재사용한다(프로바이더는 같은 계정 내 라벨/메일함 이동이라 안정적). **계정 간 물리 이동(`providerMove`)은 타지 않는다.**
  - 계정마다 Archive 대상 폴더 해석은 `resolveUnifiedTargetFolder`류 로직 재사용(계정 내 `type='archive'` 또는 이름 매칭). **대상 폴더가 없는 계정은 이동을 건너뛰고 태그만 유지**(부분 적용 허용).
- **핵심 안전장치**: 프로바이더에서의 **하드 삭제는 하지 않는다**(비가역 리스크 회피). "같은 계정 내 아카이브 이동 + 스마트 태그"까지만.
- **UX 토글(선택)**: 드롭 시 기본은 "태그+아카이브"이되, 수식어(예: `Alt`/설정)로 "태그만(원 위치 유지)"도 고를 수 있게 둔다(1차엔 기본 동작만 필수).
- 되돌리기: 아카이브는 이동일 뿐이라, 태그 해제 + 원 폴더로 재이동으로 복구 가능(하드 삭제가 아니므로 안전).

## 13.6 조건 기반 자동 태그 — MailClaw(9장) 연계 (1차 포함, 확정)

- MailClaw 규칙(9.1 조건: 발신자/도메인/제목 등)에 **신규 액션 "스마트 폴더 태그 부여"**를 추가한다. 조건 매칭 시 해당 스마트 폴더 태그를 **자동 부여**한다.
- 실행 위치: 9.2.1 자동화 실행 순서에 통합. 신규 수신/동기화된 메일에 규칙을 평가 → 매칭 시 내부적으로 태그 부여 로직(13.8의 태그 부여 API와 동일한 리포지토리 함수)을 호출한다. UI 드롭과 **같은 경로를 공유**한다.
- **아카이브 동반(선택)**: 규칙에 "태그 + 각 계정 내 아카이브"까지 지정 가능(13.5와 동일 안전 규칙 — 하드 삭제 없음).
- **멱등성**: 이미 태그된 메일을 재평가해도 중복 태그는 무시되어 무해하다. 규칙 재적용/재동기화에 안전.
- **대상 스마트 폴더 지정**: 규칙 편집 UI(9.1.2)에서 대상 스마트 폴더를 선택(없으면 즉석 생성)하도록 확장한다. 규칙은 `smart_folder_id`를 참조로 저장한다(이름 변경에 견고).
- 범위: 자동 태그는 **로컬 태그 부여**만 하며 프로바이더 라벨을 만들지 않는다(13.9 동기화 정합 유지).

## 13.7 조회 / 표시 규칙

- 스마트 폴더 목록(카운트): `mail_message_tags` ⋈ `mail_messages`를 tenant/user 스코프로 집계. 미읽음 수도 동일 집계.
- 스마트 폴더 열람: `smart_folder_id`로 태그된 메일을 여러 계정에 걸쳐 조회(정렬은 기존 목록과 동일, 수신일 기준).
- **휴지통/스팸 제외**: 태그는 유지되더라도, 스마트 폴더 뷰에서는 `type IN ('trash','spam')` 폴더에 있는 메일은 숨긴다(원 계정에서 버린 메일이 스마트 폴더에 유령처럼 남지 않도록). 원 메일이 완전 삭제되면 CASCADE로 태그도 사라진다.
- 메일 상세: 현재 이 메일이 속한 스마트 폴더(태그) 배지를 표시하고, 거기서 태그 추가/제거 가능.

## 13.8 API (mailRepository 경유, 라우트는 얇게)

- `GET /mail/smart-folders` — tenant/user의 스마트 폴더 목록 + 카운트.
- `POST /mail/smart-folders` `{ name, color? }` — 생성(이름 UNIQUE 충돌 처리).
- `PATCH /mail/smart-folders/:id` `{ name?, color? }` / `DELETE /mail/smart-folders/:id` — 이름/색 변경, 삭제(삭제 시 태그 행 CASCADE).
- `POST /mail/smart-folders/:id/messages` `{ messageIds[] }` — 태그 부여(드롭/컨텍스트 메뉴 공용, 다중/단건 동일).
- `DELETE /mail/smart-folders/:id/messages` `{ messageIds[] }` — 태그 해제.
- `GET /mail/smart-folders/:id/messages?tenantId=...` — 폴더 열람(여러 계정 집계).
- 모든 라우트는 `canAccessTenant`로 tenant 접근 검증, 실제 로직은 `mailRepository`.

## 13.9 동기화 정합 (중요)

- 스마트 태그는 **로컬 전용 메타데이터**다. 동기화는 여전히 프로바이더=진실로 `account_id`/`folder_id`만 갱신하고, **`mail_message_tags`는 건드리지 않는다**.
- 프로바이더에서 메일이 사라져 로컬 행이 삭제되면 CASCADE로 태그도 제거 → 유령 방지.
- 즉 "계정 없는 소유" 방식과 달리 **동기화 로직에 특별 예외가 필요 없다**(태그는 메일에 부수되는 라벨일 뿐).

## 13.10 5원칙 준수

1. 두 신규 테이블 모두 `tenant_id` 보유. 2. 접근은 `mailRepository`만. 3. 라우트/UI에 SQL 없음. 4. 태그는 blob을 만들지 않아 `object_key` 스코프 규칙과 무관(스토리지 변화 없음). 5. tenant 라우팅은 기존 `connectionManager`가 그대로 담당(shared_db/dedicated_db 공통 스키마).

## 13.11 기존 "통합 메뉴" 대치 / 마이그레이션 (확정)

- **결정**: 기존 통합 메뉴의 **"사용자 지정 이름 집계 폴더"(11.5.1의 `key: name:<이름>`)는 전면 제거**하고, **같은 이름의 스마트 폴더로 대치**한다. 시스템 통합 항목(13.2.1 ①의 7개)은 **그대로 유지**한다.
- 11.5.1의 이름 폴더 드롭(`moveMessagesToUnified`의 `folderName` 분기)은 **스마트 폴더 태그 부여(13.4)로 대체·폐기**한다. 시스템 타입 항목(`받은 편지함`·`휴지통`) 드롭 이동은 유지.
- **주의 — 계정별 실제 폴더는 손대지 않는다**: 하단의 계정별 폴더 목록(프로바이더 미러)은 그대로 둔다. 이번 대치는 **통합(가상) 표현**만 이름-집계 → 스마트 폴더로 바꾸는 것이다.
- **마이그레이션(시드, 1회)**: 도입 시 각 tenant/user에 대해
  1. 현재 계정들의 커스텀 폴더 **이름 집합**을 수집한다.
  2. 각 이름마다 **동명 스마트 폴더를 생성**한다(`mail_smart_folders`).
  3. 그 이름 폴더에 들어 있던 메일에 **해당 스마트 폴더 태그를 일괄 부여**한다(`mail_message_tags` 시드).
  → 기존 "이름 통합 폴더"의 내용이 스마트 폴더로 자연 이전된다. 멱등하게 재실행 가능(중복 태그 무시).

| API | 스마트 폴더 CRUD + 태그 부여/해제 + 열람(13.8) | 1차 |

## 13.13 검토 결론 및 범위 밖

- **결론**: 태그 기반 스마트 폴더는 계정 무관 정리 UX를 **비파괴·동기화 안전·계정 간 물리 이동 회피**로 달성한다. 이름 통합 폴더를 스마트 폴더로 대치하고, 드롭은 태그+각 계정 아카이브, 자동 태그는 MailClaw와 연계한다. 신규 테이블 2개 + 얇은 API/리포지토리 + 사이드바 구역 분리로 국한되고, 기존 이동·동기화·5원칙을 깨지 않는다.
- **주의**: 스마트 폴더는 "가상 뷰"이므로 프로바이더(Gmail/Apple)에는 그 라벨이 생기지 않는다(앱 내에서만 유효). 아카이브 이동만 프로바이더에 반영되고, 태그 자체는 앱 내 메타데이터다.
- **범위 밖(향후 확장)**:
  - 프로바이더 라벨(특히 Gmail 라벨)과 스마트 폴더의 **양방향** 매핑/동기화.
  - 스마트 폴더 공유(팀 단위) 및 권한.
  - 계정별 Archive 폴더가 없을 때 자동 생성/선택 UI(1차는 없으면 태그만 유지).

# 14. 중요 메일 표시(별표)

## 14.1 배경 / 목적

- 메일 목록에서 특정 메일을 **"중요"로 표시**해 눈에 띄게 하고, 카드에 **별(★) 마크**로 즉시 구분하고 싶다.
- 컨텍스트(우클릭) 메뉴에서 **토글**로 켜고/끄며, 상단 통합 메뉴의 **`별표됨`** 뷰와 자연스럽게 연결한다.

## 14.2 데이터 모델 — 기존 `is_starred` 재사용 (신규 컬럼 없음)

- `mail_messages.is_starred BOOLEAN`(스키마에 이미 존재)을 **"중요" 상태**로 그대로 사용한다. 신규 컬럼/테이블 없음.
- 상단 통합 메뉴 **`별표됨`**(`unifiedKey='starred'`)은 이미 `mm.is_starred = true`로 필터한다(11장). 따라서 "중요 표시"한 메일은 **자동으로 `별표됨` 뷰에 모인다** — 별도 배선 불필요.
- **로컬 상태**로 취급한다: 동기화는 프로바이더=진실로 다른 필드를 갱신하되 `is_starred`는 앱 내 표시로 유지한다(프로바이더 별표/중요와의 양방향 동기화는 범위 밖 14.9). 스마트 폴더 태그(13장)와 동일한 "비파괴 로컬 메타데이터" 성격.

## 14.3 컨텍스트 메뉴 — "중요 메일로 표시" 토글

- `MailMessageContextMenu`에서 **`안읽은 메일로` 항목 바로 위**에 새 항목을 추가한다.
- **라벨 토글**: 우클릭 대상 메일의 상태로 라벨을 결정한다.
  - `is_starred = false` → **"중요 메일로 표시"** (선택 시 켜기)
  - `is_starred = true` → **"중요 메일 표시 해제"** (선택 시 끄기)
- 아이콘: `star`(별) 아이콘을 사용하고, 켜진 항목이면 채워진 별로 시각 구분(선택).
- **다중 선택 처리**(11.3/openMessageMenu 규칙과 동일): 선택 묶음이 있으면 `targetIds` 전체에 적용한다. 라벨/동작 방향은 **우클릭한 메일의 상태 기준**으로 정한다.
  - 우클릭 메일이 미표시면 → "중요 메일로 표시": 선택 전체를 `is_starred=true`로.
  - 우클릭 메일이 표시됨이면 → "중요 메일 표시 해제": 선택 전체를 `is_starred=false`로.

## 14.4 카드의 별(★) 마크

- 메일 목록 카드(`MailMessageList`의 각 `<button>`)에서 **왼쪽 아래**(좌측 아이콘 열의 하단, 체크/미읽음 점·발신자 파비콘이 있는 열)에 **별 마크**를 표시한다.
- 표시 조건: `message.is_starred === true`.
- 스타일: 채워진 노란/황금색 별(예: `text-amber-400`). 미표시 메일에는 아무것도 그리지 않는다(공간만 예약해 레이아웃 흔들림 방지).
- 선택 체크(✓)·미읽음 점과 시각적으로 겹치지 않게 배치한다(예: 파비콘 하단 모서리 뱃지 형태).

## 14.5 API — 별표 토글 액션

- 기존 일괄 처리 라우트 **`PATCH /mail/messages/bulk`**에 액션을 추가한다: `action: 'star'` / `action: 'unstar'`.
  - 요청: `{ tenantId, action: 'star'|'unstar', messageIds: [...] }`.
  - 처리: `mailRepository`에 `setMessagesStarred({ tenantId, userId, messageIds, starred })`를 추가해 `UPDATE mail_messages SET is_starred=$starred ... WHERE tenant_id AND user_id AND id = ANY(messageIds)`. tenant/user 스코프 필수(5원칙).
  - 응답: 기존 bulk와 동일하게 `results`(건별 ok) 반환 → 프론트는 성공 건만 반영.
- 단건도 동일 라우트로 처리(다중/단건 통일). 별도 단건 라우트는 만들지 않는다.

## 14.6 상태 갱신 / 낙관적 UI

- 성공 시 프론트에서 **낙관적 갱신**(`markMessageUnread` 패턴과 동일):
  - `setMessages`로 해당 메일들의 `is_starred`를 토글 → 카드 별 마크 즉시 반영.
  - `setSelectedMessage`도 열려 있으면 동일 반영.
  - **`별표됨` 통합 카운트 갱신**: 표시 +N / 해제 −N. 낙관적 반영 후 `reloadMailAccounts`(13장에서 추가한 뷰 진입 리로드로도 정정됨)로 보정 가능.
- 현재 뷰가 **`별표됨`**인데 "해제"하면 그 메일은 뷰 조건에서 벗어나므로 목록에서 제거한다(스마트 폴더 아카이브 목록 갱신과 동일 패턴).

## 14.7 5원칙 준수

1. `is_starred`는 `mail_messages`의 컬럼 → tenant_id 스코프 자동 충족. 2. 접근은 `mailRepository`(`setMessagesStarred`)만. 3. 라우트/UI에 SQL 없음. 4. blob 무관(스토리지 변화 없음). 5. tenant 라우팅은 `connectionManager` 그대로.

## 14.8 검토 결론 및 범위 밖

- **결론**: 신규 스키마 없이 기존 `is_starred` + `별표됨` 뷰를 재사용한다. 컨텍스트 메뉴 토글 1개 + 카드 별 마크 + bulk 액션(`star`/`unstar`) + 낙관적 갱신으로 국한된다.
- **범위 밖(향후 확장)**:
  - 프로바이더(Gmail 별표/중요, IMAP `\Flagged`)와의 양방향 동기화.
  - 카드/목록에서 별을 **직접 클릭**해 토글(컨텍스트 메뉴 외 인라인 토글).
  - 중요 메일 정렬 우선순위·필터 프리셋.

# 15. 통합 휴지통 비우기 (여러 계정 한 번에)

## 15.1 배경 / 목적

- 12장의 `휴지통 비우기`는 **"그 계정의 그 휴지통 폴더" 한정**이며, 통합 메뉴의 `휴지통`(여러 계정 집계 가상 항목)에는 비우기를 노출하지 않았다(12.1). 12.6에서 "통합 메뉴의 휴지통에서 여러 계정 휴지통을 한 번에 비우기"를 **범위 밖(향후)**으로 미뤄 두었다.
- 본 장은 이를 **정식 채택**한다: 상단 통합 메뉴의 `휴지통`을 우클릭하면 **`휴지통 비우기`** 항목이 나타나고, 실행하면 **현재 tenant의 모든 계정 휴지통에 있는 메일을 한 번에 영구 삭제**한다.

## 15.2 동작 개요

- 사이드바 **통합 메뉴의 `휴지통`**(`unifiedKey='trash'`, `type='trash'`)을 우클릭하면 통합 폴더 컨텍스트 메뉴(`UnifiedFolderContextMenu`)에 **`휴지통 비우기`**(빨강, 위험) 항목이 **추가로** 나타난다. `모든 편지함`·`받은 편지함` 등 다른 통합 항목에는 나타나지 않는다.
- 누르면 즉시 삭제하지 않고 **확인 다이얼로그**를 띄운다. `확인` 시에만 실행한다(12.2와 동일한 복구 불가 경고).
- 실행 시 **현재 tenant 소속 각 계정의 `type='trash'` 폴더를 각각 비운다**(계정별 반복). 성공 후 각 계정 휴지통 카운트와 통합 `휴지통` 카운트를 0으로 갱신하고, 통합 휴지통을 보고 있었다면 목록을 비운다(낙관적 업데이트).

## 15.3 대상 범위

- **현재 tenant(`currentTenantId`)에 속한 모든 계정**의 휴지통 폴더 전부. 계정마다 휴지통이 별도이므로 계정별로 비운다.
- 특정 계정에 휴지통 폴더가 없으면 그 계정은 건너뛴다(부분 처리 허용).

## 15.4 프론트 구현 위치 (기존 자산 재사용)

- [MailPage.jsx](../src/features/mail/MailPage.jsx)
  - `UnifiedFolderContextMenu`: 대상 통합 항목이 `type === 'trash'`(또는 `key === 'trash'`)일 때만 `휴지통 비우기` 버튼 렌더 → `onEmptyUnifiedTrash(item)` 호출.
  - `openUnifiedFolderMenu(event, item)`: 통합 항목 우클릭 시 메뉴를 연다(기존).
  - 확인 대기 상태: 기존 `pendingEmptyTrash`를 확장하거나(예: `{ unified: true }` 스냅샷) 통합 전용 상태를 둔다. `ConfirmDialog`(danger)는 그대로 재사용.
  - `emptyUnifiedTrash()`: `currentTenantId` 계정들을 순회하며 각 계정의 휴지통 폴더에 대해 **기존 라우트** `DELETE /mail/accounts/:id/folders/:folderId/trash?tenantId=...`를 반복 호출한다. 각 성공분을 낙관적으로 카운트/목록에 반영한다.

## 15.5 서버 구현 (신규 로직 불필요)

- **서버 변경 없이** 12.4의 계정별 라우트(`DELETE .../folders/:folderId/trash` → `repo.purgeTrashFolder`)를 **계정 수만큼 재사용**한다. tenant/account/folder 스코프 가드가 그대로 적용된다.
- (선택) 후속 최적화로 "한 tenant의 모든 휴지통을 한 방에 비우는" 통합 라우트를 추가할 수 있으나 1차 범위 밖. 1차는 프론트에서 계정별 반복 호출로 충분하다.

## 15.6 확인 문구 (복구 불가)

- 통합이므로 대상이 여러 계정임을 명시한다. 예: "모든 계정의 휴지통에 있는 메일을 영구 삭제합니다. / 이 작업은 복구할 수 없습니다. / 계속하시겠습니까?" (`확인`/`취소`).
- (선택) 대상 계정 수·총 건수를 문구에 노출해 실수 방지.

## 15.7 5원칙 준수

- 계정별 `purgeTrashFolder`가 `tenant_id` + `account_id` + `folder_id` + `type='trash'`로 좁혀 실행되므로, 다른 계정/폴더 메일이 지워지지 않는다. DB 접근은 `mailRepository`만, 라우트/UI에 SQL 없음.

## 15.8 개정 사항 · 주의 · 범위 밖

- **개정**: 12.1의 "통합 메뉴의 `휴지통`에는 비우기를 노출하지 않는다"와 12.6 범위 밖의 "통합 휴지통 일괄 비우기" 항목은 **본 장으로 개정**되어, 통합 `휴지통`에 한해 노출·동작으로 전환된다.
- **주의(12.6 계승)**: (a) 스토리지 blob 잔존 — DB 행만 삭제되고 오브젝트 스토리지 원본/첨부 blob은 남는다(고아 객체, 후속 GC 과제). (b) 프로바이더 미반영 — 로컬 DB만 비우고 IMAP/Gmail 원본 휴지통은 그대로라 재동기화 시 다시 나타날 수 있다.
- **범위 밖(향후 확장)**: 서버측 단일 통합 비우기 라우트(현재는 계정별 반복 호출), 프로바이더 EXPUNGE/영구삭제 연동, 스토리지 blob 회수.


# 16. 폴더 이름 변경 (프로바이더 반영)

## 16.1 배경 / 목적

계정별 관리 메뉴의 폴더는 **컨텍스트 메뉴에서 색상만** 바꿀 수 있고 이름 변경 수단이 없다(`PATCH /accounts/:id/folders/:folderId`는 `colorKey`만 처리). 폴더는 두 종류다.

- **로컬 전용 폴더**(`is_local = true`) — 앱에서 만든 폴더. 프로바이더에 존재하지 않음.
- **프로바이더 폴더**(`is_local = false`) — Gmail 라벨 / IMAP 메일함을 동기화한 것. 화면에 보이는 대부분이 여기 해당.

로컬 표시명만 바꾸면 다음 폴더 동기화 때 `upsertFolders`의 `ON CONFLICT ... DO UPDATE SET name = EXCLUDED.name`가 **프로바이더 원본 이름으로 되돌려버린다**(`server/mail/repository.js`). 따라서 "이름 변경"을 사용자가 기대하는 대로 지속시키려면 **프로바이더에 실제로 이름을 바꿔야** 한다. 본 장은 그 정책과 구현을 확정한다.

## 16.2 정책 — "프로바이더 반영" 원칙 (확정)

폴더 쓰기 작업(이름 변경·삭제)에 대해 다음 정책을 채택한다.

- **로컬 전용 폴더**: 로컬 DB만 변경한다(프로바이더에 대상이 없으므로 당연).
- **프로바이더 폴더**: **프로바이더를 진실로 삼아 먼저 프로바이더에서 변경하고, 성공 시 로컬 DB를 그 결과로 맞춘다.** 로컬만 바꾸는 "표시명 오버라이드"는 채택하지 않는다(동기화가 되돌리므로 사용자 신뢰를 깬다).
- **실패 시**: 프로바이더 변경이 실패하면 로컬도 바꾸지 않는다(원자성). 부분 성공 상태를 남기지 않는다.

> 삭제 전파와의 정합: 현재 `deleteFolder`는 로컬 DB만 지우고 프로바이더에는 전파하지 않아, 재동기화 시 프로바이더 폴더가 되살아나는 불일치가 있다(로컬 전용 폴더에는 문제없음). 본 장의 "프로바이더=진실" 원칙을 삭제에도 적용하는 것을 **동일 프로젝트 범위**로 본다(16.8 참조). 다만 삭제는 "메일 손실" 위험이 있어 이름 변경보다 신중한 확인 UX가 필요하므로 **후속 단계**로 분리한다.

## 16.3 대상 범위 / 가드 (확정)

이름 변경을 **허용하는 폴더**:

- 로컬 전용 폴더(`is_local = true`).
- 프로바이더 사용자 폴더(`type = 'custom'` 이고 시스템 폴더가 아님).

**거부하는 폴더**(400/409 반환):

- 시스템 폴더: `type ∈ {inbox, sent, drafts, trash, archive, spam}`.
- Gmail 시스템 라벨: 라벨 `type = 'system'`(INBOX, SENT, DRAFT, TRASH, SPAM, CATEGORY_* 등). `discoverGmailFolders`가 `type === 'user'`만 동기화하므로 정상 동기화된 폴더는 자동으로 사용자 라벨이지만, 방어적으로 서버에서 재확인한다.
- IMAP 특수용도 메일함(`\Inbox`, `\Sent`, `\Drafts`, `\Trash`, `\Junk`, `\Archive`, `\All`) 및 `INBOX`.

**이름 유효성**:

- 트림 후 빈 문자열 금지, 기존 형제 폴더와 대소문자 무시 중복 금지.
- IMAP 구분자(`/` 또는 서버 delimiter)·개행·제어문자 금지. Gmail 라벨은 `/`가 계층 구분이므로 이름 자체에 `/` 금지(계층 이동은 범위 밖, 16.8).
- 길이 상한(예: 225자, 서버 정책에 맞춰) 검증.

## 16.4 데이터 모델

**신규 컬럼 없음.** 기존 `mail_folders.name`(및 IMAP의 경우 `provider_folder_id`)만 갱신한다.

- **Gmail**: 라벨 ID(`provider_folder_id`)는 이름과 독립적으로 유지된다. 이름만 바뀌므로 `provider_folder_id`는 **불변**, `name`만 UPDATE. 메시지-폴더 매핑도 그대로.
- **IMAP**: 메일함 경로가 곧 식별자다. RENAME 시 `provider_folder_id`(=경로)가 **바뀐다**. 따라서 `provider_folder_id`와 `name`을 **함께** UPDATE해야 하며, `UNIQUE (account_id, provider_folder_id)` 제약과 충돌하지 않도록 새 경로가 유일해야 한다. 하위 메일함이 있으면 서버가 경로 프리픽스를 연쇄 변경하지만, 1차에서는 **하위 폴더가 없는 폴더만** 허용(16.8)해 로컬 재매핑을 단순화한다.

## 16.5 API — 이름 변경 액션

기존 `PATCH /accounts/:id/folders/:folderId`를 확장한다(신규 라우트 없이 `name` 필드 수용).

```
PATCH /api/mail/accounts/:id/folders/:folderId?tenantId=...
body: { name?: string, colorKey?: string, tenantId? }
```

- `colorKey`만 오면 기존과 동일(색상만 변경, 프로바이더 무관).
- `name`이 오면 이름 변경 경로를 탄다. `name`과 `colorKey`가 함께 오면 이름 변경 성공 후 색상도 갱신.
- 라우트는 얇게: 권한 확인(`canAccessTenant`) 후 로직은 `mailRepository` + 신규 프로바이더 모듈에 위임(SQL/프로바이더 호출을 라우트에 두지 않음 — 5원칙 2·3).

**처리 순서(프로바이더 폴더)**:

1. `repo.getFolderById`로 폴더 로드 → 가드 검증(16.3). 로컬 전용이면 곧장 5로.
2. `renameFolderOnProvider({ tenantId, account, folder, newName })` 호출(신규 모듈, 16.6).
3. 프로바이더 성공 결과(Gmail: 그대로 / IMAP: 새 경로)를 받는다.
4. 실패 시 예외 → 로컬 미변경, 사용자 메시지 반환.
5. `repo.renameFolder({ tenantId, accountId, folderId, name, providerFolderId? })`로 로컬 DB를 결과에 맞춰 UPDATE(트랜잭션).

## 16.6 서버 구현 — `providerRename` 모듈 (신규)

`providerMove.js`와 동일한 구조/컨벤션으로 `server/mail/providerRename.js`를 신설한다(클라이언트 빌드·토큰 갱신 헬퍼 재사용/미러링).

```
renameFolderOnProvider({ tenantId, account, folder, newName })
  ├─ account.provider === 'gmail'      → renameGmailLabel(...)
  ├─ isImapProvider(account.provider)  → renameImapMailbox(...)
  └─ else                              → { skipped, reason }
```

- **Gmail** — `renameGmailLabel`:
  - `gmailOAuth.js`에 신규 헬퍼 `gmailPatchLabel(accessToken, labelId, { name })` 추가.
    - `PATCH https://gmail.googleapis.com/gmail/v1/users/me/labels/{id}` body `{ name }` (`gmailModifyMessage`와 동일한 `fetchJson` + `authHeader` 패턴).
  - 토큰은 `ensureGmailAccessToken`(providerMove와 동일 로직) 사용. 권한 부족(403 insufficient scope) 시 `gmail.modify`(라벨 수정 포함) 재승인 안내 메시지로 변환.
  - 반환: `{ provider: 'gmail', providerFolderId: folder.provider_folder_id, name: newName }`(ID 불변).
- **IMAP** — `renameImapMailbox`:
  - `buildImapClient` + `client.connect()`(providerMove 미러). 계정 암호는 `decryptSecret(account.password_encrypted)`.
  - `resolveMailboxPath`로 현재 경로 해석 → 대상 새 경로 계산(같은 부모 아래 새 leaf 이름; 서버 delimiter는 `client.list()`/namespace로 확인).
  - `await client.mailboxRename(currentPath, newPath)` 호출(imapflow 제공). 성공 시 `info.newPath` 사용.
  - 반환: `{ provider: 'imap', providerFolderId: newPath, name: newName }`.
  - `logout()`/`close()` 정리는 providerMove와 동일 패턴.

## 16.7 리포지토리 / 프론트

- **repo(신규)**: `renameFolder({ tenantId, accountId, folderId, name, providerFolderId })` — `UPDATE mail_folders SET name=$name, provider_folder_id=COALESCE($providerFolderId, provider_folder_id), updated_at=NOW() WHERE tenant_id AND account_id AND id AND type='custom'`. tenant/account 스코프 필수(5원칙 1). IMAP처럼 `provider_folder_id`가 바뀌면 해당 폴더의 메시지 `provider_message_id`(`imap:<folder>:<uid>` 형식)도 경로 프리픽스를 갱신할지 검토 — 1차는 폴더의 `folder_id` 매핑이 유지되므로 조회에는 지장 없고, `provider_message_id`의 경로 부분은 다음 동기화/이동 시 자연 정정되게 둔다(주의로 명시, 16.9).
- **프론트(`MailPage.jsx`)**:
  - 폴더 컨텍스트 메뉴에 **"이름 변경"** 항목 추가(색상 설정 위, 삭제 근처). 시스템 폴더에서는 숨김/비활성.
  - 클릭 시 인라인 편집 또는 프롬프트로 새 이름 입력 → `apiFetch(PATCH /mail/accounts/:id/folders/:folderId, { name })`.
  - 성공 시 `accounts` 상태의 해당 폴더 `name`(+ 필요 시 `provider_folder_id`)을 낙관적 갱신. 실패 시 에러 토스트 후 롤백.

## 16.8 1차 구현 범위 / 범위 밖

**1차 포함(확정)**:

- 로컬 전용 폴더 이름 변경(DB만).
- Gmail 사용자 라벨 이름 변경(라벨 patch, ID 불변).
- IMAP **하위 폴더 없는** 사용자 메일함 이름 변경(RENAME + `provider_folder_id` 재매핑).
- 가드(시스템 폴더/특수용도/중복/유효성)와 원자성(프로바이더 먼저, 실패 시 로컬 미변경).

**범위 밖(후속)**:

- 하위 폴더가 있는 IMAP 메일함 이름 변경(경로 프리픽스 연쇄 재매핑, 자식 `provider_message_id` 일괄 정정).
- 폴더 계층 이동(부모 변경), Gmail 라벨의 `/` 계층 재배치.
- **폴더 삭제의 프로바이더 전파**(16.2 각주) — "프로바이더=진실"을 삭제에도 적용. 메일 손실 위험으로 별도 확인 UX 필요, 본 프로젝트의 후속 단계.
- 프로바이더 → 로컬 방향의 이름 변경 실시간 감지(현재는 주기 동기화가 반영).

## 16.9 주의 · 정합

- **IMAP `provider_message_id` 프리픽스**: 폴더 경로가 바뀌면 기존 메시지의 `imap:<oldPath>:<uid>` 값이 즉시 정정되지 않는다. `folder_id` 기반 조회는 정상이며, 이동/재동기화 시 정정된다. 이름 변경 직후 해당 폴더에서의 프로바이더 이동이 필요한 경우 `provider_message_id` 갱신 여부를 재확인한다.
- **동기화 경합**: 이름 변경과 폴더/메시지 동기화가 겹치면 `upsertFolders`의 `ON CONFLICT`가 새 이름을 유지하므로(프로바이더가 이미 새 이름) 문제없다. 단 프로바이더 변경 직후~다음 동기화 사이 캐시된 목록은 이전 이름을 보일 수 있어 낙관적 갱신으로 보완한다.
- **권한(Gmail)**: 라벨 patch는 `gmail.modify` 스코프가 필요하다. 이동 기능이 이미 같은 스코프를 요구하므로 추가 스코프 없이 동작하는 것이 일반적이나, 미승인 계정은 재연결 안내로 처리한다.

## 16.10 5원칙 준수

1. `mail_folders`는 `tenant_id` 보유, `renameFolder`는 tenant/account 스코프로 좁혀 UPDATE. 2. 프로바이더 호출·DB 접근은 `providerRename`/`mailRepository`만 담당, 라우트는 권한 확인·위임만. 3. 라우트/UI에 SQL·프로바이더 호출 없음. 4. 폴더 이름 변경은 blob을 만들지 않아 `object_key` 스코프 규칙과 무관(스토리지 변화 없음). 5. tenant 라우팅은 기존 `connectionManager`가 담당(shared_db/dedicated_db 공통).

## 16.11 폴더 삭제의 프로바이더 전파 (설계 — 후속 단계)

### 16.11.1 배경 / 현재 동작

현재 [deleteFolder](../server/mail/repository.js)는 **로컬 DB만** 지운다: `DELETE FROM mail_folders ... WHERE type='custom'`. 스키마상 `mail_messages.folder_id`는 `ON DELETE SET NULL`이라, 폴더를 지우면 그 폴더의 메일은 **삭제되지 않고 `folder_id`가 NULL로 고아(orphan)** 가 된다. 또한 프로바이더에는 전파하지 않으므로 **다음 동기화 때 프로바이더 폴더가 되살아난다**(로컬 전용 폴더는 프로바이더에 없어 무관).

즉 두 가지 결함: (a) 프로바이더 폴더가 재동기화로 부활, (b) 메일이 고아로 남아 어느 목록에도 안 잡힘.

### 16.11.2 프로바이더별 삭제 의미 — 반드시 구분

폴더 삭제는 프로바이더마다 **메일에 미치는 영향이 완전히 다르다.** 이 차이가 확인 UX와 로컬 처리를 좌우한다.

- **Gmail(라벨)**: 라벨 삭제(`labels.delete`)는 **라벨만 제거**한다. 메일은 삭제되지 않고 "전체보관함(All Mail)"에 그대로 남는다(다른 라벨/받은편지함 소속은 유지). → **비파괴적**.
- **IMAP(메일함)**: 메일함 삭제(`mailboxDelete` = IMAP `DELETE`)는 **메일함과 그 안의 메일을 서버에서 함께 삭제**한다. → **파괴적(메일 손실)**. iCloud/네이버 등 동일.

따라서 "폴더 삭제" 한 버튼이라도 Gmail은 라벨 해제에 가깝고, IMAP은 영구 삭제에 가깝다.

### 16.11.3 정책 (확정 방향)

16.2의 "프로바이더=진실" 원칙을 삭제에도 적용한다: **프로바이더에서 먼저 삭제 → 성공 시 로컬 정합.** 실패 시 로컬 미변경(원자성).

- **대상/가드**: 16.3과 동일. 시스템 폴더(inbox/sent/drafts/trash/archive/spam)·특수용도·`INBOX`는 거부. 1차는 **하위 폴더 없는** 사용자 폴더만(하위 연쇄 삭제는 범위 밖).
- **로컬 처리(프로바이더 의미에 맞춤)**:
  - Gmail: 라벨 삭제 성공 → 로컬 폴더 행 삭제. 메일은 **보존**(고아 방지를 위해 `folder_id`를 계정의 아카이브/전체보관함 폴더로 재배치하거나, 최소한 목록 조회가 `folder_id IS NULL`도 포괄하도록 보완).
  - IMAP: 메일함 삭제 성공 → 로컬 폴더 행 + **그 폴더의 메일 행 삭제**(서버에서 이미 사라졌으므로). 첨부/blob은 15.8과 동일하게 후속 GC 과제.
- **`ON DELETE SET NULL` 재검토**: 고아 메일을 원치 않으면, 삭제 전 리포지토리에서 메일을 명시적으로 (Gmail)재배치 또는 (IMAP)삭제한 뒤 폴더 행을 지운다. FK 동작에 의존하지 않는다.

### 16.11.4 확인 UX (필수)

파괴성이 프로바이더별로 다르므로 **확인 다이얼로그 문구를 분기**한다.

- Gmail: "라벨을 삭제합니다. 메일은 삭제되지 않고 전체보관함에 남습니다." (일반 확인)
- IMAP: "폴더와 **그 안의 메일 N개가 서버에서 영구 삭제**됩니다. 복구할 수 없습니다." (강한 경고, 메일 수 표기)
- 폴더가 비어있지 않으면 메일 개수를 반드시 노출한다.

### 16.11.5 서버 구현

`providerRename.js`와 대칭으로 폴더 쓰기 작업을 한 모듈로 모으는 것을 권장한다(예: `providerRename.js` → `providerFolderOps.js`로 확장, 또는 `providerDelete.js` 신설).

```
deleteFolderOnProvider({ tenantId, account, folder })
  ├─ gmail  → gmailDeleteLabel(labelId)         // 신규 헬퍼: DELETE .../labels/{id}
  └─ imap   → client.mailboxDelete(path)         // imapflow 제공(확인됨)
```
라우트(`DELETE /accounts/:id/folders/:folderId`)는 얇게: 가드 → `deleteFolderOnProvider` → 성공 시 `repo.deleteFolder`(로컬 메일 재배치/삭제 포함, 트랜잭션). 로컬 전용 폴더는 프로바이더 호출 없이 곧장 로컬 삭제.

### 16.11.6 범위 / 5원칙

- **1차**: 로컬 전용 폴더 삭제(현행 유지), Gmail 라벨 삭제(비파괴), 하위 없는 IMAP 메일함 삭제(파괴, 강한 확인).
- **범위 밖**: 하위 폴더 연쇄 삭제, 스토리지 blob 회수, 휴지통으로의 "안전 삭제" 옵션(즉시 영구삭제 대신 서버 휴지통 이동).
- **5원칙**: 삭제는 tenant/account 스코프 리포지토리 함수로만, 프로바이더 호출은 전용 모듈, 라우트/UI에 SQL·프로바이더 호출 없음.

## 16.12 서브 폴더 표시 위치 및 정렬 정책

### 16.12.1 배경 / 문제

현재 서브 폴더를 생성하면 전체 폴더 목록이 이름순으로 다시 정렬되면서, 새 서브 폴더가 선택한 부모 폴더 바로 아래가 아니라 전체 목록의 이름순 위치에 섞여 들어가는 문제가 있다.

예:

- `002-GTSystem` 아래에 `002-세금계산서`를 서브 폴더로 만들었는데,
- 전체 이름순 정렬 때문에 `001-SiliconCube...` 아래 또는 다른 위치에 들어간 것처럼 보일 수 있다.

사용자 기대 동작은 다음이다.

- 서브 폴더는 반드시 선택한 부모 폴더 바로 아래에 표시된다.
- 서브 폴더끼리는 해당 부모 폴더 아래에서만 이름순으로 정렬된다.
- 다른 최상위 폴더의 이름순 정렬이 서브 폴더의 표시 위치를 침범하지 않는다.

### 16.12.2 표시 정책

폴더 사이드바는 단순한 전체 이름순 목록이 아니라 **계층형 목록**으로 렌더링한다.

정렬 규칙:

1. 최상위 폴더는 기존 정책대로 이름순 또는 시스템 폴더 우선순위에 따라 정렬한다.
2. 각 최상위 폴더를 렌더링한 직후, 그 폴더의 자식 폴더를 바로 아래에 렌더링한다.
3. 자식 폴더는 부모별 그룹 안에서만 이름순으로 정렬한다.
4. 자식 폴더의 자식이 있으면 같은 규칙을 재귀적으로 적용한다.
5. 전체 `folders` 배열을 단순 이름순으로 정렬한 뒤 그대로 출력하지 않는다.

예상 표시:

```text
001-SiliconCube
  001-결재
002-GTSystem
  002-세금계산서
003-세종대
004-NWC
```

### 16.12.3 데이터 기준

서브 폴더 판정은 `parent_folder_id`를 기준으로 한다.

- 부모 없는 폴더: `parent_folder_id`가 비어 있거나 `null`
- 자식 폴더: `parent_folder_id === parent.id`

이름이 비슷하거나 prefix가 같다는 이유만으로 부모/자식 관계를 추론하지 않는다.

### 16.12.4 프론트 구현 방향

사이드바 렌더링 전에 폴더 목록을 계층 구조로 변환한다.

권장 흐름:

1. `folders`를 `parent_folder_id` 기준으로 그룹화한다.
2. 루트 폴더 목록을 구한다.
3. 루트 폴더를 정렬한다.
4. 각 루트 폴더를 출력한다.
5. 해당 루트 폴더의 자식 목록을 이름순 정렬 후 바로 아래에 출력한다.
6. 자식 폴더가 여러 단계이면 재귀적으로 반복한다.

주의:

- `getFolderDepth`만으로 들여쓰기만 계산하면 위치 문제는 해결되지 않는다.
- 반드시 렌더링 순서 자체가 부모 → 자식 순서가 되도록 정렬된 flat list를 만들어야 한다.

### 16.12.5 서브 폴더 생성 후 UI 갱신

서브 폴더 생성 API 응답을 받은 뒤 프론트 상태에 새 폴더를 추가할 때도 동일 정책을 적용한다.

처리 원칙:

- 표시 위치는 선택한 부모 폴더 바로 아래로 들어가야 한다.

# 17. 이중 휴지통 정리 / 트래시 폴더 정합 (데이터 이관)

## 17.1 배경 / 문제

일부 IMAP 계정(예: iCloud `freegear@me.com`)은 휴지통이 **둘로 중복**돼 있다.

- 실제 iCloud 휴지통 메일함 `Trash` — `type='custom'`, `provider_folder_id='Trash'`, 메일 보유.
- 정규화된 `휴지통` — `type='trash'`, `provider_folder_id='TRASH'`, 비어있음.

원인은 16장 후속으로 수정한 분류 로직 이전에, iCloud가 `\Trash` special-use를 안 줘서 `Trash` 메일함이 `custom`으로 분류됐기 때문이다(2-A에서 [classifyMailbox](../server/mail/imapSync.js)가 이름으로도 휴지통을 판정하도록 수정 완료 — **신규 계정은 재발 없음**). 그러나 **기존 계정의 잔재는 남아 있다.**

## 17.2 2-A 수정 이후의 상호작용 (중요 — 이관이 필요한 이유)

2-A 이후 기존 계정을 **재동기화하면 상황이 악화**된다.

- IMAP 메시지 식별자는 `provider_message_id = imap:<providerFolderId>:<uid>`. 기존 `Trash` 메일함 메일은 `imap:Trash:<uid>`.
- 2-A로 `Trash` 메일함이 `type='trash'`로 분류되면 `normalizeFolderIdentity`가 `providerFolderId='TRASH'`로 정규화 → `upsertFolders`는 `(account,'TRASH')` 키의 기존 `휴지통` 폴더를 갱신하고, 원래 `Trash`(provider_folder_id='Trash') 폴더는 **discovery에서 더 이상 생성되지 않아 고아**가 된다.
- 같은 물리 메일이 이제 `imap:TRASH:<uid>`로 다시 수집되는데, 이는 **새 `provider_message_id`**(`UNIQUE(account_id, provider_message_id)` 기준 다른 행)라 **중복 삽입**된다. → 휴지통 메일이 두 벌.

따라서 2-B는 "있으면 좋은 정리"가 아니라 **재동기화 전에 처리해야 중복을 막는** 이관이다.

## 17.3 이관 방안 (택1 — A 권장)

**방안 A — 로컬 재배치(무손실, 멱등) [권장]**
잔재 `custom` 트래시 폴더의 메일을 정규 `휴지통`(TRASH)으로 로컬 이동한 뒤 잔재 폴더를 제거한다.

1. 계정별로 **잔재 트래시 폴더**를 식별: 트래시-동치(`UPPER(provider_folder_id)='TRASH'` 또는 이름='휴지통' 또는 15.x 후보)이면서 `type='custom'`인 폴더.
2. 같은 계정의 **정규 트래시 폴더**(`type='trash'`) 확보. 없으면 잔재 폴더를 승격(`UPDATE type='trash', provider_folder_id='TRASH', name='휴지통'`)하고 메일 이동은 생략.
3. 정규 폴더가 이미 있으면(Apple 케이스): 잔재 폴더 메일을 정규 폴더로 이동
   - `UPDATE mail_messages SET folder_id = <정규>, provider_message_id = 'imap:TRASH:' || split_part(provider_message_id,':',3) WHERE folder_id=<잔재>`.
   - **중복 충돌 처리**: 정규 폴더에 동일 `imap:TRASH:<uid>`가 이미 있으면(재동기화가 이미 한 번 돈 경우) 잔재 쪽을 UPDATE 대신 **삭제**(`ON CONFLICT` 회피 위해 선(先)존재 검사 후 분기). `UNIQUE(account_id, provider_message_id)`를 위반하지 않도록 한다.
4. 잔재 폴더 행 삭제. 이후 메일은 정규 폴더에 있으므로 재동기화 시 `provider_message_id`가 일치 → **중복 없이 멱등**.

**방안 B — 비우고 재동기화(단순, 손실 감수)**
잔재 폴더를 비우고(1번 purge 완화로 가능) 삭제 → 재동기화가 정규 `휴지통`을 새로 채움. 로컬 전용 이력이 사라지지만 대상이 휴지통이라 수용 가능. 서버에 메일이 남아있어야 복원됨.

> 권장: **A**. 무손실·멱등이며 재동기화 중복을 원천 차단한다.

## 17.4 실행 형태

- `mailRepository`에 **멱등 유지보수 함수** 추가(예: `reconcileTrashFolders({ tenantId, userId })`) — [seedSmartFoldersFromCustomFolders](../server/mail/repository.js)처럼 트랜잭션·멱등 패턴을 따른다.
- 트리거: 관리자용 1회 실행 라우트 또는 계정 동기화 진입 시 1회 가드(플래그로 재실행 방지). **재동기화보다 먼저** 실행되도록 순서를 보장한다.
- 전 계정 스캔이지만 tenant/account/user 스코프로 좁혀 실행(5원칙).

## 17.5 주의 · 정합

- **UNIQUE(account_id, provider_message_id)**: `provider_message_id` 재작성 시 충돌 검사 필수(17.3 A-3).
- **`ON DELETE SET NULL`**: 잔재 폴더를 그냥 지우면 메일이 고아가 된다 → 반드시 **메일 이동(또는 재배치)을 먼저** 하고 폴더를 지운다.
- **첨부/blob**: 메일 행을 이동만 하면 `object_key`는 그대로 유효(계정 스코프 동일)하므로 스토리지 변화 없음. 방안 B의 삭제 시에만 blob 잔존(15.8과 동일, 후속 GC).
- **다른 시스템 폴더로 확장**: 같은 원인으로 sent/spam/archive도 이중화될 수 있으므로, `reconcile` 함수는 트래시에 국한하지 말고 **동일 로직을 시스템 폴더 일반으로** 확장 가능하게 설계한다(1차는 트래시만).

## 17.6 5원칙 준수

1. `mail_folders`/`mail_messages` 모두 `tenant_id` 보유, 이관은 tenant/account/user 스코프. 2. 이관 로직은 `mailRepository`만. 3. 라우트/UI에 SQL 없음. 4. 메일 이동은 blob을 재생성하지 않아 `object_key` 스코프 규칙과 무관. 5. tenant 라우팅은 `connectionManager`가 담당.

# 18. 메일 리스트 카드의 스마트 폴더 태그 칩(라벨)

## 18.1 배경 / 목적

- 현재 스마트 폴더 태그 배지는 **메일 상세**에서만 노출된다(13.7). 리스트 카드만 봐서는 그 메일이 이미 어떤 스마트 폴더에 태깅됐는지 알 수 없다.
- 목표: 리스트 카드 안에 **작은 색상 칩(pill)** 을 붙여, "이 메일은 `001-SilconCube` 스마트 폴더에 태깅됨"을 한눈에 보이게 한다. Gmail 라벨과 동일한 멘탈 모델.
- 색상은 **왼쪽 스마트 폴더 목록의 색과 반드시 동일**하게 써서 사이드바 ↔ 카드가 시각적으로 연결되게 한다.

목표 표시 예시(카드):

```
● Anthropic, PBC                          2026. 7. 3.
  Your receipt from Anthropic, PBC #2535…
  🏷 001-SilconCube   Anthropic, PBC (https://www.anthropic.com/) …
```

## 18.2 표시 사양 (확정)

- **위치**: 카드 하단 스니펫 줄([MailPage.jsx](../src/features/mail/MailPage.jsx) `MailMessageList`의 313~322행 영역) **맨 앞**에 칩들을 인라인 배치한다. 세로 공간을 추가로 먹지 않게 스니펫과 같은 줄에서 시작하고, 칩 영역은 `flex-shrink-0`, 스니펫은 `min-w-0 truncate`로 두어 칩이 우선 보이고 스니펫이 잘리게 한다.
- **칩 형태**: `색 점(dot) + 폴더명` 을 담은 pill. 배경은 폴더색의 연한 틴트(예: 색 + 낮은 opacity), 텍스트/점은 진한 폴더색. `color_key`가 없으면 중립 회색(gray-400/gray-100).
- **폴더명 표기**: 전체 이름을 쓰되 카드 폭 압박 시 pill 자체를 `max-w-[120px] truncate`. 접두어(`001-` 등)는 제거하지 않는다(사이드바 표기와 일치). `title` 속성에 전체 이름을 넣어 hover 툴팁 제공.
- **다중 태그**: 한 메일이 여러 스마트 폴더에 태깅될 수 있다(`mail_message_tags`는 다대다). 칩을 **최대 2개**까지 나열하고 나머지는 `+N` 배지로 축약한다. `+N`의 `title`에 생략된 폴더명 전체를 넣는다.
- **자기 폴더 숨김 규칙**: **현재 보고 있는 뷰가 특정 스마트 폴더**일 때는, 그 폴더 칩은 카드에서 **생략**한다(자기 자신 라벨은 중복·노이즈). 그 외 뷰(모든 편지함/받은 편지함/개별 계정 폴더 등)에서는 모든 태그를 표시한다.
- **정렬**: 사이드바와 동일하게 폴더명 오름차순(`listSmartFoldersForMessage`가 이미 `ORDER BY sf.name ASC`).
- **읽음/안읽음**: 칩 스타일은 읽음 상태와 무관하게 동일(가독성 유지). 안읽음 강조는 기존 제목 볼드로 충분.

## 18.3 데이터 공급 방식 (핵심 결정)

리스트 카드가 태그를 그리려면 **메일 목록 응답에 각 메일의 태그 배열이 포함**돼야 한다. 현재 `listMessages`/`listUnifiedMessages`는 태그를 반환하지 않는다.

- **채택안 (B) — 목록 쿼리에 태그 배열을 집계**: `listMessages`·`listUnifiedMessages`·`listSmartFolderMessages` 각 SELECT에 상관 서브쿼리를 추가해 `tags`를 JSON 배열로 붙인다.

  ```sql
  , COALESCE((
      SELECT json_agg(json_build_object('id', sf.id, 'name', sf.name, 'color_key', sf.color_key)
                      ORDER BY sf.name ASC)
      FROM mail_message_tags mt
      JOIN mail_smart_folders sf ON sf.id = mt.smart_folder_id
      WHERE mt.message_id = mm.id
        AND mt.tenant_id  = mm.tenant_id
        AND sf.user_id    = mm.user_id
    ), '[]'::json) AS tags
  ```

  각 메일 행이 `tags: [{ id, name, color_key }, …]`(빈 배열 가능)를 갖고 내려온다. 페이지당 최대 200행 + `idx_mail_message_tags_message` 인덱스가 있어 성능 부담이 낮다.

- **반려안 (A) 카드별 N+1 호출**(`listSmartFoldersForMessage`를 카드마다): 요청 폭증 → 반려.
- **반려안 (C) 별도 배치 엔드포인트**(메일 ID 목록 → 태그맵): 라운드트립 1회 추가 + 페이지네이션/무한스크롤과 상태 합치기 복잡 → 반려. (단, 목록 쿼리를 건드리기 싫은 경우의 대안으로만 기록.)

> 5원칙 ③: 위 SQL은 전부 `server/mail/repository.js` 안에서만 작성한다. 라우트/UI에는 SQL을 두지 않는다.

  - **칩 컴포넌트 신설**: `SmartFolderTagChip({ name, colorKey })` — `FOLDER_COLOR_MAP`(1609행)에서 색을 뽑아 pill 렌더. 색 없으면 회색 폴백. `FolderColorSwatch`/사이드바와 동일 팔레트 사용.
  - **카드 렌더 수정**: `MailMessageList`(223행)의 스니펫 줄(313~322)에서 `message.tags`를 매핑해 칩을 스니펫 앞에 배치. 자기 폴더 숨김을 위해 현재 활성 뷰의 스마트 폴더 id를 prop으로 전달받아 필터.
  - **prop 전달**: `MailMessageList` 호출부에 `activeSmartFolderId`(현재 뷰가 스마트 폴더면 그 id, 아니면 null) 추가.
  - **낙관적 업데이트**: 드래그-드롭 태그 부여/해제, 상세에서 태그 추가·제거 시 로컬 `messages`의 해당 항목 `tags`를 갱신(기존 `setMessages(prev => prev.map(...))` 패턴 재사용, 예: 3970행). 서버 재조회 없이 칩이 즉시 반영/사라지게 한다.
  - **카운트 정합**: 태그 부여/해제 후 `reloadSmartFolders()`(3877행)로 사이드바 `0/N` 카운트도 함께 갱신(기존 동작 유지).

## 18.6 성능 / 정합

- 목록 쿼리 1회로 태그까지 내려오므로 추가 왕복 없음. 서브쿼리는 메일당 인덱스 조회.
- 태그는 **로컬 전용 메타데이터**(동기화가 건드리지 않음, 13.9) → 동기화가 칩을 흔들지 않는다.
- 휴지통/스팸/삭제 메일 제외 규칙(13.7)은 **카운트/스마트 폴더 뷰**에만 적용된다. 칩 자체는 "이 메일에 붙은 태그"를 그대로 보여주므로 별도 필터 불필요(태그가 있으면 칩 표시).

## 18.7 접근성 / UX 세부

- pill에 `title`(전체 폴더명), 점 아이콘에 `aria-hidden`. `+N` 배지 `title`에 생략 폴더명 전체.
- 색만으로 구분하지 않도록 **점 + 텍스트** 병기(색각 이상 대응).
- 라이트/다크 대비: 틴트 배경 + 진한 텍스트로 두 테마 모두 대비 확보.

## 18.8 1차 구현 범위 / 범위 밖

- **1차 포함**: 목록 응답에 `tags` 집계, 카드 칩 표시(최대 2 + `+N`), 자기 폴더 숨김, 낙관적 갱신.
- **범위 밖(후속)**: 칩 클릭으로 해당 스마트 폴더로 점프, 칩에서 바로 태그 제거(x 버튼), 칩 커스텀 아이콘, 태그 순서 사용자 지정.

## 18.9 5원칙 준수

1. `mail_message_tags`/`mail_smart_folders` 모두 `tenant_id` 보유, 집계 서브쿼리도 tenant/user 스코프. 2. 태그 조회는 전부 `mailRepository`(`listMessages`/`listUnifiedMessages`/`listSmartFolderMessages`)만. 3. 라우트/UI에 SQL 없음(프래그먼트도 repository 내부 상수). 4. 스토리지 무관(메타데이터 전용). 5. tenant 라우팅은 `connectionManager` 유지.

## 18.10 태그 칩 가시성 개선 (개정)

### 18.10.1 문제 / 원인

리스트 카드의 태그 칩이 **흐릿해서 잘 안 보인다**. 원인은 두 가지이며, 실사용에서는 첫 번째가 지배적이다.

- **(주원인) 색 미지정 → 전부 회색**: 스마트 폴더 대부분이 `color_key = null`이다(사용자가 색을 따로 지정하지 않음). 그러면 칩이 중립 회색(bg `#f3f4f6` + 텍스트 `#6b7280`)으로만 렌더되어 흰 배경 카드에서 거의 묻힌다. 화면의 `001-새하늘새땅`·`010-청구·결제`가 모두 회색으로 나오는 이유.
- **(부원인) 틴트가 너무 옅고 텍스트 대비 낮음**: 색이 있어도 배경이 `${color}22`(약 13% 알파)로 매우 옅고, 텍스트를 폴더색 원색으로 써서 노랑·연두 계열은 흰 배경 대비가 부족하다.

### 18.10.2 개선안 (확정)

세 가지를 함께 적용한다. **① 자동 색 배정**이 핵심 해결책, ②·③은 대비 강화.

- **① 색 미지정 폴더에 자동 팔레트 색 배정(결정적 해시)** — `color_key`가 없으면 폴더 **이름 해시 → 6색 팔레트(빨/주/노/녹/파/퍼플) 순환**으로 안정적으로 색을 부여한다. 같은 이름은 항상 같은 색(리로드/기기 간 일관). 사용자가 색을 지정하면 그 색이 우선.

  ```
  const AUTO_TAG_PALETTE = ['red','orange','yellow','green','blue','purple'] // FOLDER_COLOR_OPTIONS에서 '' 제외
  function autoTagColorKey(name) {
    let h = 0
    for (const ch of String(name)) h = (h * 31 + ch.codePointAt(0)) >>> 0
    return AUTO_TAG_PALETTE[h % AUTO_TAG_PALETTE.length]
  }
  // 실제 사용 색 = colorKey || autoTagColorKey(name)
  ```

- **② 칩 스타일 강화 — 테두리 + 진한 틴트 + 고대비 텍스트**: 색을 **테두리(1.5px 실선, 폴더색 원색)** 로 명확히 드러내고, 배경은 조금 더 진한 틴트(예: 알파 `0x22`→`0x33` 수준), 텍스트는 **어두운 회색 `#374151` 고정**으로 색상(hue)에 무관하게 항상 읽히게 한다. 색 점(dot)은 유지. → "테두리+점으로 색을 인지, 텍스트는 항상 또렷" 조합이라 노랑·연두에서도 대비 문제 없음.

- **③ 대비 하한 규칙**: 옵션으로 "채운 칩(배경=폴더색 원색 + 흰 텍스트)"을 쓸 경우, **밝은 색(노랑·연두 등 상대 휘도 높은 색)** 은 흰 텍스트 대신 어두운 텍스트로 자동 전환한다. 1차는 ②(테두리형)를 채택하므로 이 규칙은 채운 칩을 도입할 때만 적용.

> **채택**: ①+②(테두리형). 색상 대비 함정(밝은 hue) 없이 가장 안전하게 "잘 보이게" 되는 조합. "채운 칩"(더 강한 시각 무게)은 ③ 대비 규칙과 함께 후속 옵션으로 남긴다.

### 18.10.3 다크 모드 / 접근성

- 다크 배경에서는 틴트를 배경 위 블렌드가 아닌 반투명 알파로 얹어 색이 유지되게 하고, 텍스트는 밝은 회색(`#e5e7eb`)으로 전환한다(테마 토큰/`prefers-color-scheme` 대응).
- 색만으로 구분하지 않도록 **점 + 텍스트** 병기 원칙(18.7) 유지. `title`에 전체 폴더명.

### 18.10.4 사이드바 정합 (권장)

- 리스트 칩에 자동 색을 도입하면 **사이드바 스마트 폴더 아이콘도 동일한 `autoTagColorKey`** 를 적용해 색이 어긋나지 않게 한다(칩 ↔ 사이드바 = 같은 색 원칙, 18.1). 사용자가 색을 지정하면 양쪽 모두 지정색 우선.

### 18.10.5 범위 / 5원칙

- **순수 프론트 표시 로직**: 서버/스키마/쿼리 변경 없음(태그 데이터는 18.3 그대로). `color_key`가 여전히 null이어도 표시 시점에 자동 색을 계산할 뿐, DB에 색을 쓰지 않는다. → 5원칙 무관(서버 미변경).
- 변경 지점: [MailPage.jsx](../src/features/mail/MailPage.jsx) `SmartFolderTagChip`(스타일 + 자동 색), 필요 시 사이드바 스마트 폴더 아이콘 색 계산부.

# 19. 메일 요약 서비스



# 19. 메일 요약 서비스

메일 본문을 LLM으로 분석해 업무용 요약을 생성하는 기능을 제공한다.

요약 결과는 반드시 아래 순서로 표시한다.

1. 일정:
2. 중요 포인트
3. 중요 내용 요약
4. 액션 아이템 / 시간

## 19.1 요약 기능 목표

- 사용자가 선택한 메일 본문을 확인하고 핵심 내용을 업무용으로 요약한다.
- 회의, 일정, 요청사항, 준비물, 회신 필요 여부를 빠르게 파악할 수 있게 한다.
- 출력 형식을 고정해 사용자가 항상 같은 구조로 결과를 확인할 수 있게 한다.
- 메일에 없는 내용은 추측하지 않고, 확인된 내용만 요약한다.

## 19.2 LLM 요구사항 전달 방식

LLM에는 단순히 "메일을 요약해줘"라고 요청하지 않고, 역할, 출력 순서, 추출 기준, 제약 조건을 명확히 전달한다.

### System Prompt 예시

```text
당신은 이메일 내용을 분석해 업무용 요약을 작성하는 assistant입니다.

사용자가 제공한 이메일 본문을 읽고, 반드시 아래 순서와 제목으로만 요약하세요.

출력 순서:
1. 일정:
2. 중요 포인트
3. 중요 내용 요약
4. 액션 아이템 / 시간

작성 규칙:
- 이메일 본문에 있는 정보만 사용하세요.
- 추측하거나 없는 내용을 만들지 마세요.
- 날짜, 시간, 장소, 참석 대상 등 일정 정보는 "일정:" 섹션에 정리하세요.
- 핵심 목적, 회의 배경, 주요 요청사항은 "중요 포인트"에 bullet 형식으로 정리하세요.
- 전체 메일 내용을 2~4문장으로 자연스럽게 요약해 "중요 내용 요약"에 작성하세요.
- 사용자가 해야 할 일, 준비물, 회신 필요 여부, 마감 또는 관련 시간은 "액션 아이템 / 시간"에 정리하세요.
- 정보가 없는 항목은 "확인된 내용 없음"이라고 작성하세요.
- 한국어로 작성하세요.
- 불필요한 인사말이나 설명은 제외하세요.
```

### User Prompt 예시

```text
이메일 본문:
{{EMAIL_BODY}}
```

## 19.3 요약 결과 출력 형식

LLM 응답은 아래 형식을 기본으로 한다.

```text
일정:
- 날짜:
- 시간:
- 장소:

중요 포인트
- ...
- ...

중요 내용 요약
...

액션 아이템 / 시간
- ...
- ...
```

일정 정보가 일부만 있는 경우 확인된 항목만 채우고, 없는 항목은 `확인된 내용 없음`으로 표시한다.

예:

```text
일정:
- 날짜: 7월 15일 수요일
- 시간: 13:30부터
- 장소: ETRI 대전 본원 7동 415호

중요 포인트
- 킬스위치 사업 최종년도 하반기 진행 상황 점검 회의
- 각 기관별 성과 달성 현황과 이슈 사항 공유 예정
- 각 기관에서 최소 1명 참석 요청
- 참석이 어려운 기관은 사전 연락 필요

중요 내용 요약
ETRI 오봉진 님이 킬스위치 사업 최종년도 하반기 진행 상황과 기관별 성과 달성 여부를 확인하기 위한 회의를 안내했습니다. 참석자는 진행 상황, 성과 달성 현황, 이슈 사항 등을 자유양식 자료로 준비해 공유하면 됩니다.

액션 아이템 / 시간
- 회의 참석 가능 여부 확인
- 기관별 참석자 1명 이상 선정
- 발표 자료 준비
- 참석이 어려운 경우 사전 연락
```

## 19.4 추출 기준

- 일정:
  - 날짜, 요일, 시간, 장소, 회의 방식, 참석 대상 등 일정성 정보를 정리한다.
- 중요 포인트:
  - 메일의 목적, 배경, 핵심 요청사항, 주요 공지사항을 bullet 형식으로 정리한다.
- 중요 내용 요약:
  - 메일 전체 내용을 2~4문장으로 자연스럽게 요약한다.
  - 인사말, 서명, 반복 표현은 제외한다.
- 액션 아이템 / 시간:
  - 사용자가 해야 할 일, 준비 자료, 회신 필요 여부, 마감, 참석 여부 확인 등을 정리한다.
  - 특정 시간이 연결된 액션은 함께 표시한다.

## 19.5 구현 흐름

1. 사용자가 메일 상세 화면에서 요약 기능을 실행한다.
2. 클라이언트는 선택된 메일의 제목, 발신자, 수신자, 수신 시간, 본문을 서버에 전달한다.
3. 서버는 요약용 prompt를 구성해 LLM에 요청한다.
4. LLM 응답은 `일정`, `중요 포인트`, `중요 내용 요약`, `액션 아이템 / 시간` 순서를 유지해야 한다.
5. 클라이언트는 응답을 메일 상세 화면의 요약 패널 또는 팝업에 표시한다.

## 19.6 응답 검증 규칙

- 결과에 필수 섹션 4개가 모두 있는지 확인한다.
- 섹션 순서가 아래와 같은지 확인한다.
  - `일정:` -> `중요 포인트` -> `중요 내용 요약` -> `액션 아이템 / 시간`
- 메일 본문에 없는 날짜, 장소, 인물, 액션이 생성되지 않도록 한다.
- LLM 응답이 형식을 벗어나면 재요청하거나 서버에서 기본 형식으로 보정한다.

## 19.7 UI 표시 방식

- 메일 상세 화면에 `요약` 버튼을 제공한다.
- 요약 생성 중에는 로딩 상태를 표시한다.
- 요약 결과는 읽기 쉬운 섹션 형태로 표시한다.
- 사용자가 요약 결과를 복사할 수 있는 버튼을 제공한다.
- 요약 실패 시에는 재시도 버튼과 간단한 오류 메시지를 표시한다.

## 19.8 JSON 구조화 응답 방식

메일 요약 결과는 장기적으로 Markdown 문자열이 아니라 JSON 구조로 받는 방식을 채택한다.

Markdown 응답은 사람이 읽기에는 편하지만, UI가 안정적으로 해석하기 어렵다. 예를 들어 LLM이 `**일정:**`, `## 일정`, `일정 정보:`처럼 매번 다른 표현을 만들 수 있다. 반면 JSON 응답은 서버가 검증하기 쉽고, 프론트가 섹션별 UI로 직접 렌더링하기 쉽다.

따라서 메일 요약 서비스는 아래 방향으로 개선한다.

- LLM은 Markdown 문장이 아니라 정해진 JSON 객체만 반환한다.
- 서버는 LLM 응답을 JSON으로 파싱하고 필수 필드를 검증한다.
- 프론트는 JSON 데이터를 받아 `일정`, `중요 포인트`, `중요 내용 요약`, `액션 아이템 / 시간` 섹션으로 직접 렌더링한다.
- Markdown 문법이 화면에 그대로 노출되는 문제를 제거한다.
- 향후 일정 등록, 할 일 등록, AgenticAI, MailClaw 연동에 사용할 수 있는 구조화 데이터를 확보한다.

## 19.9 JSON 응답 스키마

LLM은 반드시 아래 형태의 JSON만 반환한다.

```json
{
  "schedule": {
    "date": "",
    "time": "",
    "location": "",
    "participants": "",
    "notes": ""
  },
  "keyPoints": [],
  "summary": "",
  "actionItems": [
    {
      "task": "",
      "time": ""
    }
  ]
}
```

필드 의미:

- `schedule.date`
  - 메일에서 확인된 날짜와 요일.
  - 예: `7월 15일 수요일`
- `schedule.time`
  - 메일에서 확인된 시간.
  - 예: `13:30부터`
- `schedule.location`
  - 회의 장소 또는 진행 방식.
  - 예: `ETRI 대전 본원 7동 415호`
- `schedule.participants`
  - 참석 대상, 참석 요청 대상, 기관별 참석 조건.
  - 예: `각 기관에서 가능한 인원 1명 이상`
- `schedule.notes`
  - 일정과 관련된 추가 조건.
  - 예: `참석이 어려운 기관은 별도 일정 조율`
- `keyPoints`
  - 메일의 핵심 목적, 배경, 주요 요청사항을 문자열 배열로 정리한다.
- `summary`
  - 메일 전체 내용을 2~4문장으로 요약한 문자열.
- `actionItems`
  - 사용자가 해야 할 일을 배열로 정리한다.
  - `task`는 해야 할 일, `time`은 관련 시간 또는 마감이다.

값이 없을 때 처리:

- 문자열 필드에 정보가 없으면 빈 문자열 대신 `확인된 내용 없음`을 넣는다.
- 배열 필드에 정보가 없으면 빈 배열 대신 `["확인된 내용 없음"]`을 넣는다.
- `actionItems`에 할 일이 없으면 아래와 같이 넣는다.

```json
{
  "actionItems": [
    {
      "task": "확인된 내용 없음",
      "time": "확인된 내용 없음"
    }
  ]
}
```

## 19.13 서버 검증 및 보정 규칙

서버는 LLM 응답을 그대로 클라이언트에 전달하지 않고 아래 절차를 수행한다.

1. LLM 응답 문자열에서 JSON을 파싱한다.
2. JSON 파싱에 실패하면 1회 재요청한다.
3. 재요청도 실패하면 기존 텍스트 요약 방식 또는 fallback 메시지를 사용한다.
4. 필수 필드가 없으면 기본값으로 보정한다.
5. 필드 타입이 다르면 안전한 타입으로 보정한다.
6. 최종 응답은 항상 동일한 JSON 스키마를 유지한다.

보정 기준:

- `schedule`이 없으면 기본 schedule 객체를 만든다.
- `keyPoints`가 배열이 아니면 문자열을 배열로 감싸거나 `["확인된 내용 없음"]`으로 바꾼다.
- `summary`가 문자열이 아니면 `확인된 내용 없음`으로 바꾼다.
- `actionItems`가 배열이 아니면 기본 action item을 넣는다.
- `actionItems`의 각 항목에 `task`, `time`이 없으면 `확인된 내용 없음`으로 채운다.

API 응답 예:

```json
{
  "ok": true,
  "messageId": "message-id",
  "tenantId": "tenant-id",
  "model": "gemma4:e4b",
  "summary": {
    "schedule": {
      "date": "7월 15일 수요일",
      "time": "13:30부터",
      "location": "ETRI 대전 본원 7동 415호",
      "participants": "각 기관에서 가능한 인원 1명 이상",
      "notes": "참석이 어려운 기관은 사전 연락 후 별도 일정 조율"
    },
    "keyPoints": [],
    "summary": "",
    "actionItems": []
  },
  "rawText": ""
}
```

`rawText`는 디버깅 또는 fallback 용도로만 사용하며, 기본 UI에는 노출하지 않는다.

## 19.14 프론트 UI 렌더링 방식

프론트는 Markdown 렌더링을 하지 않고 JSON 데이터를 직접 화면에 그린다.

표시 순서:

1. 일정
2. 중요 포인트
3. 중요 내용 요약
4. 액션 아이템 / 시간

섹션별 표시:

- 일정
  - 날짜, 시간, 장소, 참석 대상, 비고를 작은 정보 행으로 표시한다.
  - 값이 `확인된 내용 없음`이면 흐린 색으로 표시한다.
- 중요 포인트
  - `keyPoints` 배열을 bullet 목록으로 표시한다.
- 중요 내용 요약
  - `summary` 문자열을 문단으로 표시한다.
- 액션 아이템 / 시간
  - `actionItems` 배열을 목록 또는 테이블 형태로 표시한다.
  - `task`와 `time`을 분리해서 보여준다.

복사 기능:

- `요약 복사` 버튼은 화면에 보이는 형태와 같은 순서의 일반 텍스트를 만들어 클립보드에 복사한다.
- JSON 원문을 복사하지 않는다.

## 19.15 향후 확장 포인트

JSON 구조화 응답을 사용하면 아래 기능으로 확장할 수 있다.

- `schedule`을 캘린더 일정 등록으로 연결
- `actionItems`를 EasyStation 할일목록에 추가

## 19.17 요약 결과 DB 저장 및 재조회

메일 요약 결과는 메일 상세 화면의 임시 상태에만 보관하지 않고 DB에 저장한다.

현재 동작은 사용자가 메일 상세 화면에서 `요약` 버튼을 눌러 결과를 생성한 뒤 다른 메일을 선택하거나 화면을 이동하면 요약 결과가 사라진다. 사용자가 이미 비용과 시간을 들여 생성한 요약은 같은 메일을 다시 열었을 때 그대로 보여야 한다.

따라서 한 번 생성된 요약은 메일 DB에 연결해 저장하고, 이후 해당 메일을 다시 조회할 때 저장된 요약을 함께 내려준다.

목표:

- 한 번 생성한 요약은 같은 메일을 다시 열어도 유지한다.
- 요약 결과는 tenant/user/message 스코프를 지켜 저장한다.
- `요약` 버튼은 저장된 요약이 없을 때만 새 요약을 생성한다.
- 저장된 요약이 있으면 즉시 표시하고, 사용자가 원할 때만 `요약 다시 생성`으로 갱신한다.
- 요약 결과는 JSON 구조화 응답 스키마(19.9)를 그대로 저장한다.

## 19.18 DB 테이블 설계

요약 결과는 별도 테이블로 저장한다. `mail_messages` 테이블에 컬럼을 직접 추가하지 않는다.

이유:

- 요약은 원본 메일 데이터가 아니라 AI 생성 메타데이터다.
- 재생성 이력, 모델명, raw 응답, 오류 상태 등을 확장하기 쉽다.
- 메일 동기화 로직이 원본 메일 필드와 요약 필드를 혼동하지 않게 한다.

테이블명:

```text
mail_message_summaries
```

컬럼 예시:

```sql
CREATE TABLE IF NOT EXISTS mail_message_summaries (
  id                  TEXT PRIMARY KEY,
  tenant_id           TEXT NOT NULL,
  user_id             TEXT NOT NULL,
  account_id          TEXT NOT NULL,
  message_id          TEXT NOT NULL,
  provider_message_id TEXT,

  summary_json        JSONB NOT NULL,
  raw_text            TEXT NOT NULL DEFAULT '',
  model               TEXT NOT NULL DEFAULT '',
  prompt_version      TEXT NOT NULL DEFAULT 'mail-summary-json-v1',
  summary_version     INTEGER NOT NULL DEFAULT 1,

  generated_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at          TIMESTAMPTZ NOT NULL DEFAULT NOW(),

  UNIQUE (tenant_id, user_id, message_id)
);
```

인덱스:

```sql
CREATE INDEX IF NOT EXISTS idx_mail_message_summaries_message
  ON mail_message_summaries (tenant_id, user_id, message_id);

CREATE INDEX IF NOT EXISTS idx_mail_message_summaries_account
  ON mail_message_summaries (tenant_id, user_id, account_id);
```

삭제 정책:

- 메일이 영구 삭제될 때 해당 메일의 요약도 함께 삭제한다.
- 계정 삭제 시 해당 계정의 요약도 함께 삭제한다.
- tenant/user 범위를 벗어난 요약 조회는 금지한다.

## 19.19 Repository 함수

DB 접근은 `mailRepository`에만 둔다. 라우트 또는 UI에서 SQL을 직접 작성하지 않는다.

필요 함수:

```text
getMessageSummary({ tenantId, userId, messageId })
upsertMessageSummary({ tenantId, userId, accountId, messageId, providerMessageId, summary, rawText, model, promptVersion })
deleteMessageSummary({ tenantId, userId, messageId })
deleteMessageSummariesForAccount({ tenantId, userId, accountId })
```

동작:

- `getMessageSummary`
  - 해당 메일에 저장된 최신 요약을 조회한다.
  - 없으면 `null`을 반환한다.
- `upsertMessageSummary`
  - `(tenant_id, user_id, message_id)` 기준으로 insert 또는 update한다.
  - 기존 요약이 있으면 `summary_json`, `raw_text`, `model`, `prompt_version`, `summary_version`, `updated_at`을 갱신한다.
  - `summary_version`은 갱신 시 1 증가시킨다.
- 삭제 함수
  - 메일/계정 삭제와 함께 요약을 정리한다.

## 19.20 API 동작 변경

### 메일 상세 조회

`GET /mail/messages/:id`는 메일 상세 정보와 함께 저장된 요약을 반환한다.

응답 예:

```json
{
  "id": "message-id",
  "subject": "메일 제목",
  "body_text": "...",
  "attachments": [],
  "summary": {
    "schedule": {
      "date": "7월 15일 수요일",
      "time": "13:30부터",
      "location": "ETRI 대전 본원 7동 415호",
      "participants": "각 기관에서 가능한 인원 1명 이상",
      "notes": "참석이 어려운 기관은 사전 연락 후 별도 일정 조율"
    },
    "keyPoints": [],
    "summary": "",
    "actionItems": []
  },
  "summary_meta": {
    "generated_at": "2026-07-03T00:00:00.000Z",
    "updated_at": "2026-07-03T00:00:00.000Z",
    "summary_version": 1
  }
}
```

저장된 요약이 없으면:

```json
{
  "summary": null,
  "summary_meta": null
}
```

### 요약 생성 API

`POST /mail/messages/:id/summary`는 요약을 새로 생성한 뒤 DB에 저장하고 저장된 결과를 반환한다.

기본 동작:

- 기존 저장 요약이 없으면 새로 생성한다.
- 기존 저장 요약이 있어도 사용자가 `요약 다시 생성`을 누르면 새로 생성하고 기존 요약을 갱신한다.

요청 예:

```json
{
  "tenantId": "tenant-id",
  "force": true
}
```

응답 예:

```json
{
  "ok": true,
  "messageId": "message-id",
  "tenantId": "tenant-id",
  "summary": {},
  "summary_meta": {
    "generated_at": "2026-07-03T00:00:00.000Z",
    "updated_at": "2026-07-03T00:00:00.000Z",
    "summary_version": 2
  }
}
```

`model`과 `rawText`는 서버 내부 저장 및 디버깅 용도로 사용하되 기본 UI 응답에서는 숨길 수 있다.

## 19.21 프론트 동작 변경

메일 상세 화면 진입 시:

1. 사용자가 메일을 선택한다.
2. `GET /mail/messages/:id`로 메일 상세 정보를 조회한다.
3. 응답에 `summary`가 있으면 요약 패널을 즉시 표시한다.
4. 응답에 `summary`가 없으면 요약 패널은 숨기고 `요약` 버튼만 표시한다.

버튼 표시:

- 저장된 요약이 없을 때:
  - `요약`
- 저장된 요약이 있을 때:
  - `요약 다시 생성`
  - `요약 복사`

요약 생성 시:

1. 사용자가 `요약` 또는 `요약 다시 생성` 버튼을 누른다.
2. 프론트는 `POST /mail/messages/:id/summary`를 호출한다.
3. 서버는 새 요약을 생성하고 DB에 저장한다.
4. 프론트는 응답의 `summary`로 화면을 갱신한다.
5. 사용자가 다른 메일을 봤다가 다시 돌아와도 `GET /mail/messages/:id` 응답의 저장 요약을 다시 표시한다.

UI 표시:

- 저장된 요약이 있으면 메일 본문 위쪽에 요약 패널을 표시한다.
- 요약 생성 시간을 표시할 수 있다.
  - 예: `요약 생성: 2026. 7. 3. 오후 2:10`
- 모델명은 기본 UI에 표시하지 않는다.
- `요약 다시 생성`은 기존 요약을 덮어쓰는 동작이므로 로딩 상태를 명확히 표시한다.

## 19.22 재생성 및 버전 정책

요약은 사용자가 명시적으로 `요약 다시 생성`을 누를 때만 갱신한다.

자동 재생성은 하지 않는다.

이유:

- 메일 원문은 동기화 후 일반적으로 바뀌지 않는다.
- LLM 결과가 매번 조금씩 달라질 수 있으므로, 사용자가 확인한 요약을 자동으로 바꾸면 혼란이 생긴다.
- 비용과 처리 시간을 줄인다.

버전 정책:

- 최초 생성 시 `summary_version = 1`
- 재생성 시 `summary_version = summary_version + 1`
- 현재는 최신 요약 1개만 보관한다.
- 과거 요약 이력 보관은 후속 기능으로 둔다.

## 19.23 오류 및 fallback 정책

요약 생성에 실패한 경우:

- DB에 실패 결과를 저장하지 않는다.
- 기존 저장 요약이 있으면 기존 요약을 유지한다.
- 프론트에는 오류 메시지를 표시하되 기존 요약 패널은 계속 보여준다.

예:

```text
요약을 다시 생성하지 못했습니다. 기존 요약을 유지합니다.
```

저장된 요약 JSON이 깨진 경우:

- 서버에서 기본 스키마로 보정한다.
- 보정된 결과를 응답한다.
- 필요하면 보정된 JSON을 DB에 다시 저장한다.

## 19.26 기준 언어 기반 번역 후 요약

메일 요약 기능은 사용자가 선택한 기준 언어를 기준으로 동작한다.

기준 언어는 화면 제목행의 언어 선택 UI에서 선택된 언어다. 예를 들어 제목행에서 한국어가 선택되어 있으면 메일 요약 결과는 한국어로 생성되어야 한다. 일본어가 선택되어 있으면 일본어로, 영어가 선택되어 있으면 영어로 생성되어야 한다.

요약 대상 메일의 원문 언어가 기준 언어와 다르면, 서버는 먼저 메일 내용을 기준 언어로 번역한 뒤 번역된 내용을 기반으로 요약을 생성한다.

목표:

- 사용자가 선택한 기준 언어로 항상 일관된 요약 결과를 제공한다.
- 외국어 메일도 사용자의 업무 언어로 요약한다.
- 번역과 요약이 섞여서 원문 언어가 노출되지 않도록 한다.
- 요약 DB 저장 시 어떤 언어 기준으로 생성된 요약인지 함께 저장한다.

## 19.27 기준 언어 정의

기준 언어는 제목행의 언어 선택 상태를 사용한다.

예:

```text
한국어 선택 -> 기준 언어: ko
영어 선택   -> 기준 언어: en
일본어 선택 -> 기준 언어: ja
```

지원 언어 코드는 아래처럼 관리한다.

```json
{
  "ko": "한국어",
  "en": "영어",
  "ja": "일본어"
}
```

프론트는 요약 API 호출 시 현재 선택된 기준 언어를 함께 전달한다.

요청 예:

```json
{
  "tenantId": "tenant-id",
  "force": true,
  "targetLanguage": "ko"
}
```

`targetLanguage`가 없으면 기본값은 `ko`로 처리한다.

## 19.28 언어 감지 및 처리 흐름

요약 생성 흐름은 아래 순서를 따른다.

1. 사용자가 메일 상세 화면에서 `요약` 또는 `요약 다시 생성`을 누른다.
2. 프론트는 현재 제목행 언어 선택값을 `targetLanguage`로 서버에 전달한다.
3. 서버는 메일 제목, 발신자/수신자 메타데이터, 본문을 읽는다.
4. 서버는 메일 본문의 원문 언어를 감지한다.
5. 원문 언어와 기준 언어가 같으면 번역 없이 요약한다.
6. 원문 언어와 기준 언어가 다르면 기준 언어로 번역한다.
7. 서버는 번역된 본문을 기준으로 JSON 구조화 요약을 생성한다.
8. 요약 결과와 언어 메타데이터를 DB에 저장한다.
9. 프론트는 저장된 요약을 기준 언어로 표시한다.

언어 감지 기준:

- 1차: LLM에 원문 언어 감지를 요청한다.
- 2차: 서버의 간단한 문자권 휴리스틱을 사용할 수 있다.
  - 한글 포함 비율이 높으면 `ko`
  - 히라가나/가타카나/일본어 한자 문맥이 있으면 `ja`
  - 라틴 알파벳 중심이면 `en`
- 감지 실패 시 `unknown`으로 기록한다.

감지 실패 정책:

- `sourceLanguage = unknown`이면 기준 언어로 번역을 시도한다.
- LLM이 이미 기준 언어라고 판단하면 번역 결과는 원문과 거의 동일할 수 있다.

## 19.29 번역 결과와 요약 결과의 관계

요약은 반드시 기준 언어로 생성한다.

원문 언어가 기준 언어와 다를 경우:

- 원문 메일 본문은 변경하지 않는다.
- 번역문은 요약 생성용 중간 데이터로 사용한다.
- 요약 결과는 번역문을 기반으로 생성한다.
- 기본 UI에는 번역문 전체를 표시하지 않는다.
- 필요 시 후속 기능으로 `번역문 보기`를 제공할 수 있다.

예:

```text
기준 언어: ko
메일 원문: 일본어

처리:
1. 일본어 메일 본문을 한국어로 번역
2. 한국어 번역문을 기반으로 일정/중요 포인트/요약/액션 아이템 추출
3. 한국어 JSON 요약 저장 및 표시
```

## 19.30 JSON 응답 스키마 확장

기존 요약 JSON 스키마는 유지하되, API 응답과 DB 저장 메타데이터에는 언어 정보를 추가한다.

요약 본문 JSON:

```json
{
  "schedule": {
    "date": "",
    "time": "",
    "location": "",
    "participants": "",
    "notes": ""
  },
  "keyPoints": [],
  "summary": "",
  "actionItems": [
    {
      "task": "",
      "time": ""
    }
  ]
}
```

API 메타데이터:

```json
{
  "summary_meta": {
    "target_language": "ko",
    "source_language": "ja",
    "translated": true,
    "generated_at": "2026-07-03T00:00:00.000Z",
    "updated_at": "2026-07-03T00:00:00.000Z",
    "summary_version": 1
  }
}
```

필드 의미:

- `target_language`
  - 제목행 언어 선택값에서 온 기준 언어.
- `source_language`
  - 감지된 메일 원문 언어.
- `translated`
  - 원문 언어와 기준 언어가 달라 번역을 수행했는지 여부.

## 19.31 DB 저장 확장

`mail_message_summaries` 테이블에 언어 관련 컬럼을 추가한다.

추가 컬럼:

```sql
ALTER TABLE mail_message_summaries
  ADD COLUMN IF NOT EXISTS target_language TEXT NOT NULL DEFAULT 'ko',
  ADD COLUMN IF NOT EXISTS source_language TEXT NOT NULL DEFAULT 'unknown',
  ADD COLUMN IF NOT EXISTS translated BOOLEAN NOT NULL DEFAULT false,
  ADD COLUMN IF NOT EXISTS translated_text TEXT NOT NULL DEFAULT '';
```

저장 정책:

- `summary_json`
  - 기준 언어로 생성된 최종 요약 JSON.
- `target_language`
  - 요약 생성 기준 언어.
- `source_language`
  - 메일 원문 감지 언어.
- `translated`
  - 번역 수행 여부.
- `translated_text`
  - 번역된 본문.
  - 기본 UI에는 표시하지 않는다.
  - 향후 `번역문 보기` 또는 디버깅에 사용할 수 있다.

저장 요약 조회 정책:

- 같은 메일이라도 기준 언어가 다르면 다른 요약으로 본다.
- 따라서 unique key는 기존 `(tenant_id, user_id, message_id)`에서 아래로 확장하는 것을 검토한다.

```sql
UNIQUE (tenant_id, user_id, message_id, target_language)
```

이렇게 하면 같은 일본어 메일에 대해 한국어 요약과 영어 요약을 각각 저장할 수 있다.

## 19.32 API 동작 변경

### 메일 상세 조회

`GET /mail/messages/:id`는 현재 기준 언어를 query로 받을 수 있다.

예:

```text
GET /mail/messages/:id?tenantId=...&targetLanguage=ko
```

서버는 해당 기준 언어로 저장된 요약을 조회한다.

- `targetLanguage=ko`이면 한국어 요약 조회
- `targetLanguage=en`이면 영어 요약 조회
- `targetLanguage=ja`이면 일본어 요약 조회

해당 언어의 저장 요약이 없으면 `summary: null`을 반환한다.

### 요약 생성 API

`POST /mail/messages/:id/summary`는 `targetLanguage`를 받는다.

예:

```json
{
  "tenantId": "tenant-id",
  "targetLanguage": "ko",
  "force": true
}
```

서버 동작:

1. `targetLanguage`를 검증한다.
2. 메일 원문 언어를 감지한다.
3. `sourceLanguage !== targetLanguage`이면 번역한다.
4. 번역된 텍스트 또는 원문 텍스트를 요약 입력으로 사용한다.
5. 요약 결과를 `targetLanguage` 기준으로 저장한다.
6. 응답에는 `summary`, `summary_meta`를 반환한다.

## 19.34 프론트 동작 변경

프론트는 제목행 언어 선택값을 메일 요약 API에 전달한다.

메일 상세 조회 시:

1. 현재 제목행 언어 선택값을 확인한다.
2. `GET /mail/messages/:id` 호출 시 `targetLanguage` query를 붙인다.
3. 해당 언어의 저장 요약이 있으면 즉시 표시한다.
4. 없으면 `요약` 버튼만 표시한다.

요약 생성 시:

1. 현재 제목행 언어 선택값을 `targetLanguage`로 전달한다.
2. 서버가 기준 언어로 요약을 생성한다.
3. 응답의 `summary_meta.translated`가 true이면 필요 시 UI에 작은 안내를 표시할 수 있다.

표시 예:

```text
일본어 메일을 한국어로 번역 후 요약했습니다.
```

단, 기본 UI에서는 과도한 설명을 피하고 요약 결과 자체를 우선 보여준다.

언어 선택이 변경될 때:

- 현재 열려 있는 메일의 상세 요약도 새 기준 언어에 맞춰 다시 조회한다.
- 해당 언어 요약이 저장되어 있으면 표시한다.
- 없으면 요약 패널을 숨기고 `요약` 버튼을 표시한다.

## 19.35 오류 및 fallback 정책

번역 실패 시:

- 요약 생성을 중단한다.
- 기존 저장 요약이 있으면 유지한다.
- 프론트에는 기준 언어 변환 실패 메시지를 표시한다.

예:

```text
메일을 기준 언어로 번역하지 못해 요약을 생성하지 못했습니다.
```

언어 감지 실패 시:

- `source_language = unknown`으로 저장한다.
- 기준 언어로 번역을 시도한다.
- 번역 결과가 비어 있으면 요약 생성을 중단한다.

요약 실패 시:

- DB에 실패 결과를 저장하지 않는다.
- 기존 저장 요약이 있으면 유지한다.

## 19.36 구현 우선순위

1차 구현:

- 프론트에서 제목행 언어 선택값을 요약 API에 전달
- `GET /mail/messages/:id`에 `targetLanguage` query 추가
- `POST /mail/messages/:id/summary`에 `targetLanguage` body 추가
- 서버에서 target language 검증 및 기본값 처리
- LLM prompt에 기준 언어 반영
- 원문 언어 감지
- 기준 언어와 다르면 번역 후 요약
- `mail_message_summaries`에 언어 메타데이터 저장
- 기준 언어별 저장 요약 조회

2차 구현:

- 번역문 보기 UI
- 지원 언어 추가
- 언어 감지 정확도 개선
- 사용자가 메일별 요약 언어를 수동 변경하는 기능
- 번역 결과 캐싱 및 재사용

## 19.37 5원칙 준수

1. 언어별 요약도 `tenant_id`, `user_id`, `account_id`, `message_id`, `target_language` 스코프를 가진다.
2. 언어별 요약 조회/저장 SQL은 `mailRepository` 내부에 둔다.
3. 라우트는 기준 언어 검증, 권한 확인, repository 호출만 담당한다.
4. 번역문과 요약문은 원본 메일 object storage와 분리된 AI 메타데이터다.
5. tenant DB 라우팅은 기존 `connectionManager`/`tenantQuery` 흐름을 따른다.

## 19.38 내장 LLM 요약 품질 개선 파이프라인

내장 LLM이 짧은 외국어 업무 메일을 요약할 때 모든 항목을 `확인된 내용 없음`으로 채우는 문제가 발생할 수 있다.

원인은 모델이 정보를 전혀 찾지 못해서라기보다, 한 번의 요청에서 아래 작업을 동시에 수행하도록 요구받기 때문이다.

- 원문 언어 감지
- 기준 언어 번역
- 업무 사실 추출
- JSON 스키마 맞춤
- 누락 정보 판단

작은 모델일수록 여러 작업을 한 번에 처리하면 실패 확률이 높다. 따라서 메일 요약은 단일 LLM 호출이 아니라 단계별 파이프라인으로 분리한다.

목표:

- 짧은 업무 메일에서도 `확인된 내용 없음` 남발을 줄인다.
- 번역 품질과 요약 품질을 분리해서 안정화한다.
- JSON 생성 전에 사실 추출 단계를 두어 모델이 놓친 정보를 줄인다.
- LLM 실패 시 규칙 기반 fallback으로 최소 품질을 보장한다.

## 19.39 개선된 처리 순서

메일 요약 생성은 아래 순서를 따른다.

```text
메일 원문
-> 본문 정제
-> 언어 감지
-> 기준 언어로 번역
-> 업무 사실 추출
-> JSON 요약 생성
-> 서버 검증/보정
-> DB 저장
-> UI 렌더링
```

단계별 책임:

1. 본문 정제
   - HTML, 스타일, 이전 메일 인용, 불필요한 공백을 제거한다.
2. 언어 감지
   - 메일 원문의 주 언어를 `ko/en/ja/unknown` 중 하나로 판단한다.
3. 기준 언어 번역
   - 원문 언어가 기준 언어와 다르면 기준 언어로 번역한다.
4. 업무 사실 추출
   - 번역문에서 확인 가능한 사실을 먼저 bullet 형태로 추출한다.
5. JSON 요약 생성
   - 추출된 사실 목록을 입력으로 사용해 JSON 스키마를 채운다.
6. 서버 검증/보정
   - JSON 파싱, 필수 필드, 타입, 빈 값 정책을 검증한다.
7. DB 저장
   - 기준 언어별 요약 결과와 메타데이터를 저장한다.

## 19.40 본문 정제 규칙

LLM에 원본 HTML 전체를 그대로 전달하지 않는다.

요약 입력은 아래 형태로 정리한다.

```text
[제목]
{{SUBJECT}}

[본문]
{{CLEAN_BODY_TEXT}}
```

제거 대상:

- `<style>`, `<script>` 등 HTML 제어 요소
- 메일 클라이언트가 삽입한 불필요한 태그
- 과도한 공백과 줄바꿈
- 이전 메일 인용문
- 자동 서명 중 반복적인 회사 정보
- 첨부파일 목록 중 본문 의미와 무관한 UI 텍스트

단, 아래 정보는 보존한다.

- 날짜
- 시간
- 장소
- 금액
- 계좌/계정/DHL 번호
- 회사명/담당자명
- 송금/입금/발송/확인 요청 문장

정제 예:

```text
Kevin 様

お世話になっております。
下記ご回答いただきありがとうございます。
いただいた内容で処理進めて参ります。
入金まで少々お待ちください。

引き続きよろしくお願いいたします。

平林
```

## 19.41 번역과 요약 분리

번역과 요약은 반드시 별도 단계로 처리한다.

나쁜 방식:

```text
이 일본어 메일을 한국어로 번역하고, 동시에 JSON으로 요약해줘.
```

좋은 방식:

1. 일본어 원문을 한국어로 번역한다.
2. 한국어 번역문을 요약 입력으로 사용한다.
3. 한국어 요약 JSON을 생성한다.

번역 전용 Prompt:

```text
다음 이메일 본문을 {{TARGET_LANGUAGE_NAME}}로 정확히 번역하세요.

규칙:
- 업무 메일의 의미를 유지하세요.
- 날짜, 시간, 금액, 장소, 고유명사, 계정 번호는 변경하지 마세요.
- 인사말은 자연스럽게 번역하세요.
- 번역문만 출력하세요.
```

번역 결과는 `translated_text`로 저장할 수 있지만 기본 UI에는 표시하지 않는다.

## 19.42 업무 사실 추출 단계

JSON 요약을 생성하기 전에 번역문에서 업무 사실을 먼저 추출한다.

이 단계의 출력은 JSON이 아니라 단순 bullet 목록이다. 작은 LLM은 복잡한 JSON보다 bullet 추출을 더 안정적으로 수행한다.

사실 추출 Prompt:

```text
다음 이메일에서 확인 가능한 업무 사실만 추출하세요.

규칙:
- 메일에 직접 적힌 내용 또는 직접 번역에서 확인 가능한 내용만 작성하세요.
- 추측하지 마세요.
- 날짜/시간이 없으면 "구체적인 날짜/시간 없음"이라고 쓰세요.
- 수신자가 해야 할 일이 없으면 "수신자의 추가 액션 없음"이라고 쓰세요.
- bullet 목록으로만 출력하세요.

[이메일]
{{TRANSLATED_BODY}}
```

예상 사실 추출 결과:

```text
- 이전 답변에 대한 감사 인사가 있음
- 받은 내용을 바탕으로 처리를 진행하겠다고 함
- 입금까지 조금 기다려 달라고 요청함
- 구체적인 날짜/시간은 없음
- 수신자의 추가 액션은 없음
```

이 사실 목록을 다음 JSON 요약 생성 단계의 입력으로 사용한다.

## 19.43 JSON 요약 생성 단계

JSON 요약 생성 단계는 원문 전체가 아니라 아래 입력을 사용한다.

```text
[기준 언어 번역문]
{{TRANSLATED_BODY}}

[업무 사실 목록]
{{FACT_LIST}}
```

JSON 생성 Prompt:

```text
아래 번역문과 업무 사실 목록을 기반으로 메일 요약 JSON을 생성하세요.

반드시 {{TARGET_LANGUAGE_NAME}}로만 작성하세요.
JSON 객체만 반환하세요.
Markdown, 설명 문장, 코드블록은 출력하지 마세요.

"확인된 내용 없음"은 해당 필드에 정말 정보가 없을 때만 사용하세요.
중요 포인트와 중요 내용 요약에는 업무 사실 목록의 내용을 반드시 반영하세요.

반환 스키마:
{
  "schedule": {
    "date": "",
    "time": "",
    "location": "",
    "participants": "",
    "notes": ""
  },
  "keyPoints": [],
  "summary": "",
  "actionItems": [
    {
      "task": "",
      "time": ""
    }
  ]
}
```

중요 규칙:

- `schedule`은 날짜/시간/장소/참석 정보가 있을 때만 채운다.
- `keyPoints`는 메일에서 확인된 핵심 업무 사실을 최소 1개 이상 포함한다.
- `summary`는 짧은 메일이라도 1~2문장 이상 작성한다.
- `actionItems`는 수신자가 해야 할 일이 없으면 `수신자의 추가 액션 없음` 또는 기준 언어에 맞는 표현으로 채운다.

## 19.44 "확인된 내용 없음" 사용 제한

`확인된 내용 없음`은 남발하면 안 된다.

사용 가능한 경우:

- 일정 날짜가 명시되어 있지 않음
- 장소가 명시되어 있지 않음
- 참석 대상이 명시되어 있지 않음
- 수신자가 해야 할 추가 작업이 없음

사용하면 안 되는 경우:

- 감사 인사, 처리 진행, 입금 대기 요청 등 명확한 업무 내용이 있음
- 날짜는 없지만 "입금까지 기다려 달라"는 요청이 있음
- 메일 전체의 목적이 명확함

예:

```text
入金まで少々お待ちください。
```

위 문장은 아래처럼 반영해야 한다.

```json
{
  "actionItems": [
    {
      "task": "입금 완료까지 대기",
      "time": "구체적인 날짜 없음"
    }
  ]
}
```

## 19.45 짧은 업무 메일 fallback 규칙

짧은 업무 메일은 LLM이 실패하더라도 규칙 기반 fallback으로 최소 요약을 생성한다.

대상:

- 본문 길이가 짧은 메일
- 일정 정보는 없지만 업무 상태 안내가 있는 메일
- 감사/확인/처리/입금/송금/발송/대기 표현이 있는 메일

일본어 업무 표현 예:

```text
ありがとうございます
いただいた内容で処理進めて参ります
入金まで少々お待ちください
引き続きよろしくお願いいたします
```

한국어 fallback 매핑 예:

```text
ありがとうございます
-> 감사 인사를 전달함

いただいた内容で処理進めて参ります
-> 제공받은 내용을 바탕으로 처리를 진행할 예정

入金まで少々お待ちください
-> 입금 완료까지 기다려 달라고 요청함
```

fallback 결과 예:

```json
{
  "schedule": {
    "date": "확인된 내용 없음",
    "time": "확인된 내용 없음",
    "location": "확인된 내용 없음",
    "participants": "확인된 내용 없음",
    "notes": "입금 완료까지 대기 요청"
  },
  "keyPoints": [
    "상대방이 이전 답변에 감사 인사를 전달함",
    "받은 내용을 바탕으로 내부 처리를 진행할 예정",
    "입금 완료까지 조금 기다려 달라고 요청함"
  ],
  "summary": "상대방이 이전 답변에 감사 인사를 전하며, 받은 내용을 바탕으로 처리를 진행하겠다고 안내했습니다. 입금이 완료될 때까지 조금 기다려 달라는 내용입니다.",
  "actionItems": [
    {
      "task": "입금 완료까지 대기",
      "time": "구체적인 날짜 없음"
    }
  ]
}
```

## 19.46 재시도 및 보정 전략

LLM 결과가 부실하면 바로 저장하지 않고 재시도한다.

부실 결과 판정:

- `keyPoints`가 `확인된 내용 없음` 하나뿐임
- `summary`가 `확인된 내용 없음`
- `actionItems`가 모두 `확인된 내용 없음`
- 번역문 또는 사실 목록에는 업무 내용이 있는데 JSON 요약에는 반영되지 않음

재시도 순서:

1. JSON 요약 생성 재시도
2. 사실 목록을 더 강하게 강조해 재시도
3. 짧은 업무 메일 fallback 적용
4. 그래도 실패하면 기존 기본 스키마 반환

재시도 Prompt 추가 문구:

```text
이전 결과가 너무 빈약했습니다.
업무 사실 목록에 있는 내용을 반드시 keyPoints, summary, actionItems에 반영하세요.
"확인된 내용 없음"은 일정/장소처럼 실제로 없는 필드에만 사용하세요.
```

## 19.47 DB 저장 메타데이터 확장

품질 개선 파이프라인의 각 단계 결과를 추적하기 위해 요약 메타데이터를 확장한다.

추가 저장 후보:

```sql
ALTER TABLE mail_message_summaries
  ADD COLUMN IF NOT EXISTS clean_body_text TEXT NOT NULL DEFAULT '',
  ADD COLUMN IF NOT EXISTS fact_list_json JSONB NOT NULL DEFAULT '[]',
  ADD COLUMN IF NOT EXISTS pipeline_version TEXT NOT NULL DEFAULT 'mail-summary-pipeline-v2',
  ADD COLUMN IF NOT EXISTS fallback_used BOOLEAN NOT NULL DEFAULT false,
  ADD COLUMN IF NOT EXISTS quality_flags JSONB NOT NULL DEFAULT '[]';
```

필드 의미:

- `clean_body_text`
  - HTML/인용문/서명을 제거한 요약 입력 본문.
- `fact_list_json`
  - 업무 사실 추출 단계의 결과.
- `pipeline_version`
  - 요약 생성 파이프라인 버전.
- `fallback_used`
  - LLM 실패 후 규칙 기반 fallback을 사용했는지 여부.
- `quality_flags`
  - `empty_summary_retry`, `fallback_short_mail`, `translation_failed` 같은 품질 플래그.

기본 UI에는 이 메타데이터를 노출하지 않는다.

## 19.48 구현 우선순위

1차 구현:

- 메일 본문 정제 함수 강화
- 번역 단계와 JSON 요약 단계를 분리
- 업무 사실 추출 단계 추가
- JSON 생성 prompt에 사실 목록 반영
- `확인된 내용 없음` 사용 제한 prompt 적용
- 부실 결과 판정 로직 추가
- 부실 결과 시 1회 재시도

2차 구현:

- 짧은 업무 메일 fallback 규칙 추가
- 일본어/영어 업무 표현 사전 확장
- `fact_list_json`, `quality_flags`, `fallback_used` 저장
- 관리자용 품질 디버그 로그 제공
- 번역문 보기 UI 제공

## 19.49 5원칙 준수

1. 품질 개선 파이프라인 결과도 `mail_message_summaries`의 tenant/user/message/language 스코프 안에 저장한다.
2. 파이프라인 메타데이터 저장 SQL은 `mailRepository` 내부에 둔다.
3. 라우트는 파이프라인 실행 요청과 응답 전달만 담당한다.
4. 정제 본문, 번역문, 사실 목록은 원본 메일을 변경하지 않는 AI 메타데이터다.
5. tenant DB 라우팅은 기존 `connectionManager`/`tenantQuery` 흐름을 따른다.

## 19.50 요약 복사 버튼 안정화

메일 상세 화면의 `요약 복사` 버튼은 요약 결과를 일반 텍스트로 변환한 뒤 클립보드에 복사한다.

현재 장애 원인 분석:

- 요약 내용은 화면에 정상 표시되므로 요약 데이터 자체가 비어 있는 문제일 가능성은 낮다.
- 복사 버튼은 `navigator.clipboard.writeText`에만 의존하고 있다.
- `navigator.clipboard.writeText`는 브라우저 보안 정책에 따라 실패할 수 있다.
- HTTP 접속, 일부 WebView, iframe, 브라우저 권한 차단, Safari 계열 환경에서는 Clipboard API가 없거나 거부될 수 있다.
- 현재 구현은 Clipboard API가 없으면 즉시 `return`하고, 실패해도 사용자에게 실패 사유를 보여주지 않는다.
- 다른 화면의 복사 기능은 `textarea + document.execCommand('copy')` fallback을 가지고 있으나, 메일 요약 복사에는 fallback이 없다.

해결 방향:

1. `formatMailSummaryForCopy(summary)`로 복사할 문자열을 먼저 만든다.
2. 복사 문자열이 비어 있으면 버튼을 비활성화하거나 안내 메시지를 표시한다.
3. 1차로 `navigator.clipboard.writeText(text)`를 시도한다.
4. Clipboard API가 없거나 실패하면 `textarea` 임시 엘리먼트를 사용해 `document.execCommand('copy')` fallback을 수행한다.
5. fallback까지 실패하면 조용히 무시하지 않고 사용자에게 `복사에 실패했습니다. 직접 선택해 복사해주세요.` 같은 안내를 표시한다.
6. 성공 시에는 기존처럼 버튼 문구를 `복사됨`으로 잠시 변경한다.

권장 공통 함수:

```js
async function copyTextWithFallback(text) {
  const normalized = String(text || '').trim()
  if (!normalized) return false

  try {
    if (navigator?.clipboard?.writeText) {
      await navigator.clipboard.writeText(normalized)
      return true
    }
  } catch {
    // fallback으로 진행
  }

  try {
    const textarea = document.createElement('textarea')
    textarea.value = normalized
    textarea.setAttribute('readonly', '')
    textarea.style.position = 'fixed'
    textarea.style.left = '-9999px'
    textarea.style.opacity = '0'
    document.body.appendChild(textarea)
    textarea.select()
    const copied = document.execCommand('copy')
    document.body.removeChild(textarea)
    return copied
  } catch {
    return false
  }
}
```

메일 요약 복사 적용 기준:

- `copySummary()`는 `navigator.clipboard` 존재 여부로 조기 반환하지 않는다.
- `copyTextWithFallback(formatMailSummaryForCopy(summary))` 형태로 호출한다.
- 성공하면 `summaryCopied=true`로 바꾸고 1.8초 후 원복한다.
- 실패하면 `summaryError` 또는 별도 toast 상태를 사용해 복사 실패를 안내한다.
- 모델명, raw JSON, 내부 메타데이터는 복사하지 않는다.
- 복사 내용 순서는 화면 요약 순서와 동일하게 유지한다.

복사 텍스트 형식:

```text
일정:
- 날짜: ...
- 시간: ...
- 장소: ...
- 참석 대상: ...
- 비고: ...

중요 포인트
- ...

중요 내용 요약
...

액션 아이템 / 시간
- ... (...)
```

5원칙 적용:

1. 복사 기능은 프론트 UI 동작이므로 DB 스키마를 변경하지 않는다.
2. 요약 원본은 이미 저장된 `summary_json`을 사용하고, 복사 시점에만 텍스트로 변환한다.
3. 라우트/API는 변경하지 않는다.
4. 복사 실패는 원본 메일과 요약 저장 상태에 영향을 주지 않는다.
5. 같은 복사 fallback 로직은 다른 화면과 공통 유틸로 재사용할 수 있다.

## 19.51 액션 아이템 날짜/시간 보정 및 캘린더 등록

메일 요약의 `액션 아이템 / 시간` 영역에서 LLM이 시간 정보를 찾지 못해 `확인된 내용 없음`으로 표시되는 경우가 있다.

이 경우 사용자가 직접 날짜와 시간을 선택하여 액션 아이템의 시간을 보정할 수 있게 한다.

### 목적

- LLM이 추출하지 못한 날짜/시간을 사용자가 직접 보완한다.
- 보완된 날짜/시간은 화면의 `확인된 내용 없음` 값을 대체한다.
- 날짜/시간이 선택되면 해당 액션 아이템을 캘린더 일정으로 등록한다.
- 메일 요약과 캘린더가 연결되어, 메일에서 나온 업무를 일정으로 바로 전환할 수 있게 한다.

### UI 표시 기준

`액션 아이템 / 시간` 목록의 각 action item은 아래 구조로 표시한다.

```text
입금 처리가 완료될 때까지 대기        [확인된 내용 없음 ▼]  [캘린더 등록됨]
```

표시 규칙:

- action item row에는 날짜 선택, 하루종일 스위치, 시간 선택 컨트롤을 항상 펼쳐서 노출하지 않는다.
- row 오른쪽에는 현재 시간 표시값을 담은 작은 버튼/드롭다운 트리거를 표시한다.
  - 예: `확인된 내용 없음 ▼`, `2026-07-05 ▼`, `2026-07-05 14:00 ▼`
- 사용자가 시간 표시 버튼을 클릭하면 펼침 메뉴(popover/dropdown)를 열고, 그 안에 날짜 선택/하루종일/시간 선택 컨트롤을 배치한다.
- 메뉴 밖의 row 본문은 업무 내용과 현재 시간값, 저장/등록 상태를 빠르게 스캔할 수 있게 유지한다.
- 기준 언어가 영어/일본어이면 해당 언어의 no-info 값에도 동일하게 적용한다.
  - 한국어: `확인된 내용 없음`
  - 영어: `No confirmed information`
  - 일본어: `確認できる内容なし`
- 이미 명확한 날짜/시간이 있는 action item도 같은 펼침 메뉴를 통해 수정할 수 있다.
- `calendarEventId`가 있으면 `캘린더 등록됨` 버튼/링크를 시간 드롭다운과 별도로 표시한다.

### 날짜/시간 선택 컨트롤

컨트롤:

- 날짜 선택: `<input type="date">`
- 하루종일: switch/checkbox 형태의 토글
- 시간 선택: `<input type="time">`

기본값:

- 날짜 기본값은 비워둔다.
- 시간 기본값은 비워둔다.
- 날짜만 선택된 경우 기본 시간은 정하지 않는다.
- 캘린더 등록은 날짜와 시간이 모두 선택된 경우에만 자동 수행한다.

표시 위치:

- action item row의 오른쪽 끝에는 현재 시간 표시 버튼만 배치한다.
- 날짜 선택, 하루종일 스위치, 시간 선택은 시간 표시 버튼 아래 펼침 메뉴 안에 배치한다.
- 펼침 메뉴는 row 위를 과도하게 밀어내지 않는 작은 폭으로 표시한다.
- 모바일에서는 펼침 메뉴가 화면 폭을 넘지 않도록 row 아래에 맞춰 표시한다.
- 선택 컨트롤은 작은 크기로 유지하여 action item 본문과 캘린더 등록 상태를 가리지 않는다.

예시:

```text
액션 아이템 / 시간

[업무 내용]                              [시간]              [보정]
입금 처리가 완료될 때까지 대기             2026-07-06 ▼        캘린더 등록됨

펼침 메뉴:
- 날짜 선택: 2026-07-06
- 하루종일: 켜짐
- 시간 선택: 비활성
```

### 선택 후 화면 반영

사용자가 날짜와 시간을 모두 선택하면:

1. `actionItems[n].time`의 화면 표시 값을 선택한 날짜/시간 문자열로 교체한다.
2. 날짜/시간 선택 컨트롤은 숨기거나, 선택된 값을 수정할 수 있는 상태로 유지한다.
3. 선택 결과는 메일 요약 상태에 반영한다.
4. 가능하면 DB에 저장된 `summary_json`도 업데이트하여 다음에 해당 메일을 열어도 보정된 시간이 유지되게 한다.

표시 형식:

```text
2026-07-06 14:00
```

기준 언어별 표시 형식:

- 한국어: `2026-07-06 14:00`
- 영어: `2026-07-06 14:00`
- 일본어: `2026-07-06 14:00`

날짜/시간은 데이터 처리 안정성을 위해 ISO에 가까운 고정 형식을 사용한다.

### 캘린더 등록 조건

날짜와 시간이 모두 선택되면 해당 액션 아이템을 캘린더에 추가한다.

캘린더 이벤트 생성 기준:

- 제목:
  - action item의 `task`
  - 예: `입금 처리가 완료될 때까지 대기`
- 시작 시간:
  - 사용자가 선택한 날짜 + 시간
- 종료 시간:
  - 기본값: 시작 시간 + 30분
  - 추후 설정 가능하게 확장 가능
- 설명:
  - 메일 제목
  - 보낸 사람
  - 원본 메일 수신 시간
  - 요약의 `중요 내용 요약`
  - 원본 메일 상세로 돌아갈 수 있는 내부 링크 또는 message id
- 출처:
  - `source_type = mail_summary_action_item`
  - `source_message_id = mail_messages.id`
  - `source_summary_id = mail_message_summaries.id`
  - `source_action_index = action item index`

예시 캘린더 이벤트:

```json
{
  "title": "입금 처리가 완료될 때까지 대기",
  "start_at": "2026-07-06T14:00:00+09:00",
  "end_at": "2026-07-06T14:30:00+09:00",
  "description": "메일에서 생성된 액션 아이템입니다.\n제목: ...\n보낸 사람: ...",
  "source_type": "mail_summary_action_item",
  "source_message_id": "...",
  "source_action_index": 0
}
```

### 중복 등록 방지

같은 action item에서 날짜/시간을 여러 번 선택할 수 있으므로 중복 등록을 방지해야 한다.

중복 방지 기준:

- 같은 `tenant_id`
- 같은 `user_id`
- 같은 `message_id`
- 같은 `summary_id`
- 같은 `action_index`

위 값이 같은 캘린더 이벤트가 이미 있으면 새로 생성하지 않고 기존 이벤트를 업데이트한다.

수정 동작:

- 기존 캘린더 이벤트가 없으면 생성한다.
- 기존 캘린더 이벤트가 있으면 시작/종료 시간과 제목/설명을 업데이트한다.

### DB 저장 확장

메일 요약 JSON 자체에도 사용자가 보정한 날짜/시간을 저장한다.

권장 action item 구조:

```json
{
  "task": "입금 처리가 완료될 때까지 대기",
  "time": "2026-07-06 14:00",
  "timeSource": "user",
  "calendarEventId": "calendar-event-id"
}
```

필드 의미:

- `time`
  - 화면에 표시할 시간 문자열.
- `timeSource`
  - `llm`: LLM이 추출한 시간
  - `user`: 사용자가 직접 선택한 시간
  - `none`: 확인된 시간이 없음
- `calendarEventId`
  - 해당 action item으로 생성/업데이트된 캘린더 이벤트 ID.

기존 요약 구조와 호환성을 위해 `task`, `time`은 유지한다.

### API 설계

프론트는 날짜/시간 선택 후 별도 API를 호출한다.

권장 API:

```http
PATCH /api/mail/messages/:messageId/summary/action-items/:actionIndex/time
```

요청 body:

```json
{
  "tenantId": "tenant-id",
  "targetLanguage": "ko",
  "date": "2026-07-06",
  "time": "14:00",
  "createCalendarEvent": true
}
```

서버 처리:

1. tenant/user/message 접근 권한 확인
2. 해당 언어의 저장된 메일 요약 조회
3. action item index 유효성 확인
4. `summary_json.actionItems[actionIndex].time` 업데이트
5. `timeSource = user` 저장
6. 캘린더 이벤트 생성 또는 업데이트
7. `calendarEventId`를 action item에 저장
8. 갱신된 summary JSON 반환

응답:

```json
{
  "ok": true,
  "summary": {},
  "calendarEvent": {
    "id": "calendar-event-id",
    "start_at": "2026-07-06T14:00:00+09:00",
    "end_at": "2026-07-06T14:30:00+09:00"
  }
}
```

### 프론트 동작 흐름

1. `MailSummaryPanel`에서 각 action item을 렌더링한다.
2. `item.time`이 no-info 값이면 날짜/시간 선택 컨트롤을 표시한다.
3. 사용자가 날짜와 시간을 모두 선택하면 API를 호출한다.
4. API 응답의 `summary`로 화면 summary state를 갱신한다.
5. 캘린더 이벤트 생성 성공 시 작은 성공 메시지를 표시한다.
6. 실패 시 action item row 하단에 오류 메시지를 표시하고 선택값은 유지한다.

성공 메시지 예:

```text
캘린더에 추가했습니다.
```

실패 메시지 예:

```text
캘린더 등록에 실패했습니다. 다시 시도해주세요.
```

### 캘린더 서비스 연동 원칙

- 메일 요약 UI는 캘린더 DB에 직접 접근하지 않는다.
- 캘린더 등록은 서버 API를 통해 수행한다.
- 서버는 기존 캘린더 서비스/Repository가 있으면 해당 레이어를 사용한다.
- 캘린더 서비스가 아직 없다면 별도 Calendar Repository를 먼저 정의한다.
- 메일 요약 테이블은 캘린더 이벤트의 ID만 참조한다.

### 5원칙 준수

1. 메일 요약 action item 보정은 `tenant_id`, `user_id`, `message_id`, `target_language` 범위 안에서만 수행한다.
2. 요약 JSON 갱신 SQL은 `mailRepository`에 둔다.
3. 캘린더 이벤트 생성/업데이트 SQL은 캘린더 Repository에 둔다.
4. 라우트는 권한 확인, 서비스 호출, 응답 반환만 담당한다.
5. 원본 메일 본문은 수정하지 않고, 사용자 보정값은 AI 요약 메타데이터와 캘린더 이벤트로만 저장한다.

## 19.52 메일 상세 화면 전체 단일 스크롤

### 19.52.1 배경 / 문제

현재 메일 상세 화면에서 헤더, 본문, 하단 액션 영역이 각각 다른 스크롤/고정 영역으로 나뉘면 사용자가 메일 전체를 한 흐름으로 읽기 어렵다.

특히 다음 상황에서 사용성이 떨어진다.

- 제목/보낸 사람/받는 사람/날짜 헤더가 고정되고 본문 일부만 스크롤된다.
- 요약 패널에 일정, 중요 포인트, 액션 아이템이 모두 표시된다.
- 액션 아이템에 날짜/시간 선택 컨트롤까지 표시된다.
- 메일 본문에 첨부파일 목록이 함께 표시된다.
- 하단 답장/전달 버튼이 고정되어 본문 영역 일부를 계속 차지한다.

사용자 기대 동작은 다음이다.

- 제목/메타데이터, 요약 패널, 원본 메일 본문, 첨부파일, 답장/전달 버튼이 하나의 읽기 흐름으로 보여야 한다.
- 메일 상세 화면의 스크롤은 메일 본문 영역 전체를 커버해야 한다.
- 헤더나 하단 액션만 별도 고정되어 본문 스크롤 영역을 압박하면 안 된다.

### 19.52.2 UI 배치 정책

메일 상세 화면은 아래 콘텐츠를 모두 같은 스크롤 흐름에 둔다.

1. 제목
2. 보낸 사람 / 받는 사람 / 참조 / 날짜
3. 요약 생성 / 요약 복사 버튼
4. AI 요약 패널
5. 원본 메일 본문
6. 첨부파일 목록
7. 전달 / 전체 답장 / 답장 버튼

즉, `MailViewer` 내부에 본문 전용 `overflow-auto` 영역을 만들지 않고, 바깥 메일 상세 패널의 단일 스크롤 컨테이너가 전체 콘텐츠를 스크롤한다.

### 19.52.3 렌더링 구조

권장 구조:

```text
MailViewer
├─ Header
│  ├─ subject
│  ├─ metadata
│  └─ summary buttons
├─ SummaryPanel (있을 때만)
├─ MailBody
├─ Attachments
└─ FooterActions
```

현재 구조처럼 Header 안에 SummaryPanel을 넣지 않는다.
또한 Header/Footer를 `flex-shrink-0` 고정 영역으로 두고 중간 `ScrollBody`만 스크롤하지 않는다.

잘못된 구조:

```text
Header
├─ subject
├─ metadata
├─ buttons
└─ SummaryPanel   ← 고정 영역을 키워 본문을 압박함
```

수정 구조:

```text
MailViewer
├─ Header
│  ├─ subject
│  ├─ metadata
│  └─ buttons
├─ SummaryPanel
├─ MailBody
├─ Attachments
└─ FooterActions
```

### 19.52.4 스크롤 동작

통합 스크롤 영역은 하나만 둔다.

- 오른쪽 메일 상세 패널의 바깥 컨테이너가 `overflow-y-auto`를 담당한다.
- `MailViewer` 내부에는 별도의 `flex-1 overflow-auto` 본문 영역을 만들지 않는다.
- Header, SummaryPanel, MailBody, Attachments, FooterActions는 모두 일반 블록 흐름으로 배치한다.
- Header와 Footer에 고정/축소 방지용 `flex-shrink-0`을 적용해 중간 영역만 스크롤되게 만들지 않는다.

요약 패널은 Header 아래, 원본 메일 본문 위에 일반 콘텐츠 블록으로 들어간다.

결과:

- 헤더가 길어도 사용자가 아래로 스크롤하면 헤더도 함께 올라간다.
- 요약 패널이 길면 사용자가 아래로 스크롤하면서 본문으로 자연스럽게 이동한다.
- 본문이 길어도 동일한 스크롤바로 읽는다.
- 하단 답장/전달 버튼은 본문 끝에 도달했을 때 나타난다.
- 본문 iframe 또는 plain text 영역이 요약 패널 때문에 작은 고정 영역에 갇히지 않는다.

### 19.52.5 HTML 메일 iframe 처리

HTML 메일 본문을 iframe으로 표시하는 경우에도 메일 상세 단일 스크롤 흐름 안에서 자연스럽게 배치해야 한다.

권장:

- iframe을 별도 `flex-1 overflow-auto` 영역으로 강제하지 않는다.
- iframe은 본문 콘텐츠 블록으로 표시한다.
- 최소 높이는 유지하되, 요약 패널과 같은 스크롤 흐름 안에 들어간다.
- HTML 메일 iframe은 내부 문서의 `scrollHeight`를 읽어 iframe 높이를 본문 콘텐츠 높이에 맞춘다.
- iframe 내부 `html`, `body`의 `overflow`는 숨겨서 iframe 자체 스크롤바가 생기지 않게 한다.
- iframe sandbox는 스크립트를 허용하지 않되, 높이 계산을 위해 필요한 경우 `allow-same-origin`만 추가할 수 있다.

예:

```text
MailViewer
├─ Header
├─ SummaryPanel
├─ iframe mail body
├─ AttachmentList
└─ FooterActions
```

주의:

- iframe 내부 문서가 별도 스크롤을 가지면 요약본과 본문이 분리 스크롤되는 문제가 재발한다.
- 외부 메일 상세 스크롤과 iframe 내부 스크롤이 이중으로 겹치면 안 된다.
- 높이 계산에 실패한 경우에만 최소 높이 fallback을 사용하되, 기본 정책은 iframe을 콘텐츠 높이에 맞춰 늘리는 것이다.

### 19.52.6 첨부파일 영역

첨부파일 목록도 메일 본문과 같은 흐름에 둔다.

정책:

- 첨부파일은 본문 하단에 표시한다.
- 첨부파일 영역만 별도 고정 하단 영역으로 빼지 않는다.
- 본문과 첨부파일이 메일 상세 단일 스크롤 흐름 안에서 함께 스크롤되게 한다.

### 19.52.7 검증 기준

다음 시나리오를 확인한다.

1. AI 요약이 있는 메일을 연다.
2. 제목/메타데이터 헤더가 별도 고정되지 않고 메일 상세 스크롤과 함께 움직인다.
3. 화면의 스크롤을 내리면 헤더, 요약 패널, 메일 본문, 첨부파일, 하단 액션이 같은 스크롤 흐름으로 이동한다.
4. 요약 패널이 길어도 메일 본문 영역이 지나치게 작아지지 않는다.
5. 요약이 없는 메일은 기존처럼 본문이 바로 표시된다.
6. 답장/전달 버튼 영역은 본문 끝 하단에서 사용할 수 있고 별도 고정 영역으로 본문을 가리지 않는다.
7. HTML 메일과 plain text 메일 모두 레이아웃이 깨지지 않는다.
8. HTML 메일 iframe 내부에는 별도 세로 스크롤바가 생기지 않고, 요약본과 본문이 바깥 메일 상세 스크롤 하나로 함께 이동한다.

### 19.52.8 구현 원칙

- 요약 데이터 저장/API 구조는 변경하지 않는다.
- 변경 범위는 `MailViewer`의 레이아웃 배치와 스크롤 컨테이너 구조로 제한한다.
- `MailSummaryPanel` 자체의 내용 구조는 유지한다.
- 요약 생성/복사 버튼은 헤더에 남기되, 헤더 자체는 고정하지 않는다.
- 요약 결과 패널은 Header 아래 일반 콘텐츠 블록으로 배치한다.

## 19.53 액션 아이템 하루종일 스위치

### 19.53.1 배경 / 목적

메일 요약의 `액션 아이템 / 시간` 영역에서 사용자가 날짜와 시간을 직접 보정할 때, 모든 일정이 특정 시각을 필요로 하지는 않는다.

예를 들어 다음과 같은 액션은 특정 시간이 아니라 해당 날짜 전체에 걸친 업무로 보는 것이 자연스럽다.

- 문서 검토
- 자료 회신
- 입금 처리 대기
- 계약서 확인
- 내부 검토 후 의견 전달

따라서 액션 아이템의 날짜 선택 컨트롤과 시간 선택 컨트롤 사이에 `하루종일` 슬라이드 스위치를 추가한다.

### 19.53.2 UI 배치

각 액션 아이템 row의 오른쪽 시간 보정 영역은 아래 순서로 표시한다.

```text
[현재 저장된 시간 표시] [날짜 선택] [하루종일 스위치] [시간 선택]
```

예시:

```text
2026-07-05 05:49   [2026. 07. 05.]   [하루종일 ON/OFF]   [오전 05:49]
```

표시 정책:

- `하루종일` 스위치는 날짜 선택과 시간 선택 사이에 둔다.
- 스위치 레이블은 기준 언어에 맞춰 표시한다.
  - 한국어: `하루종일`
  - 영어: `All day`
  - 일본어: `終日`
- 모바일 또는 좁은 화면에서는 날짜, 스위치, 시간 컨트롤이 줄바꿈되어도 액션 아이템 내용과 겹치지 않아야 한다.

### 19.53.3 하루종일 동작

`하루종일`이 꺼져 있는 경우:

- 날짜 선택 컨트롤을 활성화한다.
- 시간 선택 컨트롤을 활성화한다.
- 날짜와 시간이 모두 선택되면 기존처럼 특정 시각 일정으로 캘린더에 등록한다.
- 저장 표시값은 `YYYY-MM-DD HH:mm` 형식을 사용한다.

`하루종일`이 켜져 있는 경우:

- 날짜 선택 컨트롤은 활성화한다.
- 시간 선택 컨트롤은 비활성화한다.
- 비활성화된 시간 컨트롤은 흐리게 표시하되, 기존 선택 시간이 있었다면 화면에는 유지해도 된다.
- 캘린더에는 하루종일 이벤트로 등록한다.
- 저장 표시값은 날짜 중심으로 표시한다.

하루종일 표시 예:

```text
2026-07-05 하루종일
```

### 19.53.4 저장 데이터 구조

액션 아이템에는 사용자가 보정한 시간이 특정 시각인지 하루종일인지 구분할 수 있는 값을 저장한다.

권장 구조:

```json
{
  "text": "첨부된 계약서 초안을 검토하고 의견을 제시할 것.",
  "time": "2026-07-05",
  "timeSource": "user",
  "isAllDay": true,
  "calendarEventId": "calendar-event-id"
}
```

특정 시각 일정 예:

```json
{
  "text": "7월 7일 저녁에 이성환 법인장과 미팅할 것.",
  "time": "2026-07-07 18:00",
  "timeSource": "user",
  "isAllDay": false,
  "calendarEventId": "calendar-event-id"
}
```

정책:

- `isAllDay`는 기본값 `false`로 본다.
- 기존 요약 데이터에 `isAllDay`가 없는 경우 일반 시간 일정으로 해석한다.
- 하루종일로 전환하면 `time`에는 날짜만 저장하거나, 별도 `date` 필드를 둘 수 있다.
- 기존 특정 시간이 있던 액션을 하루종일로 바꾸더라도 사용자가 다시 끌 때 이전 시간을 복원할 수 있도록 프론트 상태에는 마지막 선택 시간을 유지하는 것이 좋다.

### 19.53.5 API 요청

기존 액션 아이템 시간 보정 API에 `isAllDay` 값을 함께 전달한다.

요청 예:

```json
{
  "targetLanguage": "ko",
  "actionIndex": 0,
  "date": "2026-07-05",
  "time": null,
  "isAllDay": true,
  "createCalendarEvent": true
}
```

특정 시각 일정 요청 예:

```json
{
  "targetLanguage": "ko",
  "actionIndex": 0,
  "date": "2026-07-05",
  "time": "05:49",
  "isAllDay": false,
  "createCalendarEvent": true
}
```

서버 처리:

1. `isAllDay` 값을 검증한다.
2. `isAllDay = true`이면 `time`이 없어도 날짜만으로 저장을 허용한다.
3. `isAllDay = false`이면 날짜와 시간이 모두 있어야 캘린더 등록을 수행한다.
4. 저장된 summary JSON의 action item에 `time`, `timeSource`, `isAllDay`, `calendarEventId`를 반영한다.
5. 기존 캘린더 이벤트가 있으면 하루종일 여부까지 함께 업데이트한다.

### 19.53.6 캘린더 등록 정책

하루종일 이벤트:

- 시작일: 선택한 날짜
- 종료일: 선택한 날짜 다음 날 0시 또는 캘린더 서비스가 요구하는 all-day 종료일 규칙
- `all_day = true`
- 시간 선택값은 캘린더 이벤트에 반영하지 않는다.

특정 시각 이벤트:

- 시작 시간: 선택한 날짜 + 시간
- 종료 시간: 기본 30분 뒤
- `all_day = false`

캘린더 메모에는 기존 정책대로 메일 요약 설명과 원본 메일 링크를 포함한다.

### 19.53.7 수정 동작

이미 캘린더에 등록된 액션 아이템도 날짜, 하루종일 스위치, 시간 컨트롤을 계속 표시한다.

수정 규칙:

- 날짜를 바꾸면 summary DB와 캘린더 이벤트를 함께 업데이트한다.
- `하루종일`을 켜면 시간 컨트롤을 비활성화하고 캘린더 이벤트를 하루종일 이벤트로 변경한다.
- `하루종일`을 끄면 시간 컨트롤을 다시 활성화한다.
- 시간이 비어 있으면 사용자가 시간을 선택하기 전까지 캘린더 이벤트 업데이트를 보류하거나 기본 시간을 적용한다.
- 이미 등록된 `calendarEventId`가 있으면 새 이벤트를 만들지 않고 기존 이벤트를 업데이트한다.

### 19.53.8 검증 기준

다음 시나리오를 확인한다.

1. 액션 아이템 row에 날짜 선택, 하루종일 스위치, 시간 선택 컨트롤이 순서대로 표시된다.
2. `하루종일`을 켜면 시간 선택 컨트롤이 비활성화된다.
3. `하루종일`을 켠 상태에서 날짜만 선택해도 summary DB에 저장된다.
4. `하루종일`을 켠 상태에서 캘린더에는 하루종일 이벤트로 등록된다.
5. `하루종일`을 끄면 시간 선택 컨트롤이 다시 활성화된다.
6. 날짜 또는 하루종일 값을 수정하면 기존 캘린더 이벤트가 업데이트된다.
7. 다른 메일을 열었다가 다시 돌아와도 `isAllDay`, 날짜, 시간, 캘린더 등록 상태가 유지된다.
8. 기준 언어를 바꾸면 `하루종일` 레이블도 기준 언어로 표시된다.

## 19.54 액션 아이템 수정 시 캘린더 동기화 및 제목 정책

### 19.54.1 배경 / 목적

메일 요약의 `액션 아이템 / 시간`에서 날짜, 시간, `하루종일` 값을 수정하면 화면의 요약 정보만 바뀌면 안 된다.

사용자가 이미 캘린더에 등록한 액션 아이템을 다시 수정하는 경우, 연결된 캘린더 이벤트도 같은 값으로 갱신되어야 한다.

또한 캘린더 이벤트 제목이 액션 아이템 문구로 생성되면 캘린더 화면에서 어떤 메일에서 나온 일정인지 바로 알기 어렵다.

따라서 메일에서 생성되는 캘린더 이벤트의 제목은 **메일 제목**을 기준으로 한다.

### 19.54.2 캘린더 제목 정책

메일 요약 액션 아이템에서 생성되는 캘린더 이벤트 제목은 다음 우선순위로 정한다.

1. 원본 메일 제목
2. 메일 제목이 비어 있으면 액션 아이템 내용
3. 둘 다 없으면 `메일 액션 아이템`

예시:

```text
[GT System Vietnam] AI 솔루션 베트남 영업 대리점 계약서 초안 송부의 건
```

정책:

- 액션 아이템 문구는 캘린더 이벤트 제목으로 사용하지 않고 메모에 포함한다.
- 같은 메일에서 여러 액션 아이템이 캘린더에 등록되더라도 제목은 동일한 메일 제목을 사용한다.
- 캘린더 이벤트의 상세 메모에서 어떤 액션 아이템인지 구분한다.

### 19.54.3 캘린더 메모 정책

캘린더 이벤트 메모에는 다음 정보를 포함한다.

```text
메일 요약 액션 아이템에서 생성된 일정입니다.
제목: {메일 제목}
액션 아이템: {액션 아이템 내용}
보낸 사람: {보낸 사람}
메일 날짜: {메일 수신/발신 날짜}
요약: {메일 요약}

원본 메일 링크:
{메일 상세 화면으로 돌아가는 링크}
```

중요:

- 캘린더 제목은 메일 제목으로 단순하게 유지한다.
- 액션 아이템의 실제 업무 내용은 메모에 넣는다.
- 저장 데이터의 메모 하단에는 기존 정책처럼 원본 메일 링크를 유지한다.
- 캘린더 이벤트 편집/상세 UI에서는 원본 메일 링크를 메모 입력 박스 안에 그대로 노출하지 않는다.
- UI는 메모 문자열에서 `원본 메일 링크:` 블록과 URL을 감지하여 메모 입력 박스 밖 하단에 별도 링크로 표시한다.
- 별도 링크의 표시 문구는 `원본으로 이동`으로 한다.
- `원본으로 이동`을 클릭하면 같은 창에서 메일 화면을 열고, 해당 메일을 선택한 뒤 상세 본문 API까지 호출하여 제목/보낸 사람/첨부파일/본문이 오른쪽 상세 패널에 표시되어야 한다.
- 메일 화면으로 이동할 때는 상세 응답의 `account_id`와 `folder_id`를 기준으로 해당 메일이 속한 실제 계정/폴더를 활성화한다.
- 폴더 목록을 다시 불러오는 과정에서 해당 메일이 첫 페이지 목록에 없더라도, 딥링크로 불러온 상세 메일을 목록에 유지하고 선택 상태를 보존해야 한다.
- 결과적으로 왼쪽 메일 목록에서 해당 메일 row가 선택된 상태로 보여야 하며, 오른쪽 상세 패널에는 로딩 상태가 끝난 뒤 메일 본문이 표시되어야 한다.
- 딥링크 처리는 `messageId`, `tenantId`, `targetLanguage`, 클릭 시각/실행 토큰을 포함한 단위로 처리하여, 같은 원본 메일 링크를 반복 클릭해도 다시 상세 로딩을 시도할 수 있어야 한다.
- 상세 API 호출이 성공하기 전에 딥링크를 처리 완료로 고정하면 안 된다. 실패하거나 중단된 경우 다음 클릭에서 재시도할 수 있어야 한다.
- 상세 API 응답을 받은 뒤 폴더 전환이 발생하면, 폴더 목록 재조회가 끝날 때까지 상세 응답 객체를 보존하고 `selectedMessage`와 `selectedMessageIds`를 다시 적용한다.
- 폴더 목록 재조회 중 보존 대상 메일이 있으면 기존 선택 초기화 로직보다 보존 로직이 우선한다.
- 상세 API의 `finally` 또는 동등한 종료 경로에서 반드시 본문 로딩 상태를 해제해야 하며, 취소된 요청이 현재 딥링크 요청의 로딩 상태를 영구히 붙잡으면 안 된다.
- 같은 SPA 세션 안에서 클릭한 경우 전체 페이지 새로고침에 의존하지 않고 앱 내부 딥링크 이벤트로 처리한다.
- 사용자가 메모 내용을 수정하더라도 원본 메일 링크 블록은 저장 payload에 다시 합쳐져야 한다.

### 19.54.4 수정 시 동기화 정책

액션 아이템 row에서 아래 값이 바뀌면 서버는 summary DB와 캘린더 이벤트를 함께 업데이트한다.

- 날짜
- 시간
- 하루종일 여부

동기화 규칙:

- `calendarEventId`가 있으면 기존 캘린더 이벤트를 업데이트한다.
- `calendarEventId`가 없지만 동일한 메일/요약/actionIndex source key의 이벤트가 있으면 해당 이벤트를 찾아 업데이트한다.
- 기존 이벤트가 없으면 새 캘린더 이벤트를 생성한다.
- 수정 후 새로 생성되거나 업데이트된 캘린더 이벤트 ID를 summary JSON의 `calendarEventId`에 다시 저장한다.
- summary action item에 `calendarEventId`가 있으면 메일 요약 UI의 상태 문구를 `캘린더 등록됨`으로 표시한다.
- `캘린더 등록됨`은 단순 텍스트가 아니라 클릭 가능한 버튼/링크로 동작해야 한다.
- 사용자가 `캘린더 등록됨`을 클릭하면 같은 창에서 메일 화면을 닫고 캘린더 화면으로 이동한다.
- 캘린더 화면은 해당 `calendarEventId` 이벤트를 찾아 이벤트 시작 날짜로 이동하고, 가능하면 일 보기(`day`)로 전환한 뒤 이벤트 상세 모달을 바로 연다.
- 해당 이벤트를 찾지 못하면 캘린더 화면은 열되 기존 캘린더 상태를 유지하거나 오류 안내를 표시한다.

즉, 사용자가 메일 화면에서 날짜/시간/하루종일을 바꾼 뒤 캘린더 화면을 열면 변경 사항이 그대로 반영되어야 한다.

### 19.54.5 하루종일 수정 동기화

`하루종일`이 켜진 경우:

- summary action item의 `time`은 날짜만 저장한다.
- summary action item의 `isAllDay`는 `true`로 저장한다.
- 캘린더 이벤트의 `all_day`는 `true`로 저장한다.
- 캘린더 이벤트의 `start_dt`와 `end_dt`는 하루종일 이벤트 규칙에 맞게 업데이트한다.
- 시간 선택값은 캘린더 이벤트에 반영하지 않는다.

`하루종일`이 꺼진 경우:

- summary action item의 `time`은 `YYYY-MM-DD HH:mm` 형식으로 저장한다.
- summary action item의 `isAllDay`는 `false`로 저장한다.
- 캘린더 이벤트의 `all_day`는 `false`로 저장한다.
- 캘린더 이벤트의 시작/종료 시간은 선택한 날짜와 시간 기준으로 업데이트한다.

### 19.54.6 API 처리 원칙

기존 API:

```text
PATCH /api/mail/messages/:id/summary/action-items/:actionIndex/time
```

요청 예:

```json
{
  "tenantId": "tenant-id",
  "targetLanguage": "ko",
  "date": "2026-07-05",
  "time": "",
  "isAllDay": true,
  "createCalendarEvent": true
}
```

서버 처리 순서:

1. 메일 접근 권한을 확인한다.
2. 저장된 요약을 조회한다.
3. action item index를 검증한다.
4. 날짜/시간/하루종일 값을 summary JSON에 반영한다.
5. 캘린더 이벤트 제목을 메일 제목으로 만든다.
6. 캘린더 이벤트 메모에 액션 아이템 내용과 원본 메일 링크를 넣는다.
7. 기존 캘린더 이벤트가 있으면 업데이트하고, 없으면 생성한다.
8. 캘린더 이벤트 ID를 summary JSON에 저장한다.
9. 업데이트된 summary와 calendarEvent를 응답한다.

### 19.54.7 검증 기준

다음 시나리오를 확인한다.

1. 액션 아이템을 캘린더에 등록하면 캘린더 제목이 메일 제목으로 생성된다.
2. 캘린더 메모에 액션 아이템 내용이 포함된다.
3. 날짜를 수정하면 연결된 캘린더 이벤트의 날짜도 바뀐다.
4. 시간을 수정하면 연결된 캘린더 이벤트의 시간이 바뀐다.
5. `하루종일`을 켜면 연결된 캘린더 이벤트가 하루종일 이벤트로 바뀐다.
6. `하루종일`을 끄고 시간을 선택하면 연결된 캘린더 이벤트가 시간 지정 이벤트로 바뀐다.
7. 다른 메일을 열었다가 다시 돌아와도 summary JSON과 캘린더 이벤트가 같은 값을 유지한다.
8. 캘린더 이벤트 상세 화면에서 원본 URL은 메모 입력 박스 안에 노출되지 않는다.
9. 메모 입력 박스 아래에 `원본으로 이동` 링크가 표시된다.
10. `원본으로 이동`을 클릭하면 같은 창에서 해당 메일 상세 화면으로 이동하고, 메일 본문 로딩이 완료되어 본문 내용이 표시된다.
11. `원본으로 이동` 후 메일 목록에서 해당 메일 row가 선택된 상태로 표시된다.
12. 해당 메일이 현재 목록 첫 페이지에 없더라도 딥링크로 불러온 메일 row가 목록에 유지되고 선택된다.
13. 같은 이벤트 모달에서 같은 `원본으로 이동` 링크를 다시 클릭해도 메일 상세 API가 다시 시도된다.
14. 상세 API 실패 후 다시 `원본으로 이동`을 클릭하면 이전 실패 상태 때문에 재시도가 막히지 않는다.
15. 폴더 전환이 발생해 메일 목록이 다시 로드되어도 선택된 메일과 본문 상세가 사라지지 않는다.
16. 메일 요약 action item의 `캘린더 등록됨`을 클릭하면 같은 창에서 캘린더 화면으로 이동한다.
17. 캘린더 이동 후 해당 이벤트 날짜가 표시되고, 해당 이벤트 상세 모달이 열린다.
18. 이벤트를 수정 저장해도 원본 메일 링크 정보가 사라지지 않는다.
