# System Cache 구현 검토

## 1. 목적

한국 서버와 원격 사용자 사이의 네트워크가 느리더라도 EasyDocStation의 주요 화면을 빠르게 열 수 있도록, 필요한 데이터를 사용자 브라우저의 로컬 저장소에 보관하고 백그라운드에서 신규·변경·삭제 데이터를 계속 반영한다.

대상 데이터의 초기 기준은 다음과 같다.

- 연락처: 사용자가 연결한 주소록의 전체 연락처
- 메일: 사용자 전체 기준 최신 thread 300개(보낸편지함·휴지통·스팸·임시보관함 제외, 본문과 첨부파일 포함)
- 게시판: 사용자가 접근할 수 있는 채널별 최신 글 100개, 최근 댓글 및 첨부파일 포함
- Direct Message: 사용자가 참여한 대화의 마지막 상태
- 캘린더: 사용자가 로그아웃하기 직전의 화면 상태와 그 화면을 복원하는 데 필요한 일정 데이터
- 향후 추가되는 외부 서비스도 같은 동기화 규칙을 적용할 수 있어야 함

현재 확인된 병목은 **베트남 등의 원격 사용자 브라우저와 한국의 EasyDocStation 서버 사이의 장거리 네트워크**다. 따라서 이 문서에서 체감 속도를 개선하기 위한 `로컬 캐시`는 사용자 단말의 브라우저 저장소를 의미한다. 서버 DB와 ObjectFile 저장소는 중앙 원본 또는 서버 측 복제본으로 유지하고, 브라우저에는 로그인 사용자별로 허용된 최근 데이터 스냅샷을 보관한다.

브라우저 캐시는 중앙 원본을 대체하지 않는다. 권한 검증, 변경 저장, 최종 데이터 복구는 서버가 담당하고 브라우저 캐시는 빠른 초기 표시와 느린 회선에서의 재전송 감소를 담당한다.

## 2. 결론

구현할 가치가 있으며, 느린 네트워크 환경의 체감 속도를 크게 개선할 수 있다. 다만 별도의 범용 캐시를 하나 더 만들어 모든 데이터를 복제하기보다 다음 구조를 권장한다.

1. PostgreSQL 등 현재 서비스 DB에는 중앙 원본 또는 서버 측 복제 데이터를 영속 보관한다.
2. 첨부파일과 원문처럼 큰 바이너리는 서버 ObjectFile/object storage에 보관한다.
3. 브라우저의 IndexedDB에는 사용자별 최근 목록, 본문, 상태, 첨부파일 메타데이터와 선택된 첨부파일 blob을 보관한다.
4. Service Worker 또는 클라이언트 동기화 계층은 브라우저 캐시를 먼저 표시하고 서버의 변경분을 백그라운드에서 받는다.
5. 서버 동기화 작업자는 외부 서비스 변경분을 중앙 DB에 반영한다.
6. Redis는 영속 데이터 저장소가 아니라 서버 작업 큐, 짧은 잠금, 중복 작업 방지에만 선택적으로 사용한다.

현재 프로젝트는 이미 이 방향의 기반을 상당 부분 갖추고 있다.

- 메일은 `mail_messages`, `mail_attachments`, `mail_sync_state`와 로컬 object storage를 사용하고 신규 메시지를 적재하는 구조가 있다.
- 연락처는 `contact_resources`, `contacts`, ETag, sync token, CTag, 삭제 시각 등을 보관한다.
- 게시글, 댓글, 첨부파일, DM, 캘린더는 이미 EasyDocStation의 서버 DB/파일 저장소에 저장된다.

따라서 서버의 기존 데이터 계층을 유지하면서 **브라우저 캐시 우선(cache-first) 읽기와 서버 변경분 동기화 계층을 추가하는 작업**으로 보는 것이 적절하다.

## 3. 권장 아키텍처

```text
브라우저/UI
  ├─ IndexedDB: 최근 목록·본문·상태
  ├─ Cache Storage: 정적 자원과 허용된 응답
  └─ 선택적 파일 blob: 용량 정책 내 첨부파일
          │
          │ 캐시 즉시 표시 후 변경분 요청
          ▼
EasyDocStation API(한국)
  ├─ PostgreSQL: 목록, 본문, 권한, 읽음 상태, 동기화 상태
  ├─ Object Storage: 첨부파일, 메일 원문, 큰 본문
  └─ 선택적 Redis: 작업 큐, 분산 잠금, 짧은 메모리 캐시
          ▲
          │ upsert / tombstone / cursor 갱신
동기화 작업자(Sync Worker)
          ▲
          │ cursor, ETag, history token, updated-since 방식
외부 메일·주소록·캘린더·메시지 서비스
```

### 읽기 흐름

1. 화면 진입 즉시 브라우저 IndexedDB의 사용자별 스냅샷을 표시한다.
2. 브라우저는 마지막 cursor 또는 변경 시각을 서버에 보내 전체 목록이 아닌 변경분을 요청한다.
3. 서버 응답에는 `lastSyncedAt`, `syncStatus`, `isStale`을 함께 전달한다.
4. 변경분을 IndexedDB에 반영한 뒤 현재 화면의 변경 항목만 갱신한다.
5. 네트워크가 끊기거나 느려도 브라우저의 마지막 스냅샷을 계속 보여 주고 마지막 동기화 시각을 표시한다.
6. 첨부파일은 로컬 blob이 있으면 바로 열고, 없으면 서버에서 내려받으면서 진행 상태를 표시한다.

### 쓰기 흐름

초기에는 안전성을 위해 네트워크가 필요한 수정 작업을 무조건 성공한 것처럼 처리하지 않는 것이 좋다.

- 온라인: 외부 또는 원본 저장소에 변경 성공 후 로컬 DB를 갱신한다.
- 일시 실패: 사용자가 작성한 내용을 유실하지 않도록 `pending` 작업으로 보관하고 재시도 여부를 표시한다.
- 충돌: ETag, 버전 또는 `updated_at`을 비교해 자동 덮어쓰지 않고 충돌 상태를 노출한다.
- 삭제: 즉시 물리 삭제하지 않고 tombstone을 기록한 뒤 원본 삭제가 확인되면 보존 정책에 따라 정리한다.

읽기 캐시와 오프라인 쓰기 큐는 난이도와 위험이 다르므로, 1차에서는 빠른 읽기에 집중하고 오프라인 쓰기는 별도 단계로 구현하는 것을 권장한다.

## 4. 공통 데이터 모델

서비스마다 원본 테이블은 유지하되, 동기화 상태를 표현하는 공통 개념을 통일한다.

### 동기화 소스 상태

계정·사용자·서비스 단위로 다음 값이 필요하다.

| 항목 | 의미 |
|---|---|
| `tenant_id`, `user_id` | 데이터 격리와 권한 범위 |
| `source_type`, `source_id` | mail, contact, board, dm, calendar 및 연결 계정 식별 |
| `cursor_token` | provider cursor, history ID, sync token 등 다음 증분 조회 위치 |
| `last_attempt_at` | 마지막 동기화 시도 시각 |
| `last_success_at` | 마지막 성공 시각 |
| `status` | idle, queued, syncing, success, partial, auth_required, failed |
| `error_code`, `safe_error_message` | 비밀정보를 제거한 오류 정보 |
| `full_sync_required` | 커서 만료 등으로 전체 재동기화가 필요한지 여부 |
| `lease_owner`, `lease_until` | 동일 계정의 중복 동기화 방지 |

### 로컬 항목의 공통 상태

- 외부 서비스의 안정적인 원본 ID
- 원본의 version, ETag 또는 변경 시각
- `first_cached_at`, `last_seen_at`, `updated_at`
- `deleted_at` 또는 tombstone
- 본문/첨부파일의 로컬 저장 여부
- content hash와 파일 크기
- tenant, 사용자, 계정 및 권한 범위

별도의 거대한 `system_cache_items` JSON 테이블 하나에 모든 데이터를 넣는 것은 권장하지 않는다. 서비스별 검색, 관계, 권한, 삭제 및 인덱싱 요구가 다르기 때문에 기존 정규화 테이블을 사용하는 편이 안전하다. 공통 테이블은 동기화 작업과 상태 관리 정도로 제한한다.

## 5. 서비스별 보관 및 동기화 정책

### 5.1 연락처

#### 보관 범위

- 연결된 주소록의 전체 연락처를 로컬에 유지한다.
- 원본 vCard, 정규화된 이름·이메일·전화번호, 그룹, 사진 메타데이터를 보관한다.
- 연락처 사진은 지연 다운로드할 수 있으나 자주 표시되는 작은 썸네일은 로컬 보관이 유리하다.

#### 동기화

- CardDAV `sync-collection` 지원 시 sync token으로 증분 동기화한다.
- 미지원 서버는 CTag 또는 개별 ETag 비교를 사용한다.
- 변경, 신규, 삭제를 모두 반영하며 삭제는 tombstone으로 먼저 기록한다.
- 전체 동기화 중 일부 주소록이 실패하면 성공한 주소록까지 되돌리지 않고 `partial` 상태로 표시한다.

#### 현재 프로젝트와의 관계

연락처 스키마에 sync token, CTag, ETag, `deleted_at`, `last_seen_at`이 이미 있어 기반은 적절하다. 실제 동기화 경로가 공급자별 증분 토큰을 우선 사용하고, 주기 실행·실패 재시도·상태 표시를 일관되게 하는지가 핵심 보완점이다.

### 5.2 메일 최신 300개

#### 보관 범위

- 기준은 **로그인 사용자 전체의 최신 thread 300개**로 확정한다. 사용자가 여러 메일 계정을 연결해도 계정별 300개가 아니라 모든 포함 대상 메일함을 합쳐 최신순으로 300개를 유지한다.
- 보낸편지함, 휴지통, 스팸, 임시보관함은 대상에서 제외한다. 받은편지함과 사용자가 만든 일반 수신 폴더/라벨 등 나머지 포함 범위는 통합한다.
- thread 하나를 한 개로 계산한다. thread 내부 개별 메시지는 thread 상세을 열 수 있도록 함께 보관하되 300개 산정 시에는 증가시키지 않는다.
- 동일 thread 또는 메시지가 여러 라벨/폴더에 보여도 provider thread ID와 account ID 조합으로 중복 저장하지 않는다.
- 제목, 발신자, 수신자, 날짜, 라벨/폴더, 읽음, 별표, thread ID, 본문을 로컬에 보관한다.
- 첨부파일은 메타데이터와 다운로드 상태를 항상 보관한다.
- 첨부파일 원본까지 반드시 보관할지는 저장 용량 정책을 둔다.

권장 첨부 정책은 다음과 같다.

- 작은 첨부파일: 동기화 시 자동 다운로드
- 큰 첨부파일: 목록과 메타데이터만 먼저 저장하고 열 때 다운로드
- 사용자가 `오프라인 보관`한 메일: 크기와 관계없이 다운로드
- 악성코드 검사 실패 또는 허용 크기 초과: 원본을 열지 않고 상태만 표시

#### 동기화

- 최초 연결 시 최신 300개를 채운다.
- 이후 Gmail history ID, IMAP UID/UIDVALIDITY 등 공급자별 커서를 이용해 변경분만 받는다.
- 신규 메일을 넣은 뒤 보관 한도를 넘으면 오래된 메일을 정리하되 별표, 오프라인 보관, 게시글 출처, 진행 중 작업과 연결된 메일은 보호한다.
- 읽음, 별표, 폴더 이동, 삭제도 양방향 상태 불일치가 없도록 동기화한다.
- 커서가 만료되면 최근 구간을 다시 비교하는 복구 동기화를 수행한다.

#### 현재 프로젝트와의 관계

기존 메일 서버 구조는 이미 DB에 메타데이터를, object storage에 본문과 첨부파일을 보관하고 `mail_sync_state.cursor_token`을 관리하므로 재사용해야 한다. 브라우저에는 사용자 전체 최신 thread 300개를 별도 사용자 namespace로 보관한다. 서버 API는 여러 계정의 thread를 통합·중복 제거·최신순 정렬한 결과와 변경 cursor를 제공해야 한다.

### 5.3 게시판별 최신 글 100개

#### 보관 범위

- 로그인 사용자가 접근할 수 있는 각 채널의 최신 글 100개
- 각 글의 최근 댓글. 단, 댓글 개수 또는 기간은 아직 결정이 필요하다.
- 글/댓글의 좋아요, 수정·삭제 상태, 작성자 표시 정보
- 첨부파일 메타데이터와 로컬 파일

게시판 데이터가 현재 EasyDocStation 자체 DB에 생성되는 데이터라면 이미 로컬 원본이므로 다시 캐시 테이블에 복제하지 않는다. 목록 조회 인덱스와 API pagination을 보강하는 것으로 충분하다. 외부 게시판을 연결하는 경우에만 외부 ID, cursor, ETag를 가진 동기화 source를 추가한다.

#### 주의 사항

- `최신 100개`는 채널별 기준으로 해석한다.
- `고정 글`은 관리자가 채널 상단에 계속 노출하도록 지정한 공지성 글을 뜻한다. `사용자가 저장한 글`은 사용자가 북마크 또는 나중에 보기로 선택한 글을 뜻한다. 현재 EasyDocStation에 해당 기능이 없거나 캐시에서 별도 보호할 필요가 없다면 일반 글과 같이 최신 100개 정책을 적용한다. 향후 이 기능을 제공하면 최신 100개 밖이어도 브라우저 캐시에 보호할지를 별도 정책으로 정한다.
- 댓글과 첨부파일을 포함하면 글 수보다 저장 용량이 훨씬 커질 수 있으므로 tenant별 용량 제한이 필요하다.
- 사용자의 채널 권한이 철회되면 해당 사용자의 브라우저 캐시를 즉시 무효화하고, 서버 응답에서도 더 이상 반환하지 않는다.

### 5.4 Direct Message 마지막 상태

`마지막 상태`는 모호하므로 다음 범위로 정의하는 것을 권장한다.

- 사용자가 참여 중인 대화 목록
- 대화별 마지막 메시지와 시각
- 읽지 않은 개수와 사용자별 last-read 위치
- 참여자, 대화명, 나감/차단/보관 상태
- 마지막으로 열었던 대화와 스크롤 기준점
- 필요 시 각 대화의 최근 메시지 N개(예: 50개)

최근 대화 내역도 브라우저에 포함하는 것으로 확정한다. 다만 대화별 최근 메시지 개수 또는 기간은 아직 결정되지 않았다. 예를 들어 대화별 최근 50개처럼 수량을 정해야 브라우저 용량과 초기 다운로드량을 계산할 수 있다. 서버에서는 별도 원본 복제를 만들기보다 기존 DM 테이블의 cursor pagination과 대화 목록용 read model을 사용한다.

DM에는 현재 보존 기한 정책이 있으므로 시스템 캐시가 이를 우회해 삭제된 메시지나 첨부파일을 더 오래 보존해서는 안 된다.

### 5.5 캘린더 마지막 상태

여기서 `마지막 상태`는 일정의 마지막 변경 상태가 아니라 **사용자가 로그아웃하기 직전의 캘린더 화면 상태**를 의미하는 것으로 확정한다.

- 마지막으로 선택한 보기: 월간, 주간 또는 일간
- 마지막으로 보고 있던 기준 날짜와 선택된 일정
- 화면의 스크롤 위치, 필터, 표시 중인 캘린더 등 복원에 필요한 UI 상태
- 해당 화면을 다시 그리는 데 필요한 일정 데이터

UI 상태만 저장하면 화면 위치는 복원되지만 일정 데이터가 없어 서버를 다시 기다릴 수 있다. 따라서 일정 데이터의 브라우저 보관 범위는 **로그아웃 직전에 보고 있던 기준 날짜에서 3개월 전부터 3개월 후까지**로 확정한다. 시작 시각 또는 종료 시각이 이 기간과 겹치는 일정도 포함한다.

다음 로그인에서는 이 기간의 캐시를 먼저 표시한 후 서버에서 신규·수정·삭제된 변경분만 받아 갱신한다. 사용자가 캘린더를 이동해 기존 범위 밖의 날짜를 조회하면 새 기준 날짜를 중심으로 `-3개월 ~ +3개월` 범위를 추가로 내려받고, 최신 캐시 범위와 로그아웃 직전 화면 상태를 갱신한다.

EasyDocStation 자체 캘린더는 서버 DB가 원본이며, 반복 일정은 화면에 펼친 결과만 저장하지 않고 반복 규칙과 개별 수정·취소 예외를 함께 내려줘야 한다.

로그아웃 직전 상태는 사용자 계정에 귀속해야 한다. 공용 단말에서 다른 사용자가 볼 수 없도록 사용자별 namespace로 분리하고, 로그아웃 후 캐시를 즉시 삭제할지 암호화·잠금 상태로 유지할지는 보안 정책으로 결정해야 한다. 다음 로그인 때 상태를 복원하려면 무조건 삭제하는 정책과는 양립할 수 없다.

## 6. 동기화 실행 정책

### 실행 시점

- 서버 시작 후 지연 실행: 모든 계정을 동시에 동기화하지 않고 분산 시작
- 사용자 로그인 직후: 오래된 source만 우선 예약
- 화면 진입 시: 로컬 데이터는 즉시 반환하고 필요할 때 refresh 작업 예약
- 주기 실행: 서비스별 중요도와 API 제한에 맞춰 실행
- push/webhook 지원 서비스: 알림을 받으면 즉시 증분 동기화
- 사용자의 `지금 동기화`: 기존 작업과 중복되지 않게 높은 우선순위로 예약

초기 권장 주기는 메일·DM 1~5분, 캘린더 5~15분, 연락처 15~60분이다. 실제 값은 공급자 rate limit, 사용자 수, 서버 용량에 따라 설정 가능해야 한다.

### 작업 큐와 중복 방지

- 하나의 `source_id`에는 동시에 하나의 동기화 작업만 허용한다.
- 작업에는 idempotency key를 둬 재시도 시 같은 데이터를 중복 생성하지 않는다.
- 성공한 항목 단위로 checkpoint를 기록한다.
- 재시도는 exponential backoff와 jitter를 적용한다.
- 인증 실패는 무한 재시도하지 않고 `auth_required`로 전환한다.
- rate limit 응답은 공급자가 준 재시도 시각을 우선한다.
- worker가 중단돼도 lease 만료 후 다른 worker가 안전하게 이어받을 수 있어야 한다.

## 7. 캐시 신선도와 UI

빠르게 보이는 것만큼 오래된 데이터임을 숨기지 않는 것이 중요하다.

각 화면에는 필요에 따라 다음 상태를 표시한다.

- `마지막 동기화: 3분 전`
- `동기화 중`
- `오프라인 데이터 표시 중`
- `일부 항목 동기화 실패`
- `계정 재인증 필요`
- 사용자가 누를 수 있는 `새로고침` 또는 `지금 동기화`

API 응답은 데이터와 함께 최소한 다음 정보를 제공하는 것이 좋다.

```text
data
lastSyncedAt
syncStatus
isStale
nextCursor (목록 pagination용)
```

`stale-while-revalidate` 방식으로 로컬 결과를 먼저 보여 주고, 갱신 결과가 도착하면 목록을 통째로 깜빡이게 하지 않고 변경 항목만 반영한다.

## 8. 보안 및 개인정보

이 기능은 메일, DM, 연락처, 첨부파일을 장기간 로컬에 모으므로 단순 성능 기능이 아니라 민감정보 저장 기능으로 취급해야 한다.

- 모든 조회·동기화·파일 다운로드에서 `tenant_id + user_id + 원본 권한`을 검증한다.
- 외부 access/refresh token, CardDAV 비밀번호, 원본 vCard 등 민감값은 암호화 저장한다.
- 파일 경로를 사용자가 직접 조합할 수 없게 하고 object key를 서버에서 생성한다.
- 첨부파일 다운로드에도 원본 글/메일/DM 권한을 다시 확인한다.
- 로그에 토큰, 메일 본문, DM 본문, 연락처 원문을 기록하지 않는다.
- 계정 연결 해제, 사용자 탈퇴, 채널 권한 철회 시 삭제·격리 정책을 실행한다.
- 보존 기간과 용량 제한을 tenant 및 서비스별로 설정한다.
- 백업에도 같은 암호화·보존·삭제 정책을 적용한다.
- 브라우저 캐시는 사용자 ID와 tenant ID별 namespace로 완전히 분리한다.
- 공용 PC에서는 본문과 첨부파일을 보관하지 않는 `공용 단말 모드` 또는 로그아웃 시 전체 삭제 정책을 제공한다.
- 개인 단말에서 다음 로그인 때 캐시를 재사용하려면 저장 데이터 암호화, 사용자 재인증 전 접근 차단, 원격 캐시 무효화 정책이 필요하다.

이번 요구사항은 브라우저와 한국 서버 사이의 느린 회선을 보완하는 것이므로 IndexedDB 사용은 선택 사항이 아니라 핵심 구성이다. 다만 모든 첨부파일을 무제한 저장하지 않고 quota 안에서 선택적으로 보관하며, 브라우저 eviction으로 데이터가 없어져도 서버 원본에서 복구할 수 있어야 한다.

## 9. 용량 및 정리 정책

항목 개수만으로는 용량을 예측할 수 없다. 특히 `게시글 100개 + 최근 댓글 + 모든 첨부파일`과 `메일 thread 300개 + 첨부파일`은 사용자 한 명이 수 GB를 사용할 수도 있다.

다음 제한을 함께 두어야 한다.

- tenant별 전체 용량
- 사용자별 전체 용량
- 서비스·계정별 용량
- 단일 첨부파일 최대 크기
- 자동 선다운로드 가능한 파일 크기
- 마지막 접근 시각 기반 정리
- 고정/보호 항목과 삭제 금지 사유
- 임시 다운로드와 불완전 파일의 만료 시간

정리 작업은 DB 행을 먼저 지우고 파일 삭제에 실패하는 방식보다, 삭제 예정 상태를 기록하고 파일 삭제를 재시도한 후 메타데이터를 최종 정리하는 방식이 안전하다. DB와 파일 저장소의 고아 항목을 찾는 정기 점검도 필요하다.

## 10. 장애 및 복구 원칙

- 외부 네트워크 장애: 마지막 성공 스냅샷을 계속 제공한다.
- 인증 만료: 기존 데이터를 숨기지 않되 재인증 필요를 표시한다.
- cursor 만료: 최근 범위 재비교 또는 전체 재동기화로 복구한다.
- 부분 다운로드: 임시 object key에 저장한 뒤 해시·크기 확인 후 최종 경로로 전환한다.
- DB 성공/파일 실패: 항목을 `metadata_only` 또는 `download_failed`로 남겨 재시도한다.
- 외부 삭제: tombstone을 반영하고 열린 화면과 검색 인덱스에서도 제거한다.
- 권한 철회: 일반 동기화 주기를 기다리지 않고 즉시 접근을 차단한다.
- 백업 복구: 동기화 커서를 무조건 신뢰하지 말고 source별 재검증이 가능해야 한다.

## 11. 모니터링

운영 화면 또는 로그/메트릭에서 다음을 확인할 수 있어야 한다.

- source별 마지막 성공 시각과 지연 시간
- queued/running/failed 작업 수
- 서비스별 API 호출 수와 rate limit 발생 수
- 동기화된 신규·변경·삭제 항목 수
- 다운로드 성공/실패와 저장 용량
- 인증 필요 계정 수
- cursor 만료 및 전체 재동기화 횟수
- DB 행은 있으나 파일이 없는 항목과 고아 파일 수

메일·DM 본문이나 파일명 같은 개인정보를 메트릭 label에 넣지 않는다.

## 12. 단계별 구현 권장 순서

### 1단계: 기준과 측정

- 브라우저 IndexedDB를 사용자 단말 로컬 캐시로 사용하고 서버 DB/ObjectFile을 중앙 원본으로 유지한다.
- 서비스별 보관 범위, 용량, 신선도 목표를 확정한다.
- 현재 API별 응답 시간과 외부 네트워크 대기 시간을 측정한다.
- UI가 외부 서비스에 직접 접근하는 경로가 있는지 목록화한다.

### 2단계: 기존 메일·연락처 동기화 보강

- 현재 스키마와 object storage를 그대로 활용한다.
- 사용자 전체 최신 메일 thread 300개 및 제외 메일함 정책을 적용한다.
- 메일 첨부파일의 즉시/지연 다운로드 정책을 적용한다.
- 연락처 증분 동기화, 삭제, 재시도, 상태 표시를 완성한다.
- 모든 목록 API에 `lastSyncedAt`, `syncStatus`, `isStale`을 제공한다.

### 3단계: 게시판·DM·캘린더의 로컬 read model 정리

- 자체 DB 데이터는 중복 복제하지 않는다.
- 최신 글 100개, 댓글, 대화 마지막 상태, 일정 범위 조회에 필요한 복합 인덱스와 pagination을 점검한다.
- 첨부파일 권한 검사와 파일 상태를 통일한다.
- DM last-read와 최근 메시지 보관 범위를 명확히 한다.

### 4단계: 공통 작업 큐와 스케줄러

- source별 lease, checkpoint, backoff, idempotency를 공통화한다.
- 필요하면 이 단계에서 Redis 기반 큐를 도입한다.
- 서버 다중 인스턴스에서도 동일 source의 중복 실행을 막는다.

### 5단계: 실시간 갱신과 브라우저 캐시 운영 보강

- SSE/WebSocket으로 동기화 완료와 변경 항목을 알린다.
- IndexedDB quota, schema migration, 손상 복구와 eviction 동작을 검증한다.
- 로그아웃 정책, 권한 철회, 계정 연결 해제 시 브라우저 데이터 잠금 또는 제거를 검증한다.

## 13. 완료 기준

- 네트워크가 느리거나 외부 서비스가 응답하지 않아도 이전에 동기화된 연락처, 메일, 게시글, DM 상태, 일정이 즉시 표시된다.
- 화면 진입이 외부 동기화 완료를 기다리지 않는다.
- 신규·변경·삭제·권한 변경이 증분 동기화로 반영된다.
- 각 화면에서 마지막 동기화 시각과 오류/오래됨 상태를 알 수 있다.
- 동일 source의 중복 작업과 동일 항목의 중복 저장이 발생하지 않는다.
- 첨부파일의 메타데이터/원본 다운로드 상태가 일관되며 실패 후 재시도할 수 있다.
- 사용자와 tenant 사이에 데이터가 섞이지 않는다.
- 로그아웃, 계정 해제, 권한 철회, 보존 기간 만료 시 데이터가 정책대로 제거된다.
- 네트워크 호출량, 동기화 지연, 저장 용량, 오류율을 운영자가 확인할 수 있다.

## 14. 최종 의견

제안한 방향은 타당하다. 특히 메일과 연락처처럼 외부 네트워크 의존도가 높은 기능은 로컬 스냅샷을 먼저 보여 주는 것만으로도 큰 속도 개선을 얻을 수 있다.

EasyDocStation 서버의 DB와 ObjectFile 저장소는 중앙 원본 또는 외부 데이터의 서버 측 복제본 역할을 한다. 별도의 서버 범용 캐시 DB를 또 만들 필요는 없으며, 브라우저 IndexedDB에 필요한 범위만 사용자별로 복제해야 한다. 서버의 기존 서비스별 저장 구조를 유지하고 브라우저용 변경분 API, 동기화 상태, 캐시 무효화 규칙을 추가하는 방식이 가장 안전하다.

1차 목표는 **로컬 데이터 즉시 표시 + 백그라운드 증분 갱신 + 명확한 신선도 표시**로 잡는 것이 좋다. 오프라인 상태의 작성·수정까지 지원하는 기능은 충돌 해결과 보안 요구가 커지므로 별도의 2차 프로젝트로 분리하는 것을 권장한다.

## 15. 예상되는 문제점과 결정이 필요한 사항

현재 제안은 방향은 타당하지만, 구현 전에 다음 문제를 해결하지 않으면 기대한 속도 향상을 얻지 못하거나 데이터 불일치가 발생할 수 있다.

### 15.1 가장 먼저 확인할 문제: 어느 구간의 네트워크가 느린가

확인 결과 서버는 한국에 있고 베트남 등 원격 지역의 사용자가 접속하므로, 주된 병목은 아래 3번으로 확정한다.

1. 외부 서비스와 EasyDocStation 서버 사이
2. EasyDocStation 서버와 PostgreSQL/Cassandra/ObjectFile 저장소 사이
3. 사용자 브라우저와 EasyDocStation 서버 사이
4. 서버 내부의 느린 쿼리, 파일 처리 또는 너무 큰 API 응답

따라서 서버 캐시만으로는 충분하지 않다. 브라우저 IndexedDB를 중심으로 Service Worker, 응답 압축, cursor 기반 변경분 API, 작은 pagination, 썸네일, 첨부파일의 선택적 로컬 저장을 함께 적용해야 한다. 최초 한 번은 한국 서버에서 데이터를 받아야 하지만 이후에는 변경분만 전송해 장거리 통신량을 줄인다.

따라서 구현 전에 브라우저→API, API→DB, API→외부 서비스, 파일 전송 시간을 분리 측정해야 한다. 이 측정 없이 캐시를 만들면 실제 병목이 아닌 곳만 최적화할 수 있다.

### 15.2 `최신 N개` 기준 검토 결과

다음 기준은 확정되었다.

- 메일은 사용자의 모든 연결 계정을 합친 최신 thread 300개다.
- 보낸편지함, 휴지통, 스팸, 임시보관함은 제외한다.
- thread 하나를 한 개로 계산한다.
- 게시판은 사용자가 접근할 수 있는 채널별 최신 글 100개다.
- 글 100개에 달린 최근 댓글과 첨부파일을 포함한다.
- DM은 마지막 메시지 한 건뿐 아니라 최근 대화 내역도 포함한다.
- 캘린더는 로그아웃 직전의 화면 상태를 복원하고, 그 화면의 기준 날짜에서 3개월 전부터 3개월 후까지의 일정을 저장한다.

아직 결정해야 하는 수량은 `글 하나당 최근 댓글 몇 개`, `DM 대화별 최근 메시지 몇 개 또는 며칠`이다.

고정 글은 관리자가 공지처럼 채널 상단에 계속 보이게 지정한 글이고, 저장한 글은 사용자가 북마크한 글을 뜻한다. 현재 해당 기능을 사용하지 않는다면 별도 예외 없이 최신 글 100개에 포함되는 경우에만 캐시한다. 향후 기능이 생기면 최신 100개 밖이어도 보호할지 결정하면 된다.

### 15.3 기존 DB를 캐시라고 부를 때 원본의 경계가 불명확하다

메일과 연락처는 외부 서비스가 원본이고 EasyDocStation DB는 로컬 복제본에 가깝다. 반면 EasyDocStation에서 직접 생성한 게시글, DM, 캘린더는 현재 서버 DB가 원본이다.

원본 데이터와 캐시 데이터를 같은 개념으로 취급하면 다음 문제가 생긴다.

- 캐시 정리 작업이 원본 게시글이나 DM까지 삭제할 위험
- 외부 삭제를 로컬 보존으로 오인하거나 반대로 로컬 데이터를 너무 일찍 제거
- 백업 대상과 재동기화로 복구 가능한 대상을 구분하지 못함
- 장애 시 어느 저장소의 값을 우선해야 하는지 불명확

서비스별로 `authoritative source`, `local replica`, `derived read model`, `disposable cache`를 구분한 데이터 소유권 표가 필요하다. 원본 DB에는 LRU나 `최신 100개` 정리 정책을 적용해서는 안 된다.

### 15.4 게시판의 PostgreSQL–Cassandra 이중 저장 불일치

현재 게시글과 댓글 경로에는 PostgreSQL과 Cassandra 미러 및 fallback 로직이 함께 존재한다. 일부 댓글 데이터는 Cassandra에서 `updated_at`을 충분히 표현하지 못하고, 검색 또는 삭제 경로도 두 저장소를 함께 다룬다.

따라서 게시판 캐시/read model을 추가하기 전에 다음을 확정해야 한다.

- 게시글과 댓글의 최종 원본 저장소
- 두 DB에 쓰는 도중 하나만 성공했을 때의 복구 방식
- 수정·삭제·첨부파일 참조 상태의 우선순위
- 최신 100개를 계산할 때 어느 저장소의 시각과 행을 사용할지
- 미러 지연 중 사용자에게 어떤 값을 보여 줄지

이 문제를 정리하지 않고 세 번째 캐시 계층을 추가하면 불일치가 더 커진다. 게시판은 새 캐시 테이블보다 현재 미러의 정합성 점검과 목록 쿼리 개선을 먼저 수행해야 한다.

### 15.5 첨부파일 때문에 저장 용량이 예상보다 매우 커질 수 있다

메일 300개와 채널별 게시글 100개라는 수량만으로는 용량 상한이 생기지 않는다. 한 항목에 대용량 첨부파일 여러 개가 있으면 사용자 한 명의 캐시가 수 GB 이상이 될 수 있다. 채널 수와 메일 계정 수가 늘면 사용량이 곱해진다.

구현 전에 다음 값을 확정해야 한다.

- 사용자·tenant·서비스별 최대 용량
- 자동 다운로드할 단일 파일의 최대 크기
- 첨부파일 합계가 quota를 넘을 때의 우선순위
- 본문만 보관할지 원문 MIME까지 보관할지
- 썸네일과 미리보기 파일을 용량 계산에 포함할지
- 보호 항목이 많아 quota 아래로 줄일 수 없을 때의 동작

권장 기본값은 첨부파일 메타데이터는 모두 저장하되, 큰 파일은 지연 다운로드하고 사용자가 오프라인 보관한 항목만 보호하는 방식이다.

### 15.6 최초 동기화가 네트워크와 서버를 오히려 느리게 만들 수 있다

여러 사용자가 로그인하거나 서버가 재시작된 직후 연락처 전체, 메일 300개, 게시판 첨부파일을 동시에 내려받으면 외부 API 제한, 디스크 I/O, DB 연결, CPU 파싱 작업이 한꺼번에 증가한다.

현재 메일 스케줄러는 계정을 순차 처리하고 프로세스 메모리의 `running` 값으로 중복 실행을 막는다. 단일 프로세스에서는 단순하지만, 계정 수가 많으면 한 주기 안에 작업을 마치지 못할 수 있고 다중 서버에서는 프로세스별로 같은 계정을 실행할 수 있다.

필요한 보완은 다음과 같다.

- 로그인 요청과 최초 동기화를 분리
- 계정별 작업 큐와 우선순위
- 전역 및 공급자별 동시 실행 제한
- 서버 시작 시 jitter를 둔 분산 실행
- DB 기반 또는 Redis 기반 lease
- 작은 batch와 checkpoint
- 사용자 화면에서 초기 적재 진행률 표시

### 15.7 공급자마다 완전한 증분 동기화가 보장되지 않는다

Gmail history, IMAP UID/UIDVALIDITY, CardDAV sync token, CalDAV sync token 등은 의미와 만료 방식이 다르다. 일부 공급자는 증분 API를 지원하지 않거나 오래된 cursor를 거부한다.

공통 `cursor_token` 필드만 두는 것으로는 충분하지 않을 수 있다. 공급자별 cursor 유형, 유효 범위, UIDVALIDITY, 마지막 전체 비교 범위와 복구 전략을 함께 저장해야 한다. cursor 만료 시 무조건 전체 데이터를 지우고 다시 받으면 화면이 비거나 API 호출량이 폭증하므로, 기존 스냅샷을 유지한 채 범위 재검증을 수행해야 한다.

### 15.8 삭제와 권한 철회가 일반 신규 동기화보다 어렵다

신규 항목은 upsert하면 되지만 삭제, 계정 해제, 채널 탈퇴, DM 대화 제외, 캘린더 초대 취소는 즉시 반영되지 않으면 민감정보 노출이 발생한다.

- 권한 철회는 캐시 TTL이나 다음 주기까지 기다리지 않고 API에서 즉시 차단해야 한다.
- tombstone 보존 기간과 실제 파일 삭제 시점을 정해야 한다.
- 브라우저 캐시가 있다면 서버 데이터 삭제만으로는 충분하지 않다.
- 검색 인덱스, RAG/vector 데이터, 썸네일, 백업에도 삭제를 전파해야 한다.
- 외부 서비스에서 목록에 더 이상 보이지 않는 것이 삭제인지 일시적 권한 오류인지 구분해야 한다.

특히 RAG와 검색 인덱스를 시스템 캐시 범위에 포함한 삭제 전파 설계가 현재 문서에서 상대적으로 약하다.

### 15.9 DM 보존 정책과 캐시 목표가 충돌할 수 있다

현재 DM에는 설정 기반 보존 기한과 실제 메시지·파일 정리 로직이 있다. 캐시가 최근 대화를 별도로 복제하면 원본에서 만료된 DM이 캐시에 남아 정책을 위반할 수 있다.

DM 데이터는 별도 영속 캐시로 복제하지 않고 원본 테이블을 직접 조회하는 것이 안전하다. 목록 성능이 필요하면 본문 복제가 아니라 대화별 마지막 메시지 ID, 마지막 시각, unread count 같은 파생 read model만 두고 원본 삭제 시 함께 제거해야 한다.

### 15.10 캘린더의 시간대와 반복 일정 문제

캘린더 범위 캐시는 단순히 날짜 범위로 잘라 저장하면 다음 오류가 날 수 있다.

- 사용자 또는 서버 timezone 변경
- DST가 있는 외부 캘린더
- 무기한 반복 일정
- 반복 일정 한 건만 수정하거나 취소한 예외
- 하루 종일 일정의 날짜 경계
- 초대 상태와 원본 일정의 갱신 순서 차이

화면에 펼친 occurrence만 캐시하지 말고 반복 규칙, 원본 timezone, 예외/취소 항목을 보존해야 한다. 범위 밖에서 시작해 범위 안까지 이어지는 일정도 조회 대상에 포함해야 한다.

### 15.11 읽기 상태와 변경 충돌

메일 읽음/별표, DM last-read, 캘린더 초대 수락처럼 자주 바뀌는 작은 상태는 여러 기기에서 동시에 수정될 수 있다. 마지막으로 도착한 값을 무조건 덮어쓰면 최신 사용자 동작을 잃을 수 있다.

- 원본 version 또는 provider timestamp 비교
- 클라이언트 변경의 pending/synced/failed 상태
- 동일 항목의 작업 순서 보장
- 실패한 변경의 재시도와 사용자 안내
- 다른 기기의 새 상태를 받았을 때 충돌 정책

1차가 읽기 전용 캐시라 해도, 기존 UI의 변경 작업이 로컬 복제본을 어떻게 갱신하는지는 반드시 정의해야 한다.

### 15.12 서버 로컬 파일은 다중 서버와 장애 복구에 약하다

ObjectFile 경로가 특정 서버 디스크에 있으면 다음 문제가 생긴다.

- 다른 API 인스턴스에서 파일을 찾지 못함
- 서버 교체 또는 디스크 장애 시 캐시와 원본 파일 유실
- DB만 백업되고 파일이 빠져 불일치 발생
- 컨테이너 재배포 시 로컬 파일 소실

단일 서버 운영이라면 허용할 수 있지만, 다중 인스턴스 또는 고가용성이 필요하면 공유 object storage 또는 동일한 object key를 사용하는 S3 호환 저장소가 필요하다. 외부에서 다시 받을 수 없는 게시판·DM 첨부파일은 캐시가 아니라 원본이므로 반드시 백업해야 한다.

### 15.13 캐시가 오히려 응답을 크게 만들 수 있다

로컬에 데이터가 있다고 목록 API가 글 100개의 댓글과 첨부파일 정보를 한 번에 모두 반환하면 DB는 빨라도 브라우저 전송·JSON 파싱·React 렌더링이 느려진다.

- 목록은 요약 정보만 반환
- 댓글은 글을 열 때 cursor pagination으로 조회
- 첨부파일은 메타데이터만 반환하고 원본은 별도 요청
- 메일 본문은 목록이 아니라 상세 API에서 조회
- gzip 또는 Brotli 압축
- 변경된 항목만 갱신

즉, `로컬 보관 범위`와 `한 API 응답에 포함하는 범위`를 분리해야 한다.

### 15.14 암호화 키와 개인정보 삭제 정책이 구체적이지 않다

민감값 암호화 원칙은 있으나 다음 운영 결정이 추가로 필요하다.

- 키를 어디에 저장하고 누가 접근하는지
- tenant별 키 분리가 필요한지
- 키 회전 시 기존 데이터 재암호화 방법
- 사용자 탈퇴와 계정 연결 해제 시 즉시 삭제할 데이터
- 법적 보존 또는 감사 목적으로 유지할 데이터
- 백업본에서 삭제 요청을 처리하는 방법
- 관리자도 내용을 볼 수 없게 할지, 감사 권한으로 볼 수 있게 할지

암호화 저장만으로 권한 문제가 해결되지는 않는다. 복호화 API의 인증·감사 로그와 키 운영 절차가 필요하다.

### 15.15 완료 기준에 수치가 부족하다

현재 완료 기준은 기능 중심이며 성능 목표가 없다. 성공 여부를 판단하려면 최소한 다음 SLO를 정해야 한다.

- 캐시가 있을 때 목록 API의 p50/p95 응답 시간
- 첫 화면에 데이터가 보이는 시간
- 신규 메일·DM·일정이 로컬에 반영되는 최대 지연
- 외부 장애 시 제공 가능한 마지막 스냅샷 비율
- 동기화 성공률과 재시도 후 복구 시간
- 사용자·tenant별 최대 디스크 사용량
- 권한 철회 후 접근 차단까지 허용하는 최대 시간

예를 들어 `캐시 적중 시 목록 p95 500ms 이하`, `메일 변경 5분 이내 반영`, `권한 철회는 즉시 차단`처럼 측정 가능한 값이 있어야 한다.

## 16. 구현 전 필수 결정 목록

아래 항목이 결정되기 전에는 전체 구현보다 측정과 작은 시범 적용만 진행하는 것이 안전하다.

1. 베트남 등 대상 지역에서 현재 응답 시간과 전송량 측정
2. 글 하나당 최근 댓글 보관 개수
3. DM 대화별 최근 메시지 개수 또는 기간과 기존 보존 기한의 관계
4. 로그아웃 시 브라우저 캐시를 삭제할지 잠가서 다음 로그인을 위해 유지할지
5. 첨부파일 자동 다운로드 크기와 브라우저·사용자·tenant quota
6. 서비스별 authoritative source와 삭제 책임
7. PostgreSQL–Cassandra 게시판 원본 및 불일치 복구 정책
8. 단일 서버인지 다중 서버인지와 ObjectFile의 백업/공유 방식
9. 성능·신선도·권한 철회 SLO

가장 안전한 시작점은 메일 한 서비스에서 사용자 전체 최신 thread 300개의 메타데이터와 본문을 IndexedDB에 보관하는 시범 운영이다. 제외 메일함 정책을 적용하고 첨부파일은 작은 파일만 자동 다운로드한다. 한국과 베트남에서 첫 접속과 두 번째 접속, 변경분 동기화의 시간과 전송량을 각각 측정한다. 이 결과를 바탕으로 연락처와 캘린더로 확대하고, 자체 원본인 게시판·DM은 서버 쿼리·응답 구조와 브라우저 캐시를 함께 개선하는 것이 좋다.
