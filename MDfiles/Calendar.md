# Calendar.md

## 증상

- 이벤트 모달에서는 `"불루탑 소장님 미팅"`의 시간이 `2026년 7월 8일 오후 05:30 ~ 오후 06:00`으로 저장/표시된다.
- 하지만 주간 캘린더 시간 그리드에서는 해당 이벤트가 오후가 아니라 오전 `05:30 ~ 06:00` 위치에 표시된다.
- 사용자가 Drag & Drop으로 오후 시간대로 강제로 옮기려고 해도, 화면상으로는 오전 시간대에만 남아 있는 것처럼 보인다.

## 확인한 원인

핵심 원인은 캘린더 화면의 12시간제 -> 24시간제 변환 함수가 서로 다른 `ampm` 값 형식을 섞어 쓰고 있기 때문이다.

### 1. 이벤트 데이터는 한국어 `오전` / `오후`를 사용한다

`EventAddModal.jsx`의 시간 선택 UI는 `ampm` 값을 다음처럼 저장한다.

- `오전`
- `오후`

관련 위치:

- `src/components/EventAddModal.jsx:150`
- `src/components/EventAddModal.jsx:151`
- `src/components/EventAddModal.jsx:152`

서버의 시간 변환 로직도 한국어 `오후`를 기준으로 처리한다.

- `server/routes/events.js:11`
- `server/routes/events.js:13`
- `server/routes/events.js:26`

즉, 현재 앱의 실제 이벤트 시간 데이터 형식은 `AM/PM`이 아니라 `오전/오후`이다.

### 2. 캘린더 렌더링 함수는 영문 `AM` / `PM`만 처리한다

`CalendarView.jsx`의 `dtTo24h()` 함수는 다음 조건만 검사한다.

- `dt.ampm === 'PM'`
- `dt.ampm === 'AM'`

관련 위치:

- `src/components/CalendarView.jsx:21`
- `src/components/CalendarView.jsx:22`
- `src/components/CalendarView.jsx:25`
- `src/components/CalendarView.jsx:26`

따라서 이벤트 데이터가 `{ ampm: '오후', hour: 5, minute: 30 }`인 경우, `dtTo24h()`는 오후 5시 30분을 `17:30`으로 바꾸지 못하고 그대로 `05:30`으로 해석한다.

그 결과 `오후 05:30 ~ 오후 06:00` 이벤트가 캘린더 그리드에서는 `오전 05:30 ~ 오전 06:00` 위치에 배치된다.

### 3. Drag & Drop도 같은 변환 함수를 사용한다

Drag & Drop으로 이벤트를 이동할 때도 기존 이벤트의 시작/종료 시간을 읽기 위해 `dtTo24h()`를 사용한다.

관련 위치:

- `src/components/CalendarView.jsx:887`
- `src/components/CalendarView.jsx:911`
- `src/components/CalendarView.jsx:912`
- `src/components/CalendarView.jsx:913`
- `src/components/CalendarView.jsx:914`
- `src/components/CalendarView.jsx:915`

그래서 화면 표시뿐 아니라 드래그 이동/리사이즈 계산에서도 오후 이벤트가 오전 시간으로 해석될 수 있다.

특히 현재 증상처럼 사용자가 오후로 드롭해도 화면이 다시 오전처럼 보이는 이유는, 저장/상태 업데이트 이후에도 렌더링 단계에서 `오후`를 24시간제로 변환하지 못하기 때문이다.

## 영향 범위

- 주간 보기와 일간 보기의 시간 그리드 배치가 잘못된다.
- 이벤트 카드 내부에 표시되는 시간 문자열도 잘못될 수 있다.
- 월간 보기의 시간 prefix도 `dtTo24h()`를 사용하므로 오후 일정이 오전 시간처럼 표시될 수 있다.
- Drag & Drop 이동, 시작 시간 리사이즈, 종료 시간 리사이즈 계산도 영향을 받는다.
- 서버 저장 데이터 자체가 반드시 잘못된 것은 아니다. 모달과 서버는 한국어 `오전/오후`를 기준으로 동작하므로, 주된 문제는 프론트 캘린더 렌더링/계산 함수의 변환 불일치다.

## 해결 방법

### 1. `dtTo24h()`가 한국어와 영문 형식을 모두 처리하게 수정

`src/components/CalendarView.jsx`의 `dtTo24h()`를 다음 기준으로 보정해야 한다.

- `PM` 또는 `오후`이면 12가 아닌 hour에 12를 더한다.
- `AM` 또는 `오전`이고 hour가 12이면 0으로 바꾼다.
- `hour`, `minute` 값이 숫자가 아닐 가능성도 방어하면 더 안전하다.

예시 방향:

```js
function dtTo24h(dt) {
  let h = Number(dt.hour)
  const m = Number(dt.minute) || 0
  const ampm = dt.ampm
  if ((ampm === 'PM' || ampm === '오후') && h !== 12) h += 12
  if ((ampm === 'AM' || ampm === '오전') && h === 12) h = 0
  return { hour: h, minute: m }
}
```

### 2. 시간 데이터 형식을 하나로 통일

장기적으로는 `ampm` 저장 형식을 앱 전체에서 하나로 통일하는 것이 좋다.

권장안:

- UI 표시: `오전` / `오후`
- 내부 데이터: 가능하면 24시간제 숫자 또는 ISO datetime
- 기존 구조 유지 시: `ampm`은 `오전` / `오후`로 통일하고, 변환 함수도 이 형식을 기준으로 작성

현재 코드 기준으로는 이미 모달과 서버가 `오전/오후`를 쓰고 있으므로, 단기 수정은 `CalendarView.jsx`의 `dtTo24h()`를 한국어 기준에 맞추는 것이 가장 작고 안전하다.

### 3. 회귀 테스트 포인트

수정 후 아래 케이스를 확인해야 한다.

- `오후 05:30 ~ 오후 06:00` 이벤트가 주간/일간 보기에서 `17:30 ~ 18:00` 위치에 표시되는지
- 이벤트 카드 내부 시간이 `17:30 – 18:00`으로 표시되는지
- 해당 이벤트를 오전에서 오후로, 오후에서 오전으로 Drag & Drop 했을 때 위치가 정상 반영되는지
- 시작/종료 리사이즈가 오전/오후 경계를 넘을 때 정상 동작하는지
- `오전 12:00`은 `00:00`, `오후 12:00`은 `12:00`으로 처리되는지

## 결론

이번 문제의 직접 원인은 이벤트 데이터의 `ampm` 값은 한국어 `오후`인데, 캘린더 배치 계산 함수 `dtTo24h()`가 영문 `PM`만 인식하는 형식 불일치다.

따라서 코드 수정 시에는 우선 `src/components/CalendarView.jsx`의 `dtTo24h()`를 `오전/오후`도 처리하도록 고치면, `"불루탑 소장님 미팅"`이 오전이 아니라 실제 시간인 오후 5:30 ~ 6:00 위치에 표시되고 Drag & Drop 동작도 함께 정상화될 가능성이 높다.

## 주간 보기 날짜 열과 하루종일 이벤트 열 불일치

### 증상

- 주 단위 화면에서 상단 날짜 헤더의 각 날짜 열 위치와, 바로 아래 `하루종일` 이벤트 행의 날짜 열 위치가 서로 맞지 않는다.
- 긴 하루종일 이벤트 제목이 있는 날짜의 열이 더 넓게 보이고, 그 뒤 날짜들의 시작 위치가 날짜 헤더와 어긋난다.

### 원인

`src/components/CalendarView.jsx`의 `WeekView`에서 날짜 헤더, 하루종일 이벤트 행, 시간 그리드가 모두 `gridTemplateColumns: '56px repeat(7, 1fr)'`를 사용한다.

관련 위치:

- `src/components/CalendarView.jsx:264`
- `src/components/CalendarView.jsx:284`
- `src/components/CalendarView.jsx:317`

CSS Grid에서 `1fr` 트랙은 기본적으로 `minmax(auto, 1fr)`처럼 동작한다. 그래서 셀 내부에 긴 텍스트가 있으면 해당 열이 텍스트의 최소 콘텐츠 폭만큼 늘어날 수 있다.

날짜 헤더는 짧은 요일/날짜만 있으므로 균등하게 보이지만, 하루종일 이벤트 행은 긴 제목을 가진 이벤트가 들어오면서 특정 날짜 열이 넓어지고, 결과적으로 날짜 헤더와 하루종일 행의 열 너비가 서로 달라진다.

### 해결 방법

주간 보기에서 사용하는 7개 날짜 열을 `repeat(7, minmax(0, 1fr))`로 고정한다.

이렇게 하면 각 날짜 열이 콘텐츠의 최소 폭에 끌려가지 않고 동일한 비율로 나뉜다. 긴 하루종일 이벤트 제목은 셀 안에서 `truncate` 처리되어야 하며, 셀 자체는 `min-w-0`과 `overflow-hidden`을 가져야 한다.

구현 방향:

- 주간 보기 전용 그리드 컬럼 상수를 둔다.
- 날짜 헤더, 하루종일 이벤트 행, 시간 그리드가 같은 컬럼 정의를 공유하게 한다.
- 날짜 헤더 셀, 하루종일 셀, 시간 그리드 날짜 셀에 `min-w-0`을 적용한다.
- 하루종일 이벤트 카드에 `w-full`을 적용해 셀 너비 안에서만 말줄임되게 한다.

### 회귀 테스트 포인트

- 긴 하루종일 이벤트 제목이 있어도 날짜 헤더의 `일~토` 열과 하루종일 이벤트 행의 열 시작/끝 위치가 일치하는지 확인한다.
- 하루종일 이벤트 제목은 옆 날짜 열을 밀지 않고 해당 날짜 셀 안에서 말줄임되는지 확인한다.
- 시간 그리드의 날짜 열도 상단 날짜 헤더와 같은 x 좌표에 정렬되는지 확인한다.

## 반복 이벤트 이동 시 "이벤트를 찾을 수 없습니다" 오류

### 증상

- `"7월 7일 저녁에 이성환 법인장과 만나 베트남 시장 진출 방향에 대해 논의할 것."` 이벤트를 Drag & Drop으로 이동하면 반복 이벤트 수정 확인 팝업이 뜬다.
- 이후 수정 요청이 실패하며 `이벤트 수정 실패 / 이벤트를 찾을 수 없습니다.` 오류가 표시된다.

### 원인

드래그 이동 로직은 이벤트가 반복 이벤트인지 판단할 때 `repeat !== 'none'`만 확인한다.

관련 위치:

- `src/components/CalendarView.jsx:865`
- `src/components/CalendarView.jsx:893`
- `src/components/CalendarView.jsx:957`
- `src/components/CalendarView.jsx:983`

하지만 서버에서 반복 이벤트 전체 수정은 `series_id`로 시리즈 전체를 찾는다.

관련 위치:

- `server/routes/events.js:174`
- `server/routes/events.js:179`
- `server/routes/events.js:180`
- `server/routes/events.js:183`

즉, 프론트는 `repeat` 값만 보고 반복 이벤트 팝업을 띄우지만, 서버는 `seriesId`가 있어야 전체 수정할 수 있다. 기존 데이터, 메일/AI 액션에서 생성된 데이터, 마이그레이션 데이터처럼 `repeat` 값은 있지만 `seriesId`가 비어 있거나 올바르지 않은 경우에는 `/events/series/:seriesId` 요청이 서버에서 해당 시리즈를 찾지 못해 404가 된다.

또한 드래그 단건 저장 경로는 실패를 `.catch(() => {})`로 조용히 무시하고 있어서, 실패 시 화면 상태를 되돌리거나 사용자가 이해할 수 있는 메시지를 일관되게 보여주지 못한다.

### 해결 방법

반복 이벤트 전체 수정은 `repeat !== 'none'`뿐 아니라 `seriesId`가 실제로 있을 때만 허용해야 한다.

구현 방향:

- `repeat` 값과 `seriesId`를 함께 확인하는 헬퍼를 둔다.
- Drag & Drop 저장 시 `repeat`만 있고 `seriesId`가 없는 이벤트는 일반 단건 이벤트처럼 `/events/:id`로 저장한다.
- 드래그 저장 실패 시 기존 `prevEvents`로 화면 상태를 되돌리고 `openCalendarError('이벤트 수정 실패', err)`를 호출한다.
- 이벤트 모달의 저장/삭제 확인 팝업도 `seriesId`가 있는 반복 이벤트일 때만 띄운다.

### 회귀 테스트 포인트

- `repeat` 값은 있지만 `seriesId`가 없는 이벤트를 이동해도 `/events/series/null` 또는 `/events/series/undefined`로 요청하지 않는지 확인한다.
- `seriesId`가 있는 정상 반복 이벤트는 기존처럼 해당 날짜만/전체 선택 팝업이 뜨는지 확인한다.
- 드래그 저장 실패 시 이벤트가 이전 위치로 되돌아가고 오류 메시지가 표시되는지 확인한다.

## 다일(여러 날짜) 하루 종일 이벤트 지원 구현 방안

### 요구사항과 작업 제약

- `하루 종일`을 선택해도 시작일과 종료일은 각각 설정할 수 있어야 한다.
- `하루 종일`인 동안에는 오전/오후, 시, 분만 비활성화한다.
- 시작일과 종료일을 포함한 모든 날짜에 같은 하루 종일 이벤트를 표시한다. 예를 들어 7월 16일~18일이면 16일, 17일, 18일의 총 3일에 표시한다.
- 코드를 구현하는 단계에서도 `rag_train.py`는 절대로 수정하지 않는다.

### 현재 구현 확인 결과

#### 1. 모달은 날짜와 시간을 한꺼번에 비활성화한다

`src/components/EventAddModal.jsx`의 `DateTimeRow`는 년/월/일과 오전·오후/시/분을 한 컴포넌트에서 렌더링하고, 최상위 행에 `opacity-30 pointer-events-none`을 적용한다. 호출부도 `disabled={!canMutate || allDay}`를 시작/종료 행 전체에 전달한다.

따라서 현재 `하루 종일`을 켜면 시간뿐 아니라 시작일과 종료일도 함께 변경할 수 없다.

#### 2. 저장 구조는 이미 시작일과 종료일을 보유한다

모달의 `buildData()`는 `allDay`, `startDt`, `endDt`를 모두 API에 전달한다. `server/routes/events.js`의 생성·수정 API도 두 날짜 객체를 각각 `start_dt`, `end_dt`에 저장하고 클라이언트에 돌려준다.

즉, 다일 하루 종일 이벤트를 표현하기 위한 DB 컬럼 추가나 스키마 변경은 필요하지 않다. 기존 한 이벤트 레코드에 전체 기간을 저장할 수 있다.

#### 3. 현재 캘린더는 시작일에만 이벤트를 표시한다

`src/components/CalendarView.jsx`의 `eventOnDay(ev, date)`는 `ev.startDt`의 년/월/일이 화면 날짜와 같은지만 검사한다. 이 함수가 월간, 주간 하루 종일 행, 일간 하루 종일 행, 연간 이벤트 개수 계산 등에 공통으로 사용된다.

따라서 종료일을 다르게 저장하더라도 현재 화면에는 시작일 하루에만 나타난다.

#### 4. 서버는 비반복 이벤트를 한 행으로 생성한다

`POST /api/events`는 반복이 없으면 `{ startDt, endDt }` 한 쌍만 저장한다. 이는 다일 이벤트에 적합한 구조다. 다만 서버에는 종료일이 시작일보다 빠른 요청을 거부하는 명시적 기간 검증이 현재 보이지 않으므로 보강이 필요하다.

### 권장 데이터 의미

다일 하루 종일 이벤트는 **날짜마다 별도의 DB 이벤트를 3개 생성하지 않고**, 하나의 이벤트 레코드로 저장한다.

- `startDt`: 첫날
- `endDt`: 마지막 날
- 기간 규칙: 시작일과 종료일을 모두 포함(inclusive)
- 예: `2026-07-16 ~ 2026-07-18`은 총 3일

화면에서는 이 한 이벤트를 기간에 포함되는 각 날짜 셀에 동일하게 렌더링한다. 날짜별 독립 레코드를 만들면 같은 일정의 수정·삭제, 초대, 반복, 알림 및 RAG 학습이 중복되고 서로 분리될 위험이 있다. 사용자 관점의 “3일간 동일 이벤트 생성”은 한 논리 이벤트를 3개 날짜에 표시하는 것으로 구현하는 것이 안전하다.

### 구현 방안

#### 1. 날짜 선택과 시간 선택의 비활성 상태 분리

`EventAddModal.jsx`의 `DateTimeRow`에 행 전체용 `disabled` 하나만 두지 말고 다음 상태를 구분한다.

- 날짜 선택(년/월/일): `!canMutate`일 때만 비활성화
- 시간 선택(오전/오후/시/분): `!canMutate || allDay`일 때 비활성화

`하루 종일`일 때 날짜 select는 정상 색상과 포인터 동작을 유지하고, 시간 select와 `:` 구분자만 비활성 스타일 및 실제 `disabled` 속성을 적용한다. CSS의 `pointer-events-none`만 사용하는 대신 각 select에 `disabled`를 주어 키보드 조작과 접근성도 함께 막아야 한다.

레이블 `시간`은 날짜도 포함하므로 `날짜 및 시간` 또는 이에 준하는 표현으로 바꾸는 것도 권장한다.

#### 2. 기간 유효성 검사 추가

저장 전에 시간대를 제외한 날짜 전용 비교 함수를 사용해 다음을 검사한다.

- 종료일은 시작일보다 빠를 수 없다.
- 같은 날짜는 정상적인 1일 하루 종일 이벤트다.
- 날짜 변경 과정에서 시작일이 종료일을 넘어가면 종료일을 시작일로 자동 보정하거나, 저장 시 명확한 오류 메시지를 표시한다.

프론트 검증만 믿지 말고 `POST /api/events`, `PUT /api/events/:id`, `PUT /api/events/series/:seriesId`에서도 같은 규칙을 검증하여 잘못된 직접 API 요청을 `400`으로 거부한다.

#### 3. `eventOnDay`를 기간 포함 판정으로 확장

`CalendarView.jsx`에 년/월/일만 정규화해 비교하는 공통 유틸리티를 두고, 하루 종일 이벤트는 다음 규칙으로 판정한다.

- `startDate <= 화면 날짜 <= endDate`
- 양끝 날짜 포함
- 시간 값은 완전히 무시

시간 지정 이벤트는 기존 동작 범위를 불필요하게 바꾸지 않도록 우선 시작일 기준을 유지한다. 즉, 기간 판정 확장은 `ev.allDay === true`에만 적용하는 것이 이번 요구에 가장 안전하다.

이 공통 판정이 적용되면 월간 보기, 주간 하루 종일 행, 일간 하루 종일 행, 연간 개수/색상 표시가 모두 같은 기간 규칙을 사용해야 한다.

#### 4. 편집·삭제는 하나의 논리 이벤트로 유지

각 날짜에 보이는 카드는 같은 이벤트 `id`를 참조하게 한다. 어느 날짜에서 더블클릭하더라도 동일한 편집 모달을 열고, 기간을 변경하면 모든 보기에서 즉시 새 기간으로 다시 표시한다. 삭제도 한 번만 수행한다.

#### 5. Drag & Drop 정책 보강

현재 하루 종일 행으로 드롭하는 로직을 확인해 다일 이벤트의 기간 길이가 사라지지 않도록 해야 한다.

- 하루 종일 이벤트를 다른 날짜로 이동: 기존 날짜 수(종료일-시작일)를 유지한 채 시작일과 종료일을 함께 이동
- 시간 그리드로 변경: 기존 정책에 따라 시간 이벤트로 전환하되, 다일 기간을 어떻게 처리할지 명시 필요
- 이번 요구의 최소 범위에서는 다일 하루 종일 이벤트의 날짜 이동 시 기간 유지까지 보장하는 것을 권장

#### 6. 반복 이벤트와의 관계

다일 기간과 반복 주기는 별개다. 예를 들어 3일짜리 이벤트를 `매주` 반복하면 각 occurrence도 3일 기간을 유지해야 한다. 서버의 `generateOccurrences()`는 시작~종료 duration을 다음 occurrence에 적용하고 있으므로 기본 구조는 활용 가능하지만, 하루 종일 날짜 계산이 숨은 시간 값이나 DST에 영향받지 않도록 날짜 단위 계산 결과를 검증해야 한다.

### 변경 대상 예상 파일

| 파일 | 변경 방향 |
|---|---|
| `src/components/EventAddModal.jsx` | 날짜/시간 disabled 분리, 기간 검증 및 사용자 오류 안내 |
| `src/components/CalendarView.jsx` | 하루 종일 이벤트의 시작~종료일 포함 판정, 모든 보기 적용, 이동 시 기간 유지 |
| `server/routes/events.js` | 생성·단건 수정·시리즈 수정의 날짜 기간 검증, 반복 occurrence 기간 확인 |
| 캘린더 관련 테스트 파일 | 날짜 비교, 렌더링, API 검증 회귀 테스트 추가 |

`rag_train.py`는 변경 대상이 아니며 수정하지 않는다. 기존 `server/rag.js` 호출 흐름도 한 논리 이벤트를 한 번 학습하는 현재 원칙을 유지한다.

### 테스트 시나리오

1. 하루 종일 OFF: 날짜와 시간 모두 수정 가능하다.
2. 하루 종일 ON: 시작/종료 년·월·일은 수정 가능하고 오전/오후·시·분만 비활성화된다.
3. 시작일=종료일: 해당 날짜 한 곳에만 표시된다.
4. 7월 16일~18일: 월간, 주간, 일간 보기에서 16·17·18일 모두에 같은 제목과 색상으로 표시된다.
5. 월말/연말 경계(7월 31일~8월 2일, 12월 31일~1월 2일)도 정확히 각 3일에 표시된다.
6. 종료일을 시작일보다 앞서 설정하면 저장되지 않고 명확한 안내가 나온다.
7. 가운데 날짜의 카드를 편집하거나 삭제해도 하나의 이벤트가 수정/삭제되고 모든 날짜 표시가 함께 갱신된다.
8. 3일 이벤트를 다른 날짜로 드래그하면 3일 기간이 유지된다.
9. 3일 하루 종일 + 매일/매주/매월/매년 반복 occurrence가 각각 동일한 3일 기간을 유지한다.
10. 초대받은 사용자의 캘린더에서도 전체 기간이 동일하게 보이며 권한 규칙이 유지된다.
11. 알림은 날짜별로 중복 생성되지 않고 한 논리 이벤트의 시작일 기준으로 한 번 동작한다.
12. 저장 후 RAG 학습도 날짜별 중복 문서가 아니라 한 이벤트 문서로 처리된다.

### 완료 기준

- `하루 종일` 선택 시 시간 컨트롤만 비활성화되고 두 날짜는 편집 가능하다.
- 시작일~종료일을 포함한 모든 날짜에 이벤트가 노출된다.
- 3일 범위는 정확히 3일로 계산되며 월·주·일·연간 보기의 결과가 일치한다.
- 편집·삭제·초대·알림·RAG는 하나의 이벤트 단위로 유지된다.
- 잘못된 역방향 기간은 프론트와 서버에서 모두 차단된다.
- `rag_train.py`에는 변경이 없다.

## 월간 보기에서 다일 하루 종일 이벤트를 연결된 긴 바로 표시

### 추가 요구사항

하나의 하루 종일 이벤트가 여러 날짜에 걸쳐 있으면 월간 보기의 날짜별 셀마다 같은 카드를 반복해서 표시하지 않는다. 시작일부터 종료일까지 시각적으로 연결된 **하나의 긴 가로 바**로 표시한다.

예를 들어 `2026년 7월 16일 ~ 19일`의 `짱박혀 쉬기` 이벤트는 16일, 17일, 18일, 19일 셀에 각각 분리된 카드로 보이는 대신 다음 원칙으로 표시한다.

- 16일~18일: 같은 주의 목~토를 연결한 한 개의 바
- 19일: 다음 주 일요일에서 시작하는 후속 바
- 두 바는 같은 색상, 제목, 이벤트 `id`를 사용하여 하나의 논리 이벤트임을 유지

캘린더가 7열 주 단위로 구성되므로, 이벤트가 주 경계를 넘는 경우 DOM 요소 하나로 전체 기간을 물리적으로 연결할 수는 없다. 따라서 **주마다 하나의 segment로 나누되 사용자에게는 이어지는 하나의 이벤트처럼 보이도록** 구현한다.

### 현재 월간 보기 구조와 변경 필요성

현재 `src/components/CalendarView.jsx`의 `MonthView`는 다음 구조다.

1. 월 표시 범위를 주 단위 배열로 나눈다.
2. 각 주를 7열 grid로 렌더링한다.
3. 각 날짜 셀 안에서 `eventOnDay()`가 참인 이벤트를 찾는다.
4. 이벤트 카드를 날짜 셀 내부에 개별적으로 렌더링한다.

이 구조에서는 3일짜리 이벤트가 같은 `id`로 판정되더라도 날짜 셀마다 카드가 한 개씩 생긴다. 긴 바를 만들려면 이벤트 렌더링을 날짜 셀 내부에서 꺼내어 **주 행 단위 overlay/event layer**에서 처리해야 한다.

### 권장 구현 구조

#### 1. 월간 이벤트를 주 단위 segment로 변환

월간 보기의 각 주에 대해 다일 하루 종일 이벤트와 해당 주가 겹치는 구간을 계산한다.

- 실제 이벤트 범위: `[eventStart, eventEnd]`
- 현재 주 범위: `[weekStart, weekEnd]`
- 표시 segment 시작: `max(eventStart, weekStart)`
- 표시 segment 종료: `min(eventEnd, weekEnd)`
- 시작 열: segment 시작일의 요일 인덱스(일=0, 토=6)
- 차지할 열 수: `segmentEnd - segmentStart + 1`

월 화면 앞뒤에 포함되는 이전 달/다음 달 날짜도 현재 6주 grid 안에 있다면 동일한 교집합 계산을 사용한다. 이렇게 해야 월 경계를 지나는 이벤트가 화면 가장자리에서 자연스럽게 이어진다.

#### 2. 날짜 배경과 이벤트 레이어 분리

각 주 행을 `position: relative` 또는 CSS Grid 기반 컨테이너로 만들고 다음 두 레이어를 둔다.

- 날짜 셀 레이어: 날짜 숫자, 오늘 표시, 셀 배경, 더블클릭 및 drop 영역
- 이벤트 레이어: 7열 grid 위에 이벤트 segment를 `grid-column: start / span length`로 배치

이벤트 레이어가 날짜 숫자를 가리지 않도록 날짜 헤더 높이를 확보하고, 이벤트는 그 아래의 고정된 lane에 배치한다. 이벤트가 없는 셀도 같은 lane 높이를 공유해야 주 전체의 세로 정렬이 유지된다.

#### 3. 시작·중간·끝 segment 모양

한 이벤트 segment의 모서리는 실제 이벤트 시작/종료 여부에 따라 다르게 처리한다.

- 실제 시작일이 segment 안에 있음: 왼쪽 모서리를 둥글게 표시
- 이전 주에서 이어짐: 왼쪽 모서리를 직각으로 하고 왼쪽 여백을 최소화
- 실제 종료일이 segment 안에 있음: 오른쪽 모서리를 둥글게 표시
- 다음 주로 이어짐: 오른쪽 모서리를 직각으로 하고 오른쪽 여백을 최소화

주 경계 segment 사이의 작은 grid 간격은 불가피하지만, 동일 색상과 동일 lane을 유지하여 연결된 바로 인식되게 한다. 필요하면 계속됨을 나타내는 미세한 방향 표시를 추가할 수 있으나 기본 구현에서는 직각 끝 처리만으로 충분하다.

#### 4. 이벤트 제목 표시 규칙

- 제목은 원칙적으로 실제 시작 segment에 한 번 표시한다.
- 이벤트가 화면 이전 날짜에서 시작해 현재 화면으로 들어온 경우에는 현재 화면의 첫 segment에 제목을 표시한다.
- 다음 주 segment에는 공간이 충분하면 제목을 다시 표시할 수 있지만, 기본 권장안은 사용자가 이벤트를 식별할 수 있도록 **각 주 segment에 제목을 표시**하는 것이다.
- 긴 제목은 segment 너비 안에서 `truncate` 처리한다.
- 시간 지정 이벤트는 기존처럼 `HH:mm 제목` 형식의 날짜별 카드로 유지한다.

#### 5. 겹치는 이벤트의 lane 배치

같은 날짜 범위에 여러 이벤트가 있으면 긴 바가 서로 겹치지 않도록 주 단위 lane 할당이 필요하다.

권장 알고리즘:

1. segment를 시작 열 오름차순, 길이가 긴 순서, 이벤트 제목 또는 `id` 순으로 안정 정렬한다.
2. 각 segment를 기존 segment와 열 범위가 겹치지 않는 가장 낮은 lane에 배치한다.
3. 같은 이벤트가 다음 주로 이어질 때 가능한 한 이전 주와 같은 lane 번호를 우선 사용한다.
4. 표시 가능한 lane 수를 넘으면 나머지는 날짜별 `+N개` 또는 주 단위 `+N개 일정` 표시로 접는다.

lane 높이와 최대 표시 개수는 현재 날짜 셀 높이에 맞춰 정한다. 날짜별 단순 `slice(0, 3)` 방식은 긴 bar segment 렌더링에는 직접 사용할 수 없으므로, 숨김 개수 계산도 lane 결과를 기준으로 다시 구성해야 한다.

#### 6. 클릭, 편집 및 Drag & Drop

각 주 segment는 원본 이벤트 객체와 동일한 `id`를 참조한다.

- 더블클릭: 어느 segment를 클릭해도 동일 이벤트 편집 모달을 연다.
- 드래그 시작: segment의 어느 부분에서 시작해도 원본 이벤트 전체를 이동 대상으로 삼는다.
- 날짜 셀로 drop: 기존 이벤트 기간 길이를 유지하면서 시작일과 종료일을 함께 이동한다.
- 주 경계로 나뉜 segment를 각각 독립 이벤트로 저장하거나 수정하지 않는다.
- 읽기 전용 초대 이벤트는 기존 권한 판정에 따라 drag를 비활성화한다.

이벤트 overlay가 날짜 셀의 더블클릭/drop을 가로채지 않도록 이벤트 카드에서는 `stopPropagation()`을 유지하고, 빈 영역은 하단 날짜 셀 레이어의 동작으로 전달되게 해야 한다.

### 보기별 적용 범위

- **월간 보기:** 이번 요구의 핵심. 여러 날짜를 가로지르는 긴 바로 표시한다.
- **주간 보기:** 현재 날짜별 하루 종일 카드 구조도 향후 같은 방식으로 7열을 span하는 바로 통일할 수 있다. 월간 구현 시 segment 계산 유틸리티를 재사용 가능하게 설계하는 것을 권장한다.
- **일간 보기:** 하루만 표시하므로 기존 카드 형태를 유지한다.
- **연간 보기:** 현재 요약 표시를 유지하고 기간에 포함되는 날짜 개수/색상 판정만 사용한다.

### 구현 시 예상 변경 대상

| 파일 | 변경 방향 |
|---|---|
| `src/components/CalendarView.jsx` | 월간 주별 segment 계산, lane 할당, 이벤트 overlay grid, 연결 모서리 및 상호작용 구현 |
| 캘린더 UI 테스트 | 동일 주, 주 경계, 월 경계, 이벤트 겹침 및 drag 동작 검증 |

서버 저장 방식과 API는 이미 하나의 이벤트에 시작일과 종료일을 보관하므로 이번 **표시 방식 변경만으로는 서버나 DB 변경이 필요하지 않다**. `rag_train.py`는 관련이 없으며 절대로 수정하지 않는다.

### 테스트 시나리오

1. 하루짜리 하루 종일 이벤트는 기존처럼 한 셀 너비의 둥근 바로 표시된다.
2. 같은 주의 월~수 이벤트는 세 날짜 폭의 한 bar로 표시된다.
3. 목~다음 주 화 이벤트는 첫 주 목~토와 다음 주 일~화 segment로 나뉘며 같은 색상과 lane으로 이어져 보인다.
4. 이전 달 말일부터 현재 달 초일까지 걸친 이벤트가 월간 grid에 보이는 전체 범위만큼 연결된다.
5. 현재 달 말일 이후 다음 달 날짜까지 걸친 이벤트도 화면에 노출된 다음 달 셀까지 연결된다.
6. 같은 기간 이벤트가 둘 이상이면 서로 다른 lane에 표시되고 겹치지 않는다.
7. 짧은 이벤트와 긴 이벤트가 일부 날짜에서만 겹쳐도 lane이 안정적으로 유지된다.
8. 긴 bar의 시작·중간·끝 부분 어느 곳을 더블클릭해도 동일 이벤트가 열린다.
9. 긴 bar를 다른 날짜로 이동하면 원래 기간 길이를 유지한 채 전체 bar가 이동한다.
10. 반복 이벤트 segment도 occurrence별 기간을 유지하고 다른 occurrence와 `id`가 섞이지 않는다.
11. 표시 한도를 넘는 일정의 `+N개` 계산에 같은 다일 이벤트가 날짜마다 중복 집계되지 않는다.
12. 인쇄 화면에서도 긴 bar의 위치, 색상, 제목 및 주 경계가 정상적으로 보인다.

### 완료 기준

- 여러 날에 걸친 하나의 하루 종일 이벤트가 날짜별 독립 카드가 아니라 연결된 긴 bar로 보인다.
- 주 경계에서는 주별 segment로 분할되지만 동일 색상, lane 및 모서리 규칙으로 하나의 이벤트처럼 인식된다.
- 이벤트가 겹쳐도 bar가 서로 덮이지 않고 일정한 lane에 배치된다.
- 긴 bar의 모든 segment가 동일한 편집·삭제·권한·Drag & Drop 동작을 수행한다.
- 기존 시간 지정 이벤트와 하루짜리 이벤트 표시가 깨지지 않는다.
- 서버, DB 및 `rag_train.py` 변경 없이 프론트 월간 렌더링만으로 구현할 수 있다.

## 하루짜리 하루 종일 이벤트의 날짜 경계 및 제목 잘림 처리

### 증상과 요구사항

- 시작일과 종료일이 같은 하루짜리 `하루 종일` 이벤트인데, 제목이 길면 이벤트 바가 다음 날짜까지 이어진 것처럼 보인다.
- 하루짜리 이벤트 바는 반드시 해당 날짜 한 칸 안에서만 그려져야 한다.
- 제목이 한 칸의 너비보다 길면 다음 날짜 영역으로 넘어가지 않고, 앞부분만 한 줄로 표시한 뒤 나머지는 말줄임표로 생략한다.
- 여러 날짜로 실제 등록된 하루 종일 이벤트만 기존 기간만큼 여러 열을 차지해야 한다.

### 현재 구현 검토

월간 보기의 하루 종일 이벤트는 `src/components/CalendarView.jsx`의 `monthAllDaySegments()`에서 주 단위 segment로 변환된다. 현재 열 범위는 다음 방식으로 계산된다.

- `startCol`: 현재 주에서 이벤트가 시작되는 날짜 열
- `endCol`: 현재 주에서 이벤트가 끝나는 날짜 열
- 실제 배치: `gridColumn: startCol + 1 / span (endCol - startCol + 1)`

따라서 시작일과 종료일이 같은 데이터라면 `startCol === endCol`이고, 계산상 `span 1`이 되어 한 날짜 열만 차지하는 것이 정상이다. 반대로 화면에서 실제 배경 바 자체가 두 열을 차지한다면 단순히 제목이 긴 문제가 아니라 다음 중 하나를 먼저 구분해야 한다.

1. 저장된 `endDt`가 실제로 다음 날짜로 들어가 있어 segment가 `span 2`로 계산된 경우
2. 바의 grid span은 한 칸이지만, grid item의 최소 콘텐츠 너비 또는 텍스트 overflow 때문에 옆 칸을 침범해 보이는 경우

현재 이벤트 카드에는 Tailwind의 `truncate`가 적용되어 있다. 일반적으로 `truncate`는 `overflow-hidden`, `text-overflow: ellipsis`, `white-space: nowrap`을 설정한다. 다만 CSS Grid/Flex 자식은 기본 최소 너비가 콘텐츠에 영향을 받을 수 있으므로, 날짜 한 칸이라는 경계를 확실히 보장하려면 카드와 카드가 놓이는 overlay 모두에 너비 축소 조건을 명시하는 편이 안전하다.

### 권장 구현 방안

#### 1. 하루짜리 여부를 날짜 값으로 명확히 판정

시간과 타임존의 영향을 제외하고 `startDt`와 `endDt`의 년·월·일을 날짜 전용 값으로 정규화한다.

- 시작일과 종료일이 같음: 반드시 `span 1`
- 종료일이 시작일보다 늦음: 양끝 날짜를 포함하여 `span = 날짜 차이 + 1`
- 종료일이 시작일보다 빠름: 잘못된 데이터로 보고 저장을 거부하거나 안전한 오류 상태로 처리

이 프로젝트 문서에서 정한 다일 하루 종일 이벤트 규칙은 종료일 포함(inclusive)이다. 외부 캘린더 연동 데이터가 종료일 제외(exclusive) 규칙을 사용한다면, 화면 계산 전에 내부 inclusive 규칙으로 변환해야 한다. 그렇지 않으면 하루짜리 외부 일정의 종료일이 다음 날로 들어와 두 칸짜리로 해석될 수 있다.

#### 2. 단일 날짜 segment의 grid 배치를 한 열로 강제

`monthAllDaySegments()` 결과가 하루짜리일 때 다음 조건을 보장한다.

- `startCol === endCol`
- `grid-column`의 span은 정확히 `1`
- 제목 길이는 span 계산에 절대로 관여하지 않음
- 카드의 배경색, 오른쪽 모서리와 여백도 현재 열의 오른쪽 경계 안에서 종료

날짜 열의 폭은 `repeat(7, minmax(0, 1fr))`와 같은 축소 가능한 고정 7열 정의를 사용하는 것이 안전하다. `grid-cols-7`을 유지한다면 생성 CSS가 동일한 축소 조건을 보장하는지 빌드 결과에서도 확인한다.

#### 3. 카드와 제목을 날짜 경계 안에서 자르기

하루 종일 이벤트 카드에는 다음 성격의 스타일을 함께 적용한다.

- `min-width: 0`
- `width: 100%`
- `max-width: 100%`
- `overflow: hidden`
- `white-space: nowrap`
- `text-overflow: ellipsis`
- `box-sizing: border-box`

Tailwind 기준으로는 `min-w-0 w-full max-w-full overflow-hidden whitespace-nowrap text-ellipsis` 조합을 명시하거나, 기존 `truncate`에 `min-w-0 w-full max-w-full`을 보강하는 방향이다. 이벤트 overlay grid 자체에도 `min-w-0`과 `overflow-hidden`을 적용해 자식의 콘텐츠가 다음 날짜 열 위에 그려질 여지를 차단한다.

제목은 별도 내부 `span`으로 감싸고 그 요소에도 `block min-w-0 truncate`를 적용하면 카드 배경의 크기와 텍스트 생략 책임을 분리할 수 있다. 전체 제목은 삭제하지 않고 이벤트 카드의 `title` 속성, 편집 모달 또는 별도 툴팁으로 확인할 수 있게 유지하는 것을 권장한다.

#### 4. 월간·주간 보기에 동일한 규칙 적용

같은 `monthAllDaySegments()`를 사용하는 월간 보기와 주간 하루 종일 행 모두 다음 원칙이 같아야 한다.

- 하루짜리는 한 열
- 실제 다일 이벤트만 여러 열 span
- 긴 제목은 할당된 segment 너비 내부에서만 말줄임
- 이벤트 제목 때문에 날짜 열 너비나 인접 날짜 위치가 변하지 않음

일간 보기는 인접 날짜 열이 없지만, 긴 제목 때문에 레이아웃 폭이 늘어나지 않도록 같은 overflow 규칙을 재사용하는 것이 좋다.

### 예상 변경 대상

| 파일 | 변경 방향 |
|---|---|
| `src/components/CalendarView.jsx` | 날짜 전용 범위 정규화, 하루짜리 segment의 `span 1` 보장, overlay/card의 너비 및 overflow 제약 강화 |
| `src/components/EventAddModal.jsx` | 하루짜리 저장 시 시작일·종료일 동일 여부 확인, inclusive 날짜 규칙 유지 |
| 외부 캘린더 변환 계층(해당 시) | exclusive 종료일을 내부 inclusive 종료일로 변환 |
| 캘린더 UI 테스트 | 한 날짜 경계, 긴 제목 말줄임, 실제 다일 span 회귀 테스트 추가 |

이번 요구는 표시 문제를 우선 다루므로 서버 또는 DB 스키마 변경은 필요하지 않다. 다만 실제 저장 데이터의 종료일이 다음 날로 잘못 만들어지는 것이 확인되면 생성·수정 또는 외부 데이터 변환 경로까지 함께 보정해야 한다.

### 테스트 시나리오

1. 시작일과 종료일이 같은 하루 종일 이벤트의 짧은 제목이 해당 날짜 한 칸에만 표시된다.
2. 시작일과 종료일이 같은 이벤트에 매우 긴 한글 제목을 입력해도 배경 바와 텍스트가 다음 날짜 열로 넘어가지 않는다.
3. 긴 제목은 한 줄 앞부분과 말줄임표만 보이고, 전체 제목 데이터는 유지된다.
4. 공백 없는 긴 영문, URL, 숫자 문자열도 날짜 경계를 넘지 않는다.
5. 같은 날짜에 하루 종일 이벤트가 여러 개 있어도 각 lane의 오른쪽 경계가 동일하게 유지된다.
6. 실제 2일 이벤트는 정확히 두 열, 3일 이벤트는 정확히 세 열을 차지한다.
7. 토요일부터 일요일까지의 이벤트는 주 경계에서 segment가 나뉘되 각 주의 허용 범위를 넘지 않는다.
8. 이전 달/다음 달 날짜가 함께 보이는 월간 화면에서도 하루짜리는 해당 셀 한 칸만 차지한다.
9. 브라우저 폭과 캘린더 패널 폭을 줄여도 날짜 열이 밀리지 않고 제목만 더 짧게 생략된다.
10. 월간 보기와 주간 보기에서 같은 하루짜리 이벤트의 날짜 범위가 일치한다.
11. 이벤트를 다른 날짜로 Drag & Drop한 뒤에도 하루짜리 기간과 한 칸 표시가 유지된다.
12. 인쇄 화면에서도 이벤트 바가 다음 날짜 경계를 침범하지 않는다.

### 완료 기준

- 시작일과 종료일이 같은 하루 종일 이벤트는 제목 길이와 관계없이 해당 날짜의 정확히 한 열만 차지한다.
- 카드 배경과 제목 모두 인접 날짜 셀로 넘어가지 않는다.
- 넘치는 제목은 한 줄 앞부분만 표시되고 말줄임표로 생략된다.
- 실제 다일 이벤트의 여러 열 span 동작은 유지된다.
- 월간·주간 보기, 화면 폭 변경 및 인쇄 결과에서 동일한 경계 규칙이 유지된다.
