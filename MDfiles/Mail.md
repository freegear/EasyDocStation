# Mail.md

## 게시판에 등록된 메일에서 원본 메일로 돌아가기

### 배경과 문제

메일을 게시판의 새 게시글 또는 기존 게시글의 댓글로 등록하면, 사용자는 게시판에서 메일 요약과 본문을 확인할 수 있다.

하지만 게시판 내용을 검토하다가 원본 메일의 전체 대화, 첨부파일, 메일함 위치 또는 후속 작업을 확인하려면 다음 과정을 거쳐야 한다.

1. 상단 메뉴에서 메일 화면으로 이동한다.
2. 원본 메일이 있던 계정과 메일함을 찾는다.
3. 제목이나 발신자를 이용해 메일을 다시 검색한다.
4. 검색 결과에서 원본 메일을 다시 연다.

게시판 글이 원본 메일에서 파생되었음에도 출처로 돌아가는 직접 경로가 눈에 띄지 않아 작업 흐름이 끊긴다. 따라서 메일을 게시판에 등록할 때 게시글에 **원본 메일로 가기** 링크 또는 버튼을 함께 제공하는 것이 필요하다.

### 현재 구현 확인 결과

코드를 검토한 결과, 원본 메일 딥링크를 생성하고 게시글 데이터에 보존하며 앱 내부에서 여는 기반 기능은 이미 구현되어 있다.

#### 1. 메일 딥링크 생성

`src/features/mail/mailPostContent.js`의 `buildMailDeepLinkClient()`는 다음 정보를 URL 파라미터에 넣는다.

- `mailMessageId`: 원본 메일 ID
- `mailTenantId`: 메일이 속한 tenant ID
- `mailTargetLanguage`: 메일 화면 표시 언어

이 조합은 메일 제목이나 메일함 이름에 의존하지 않고 원본 메시지를 직접 식별하는 데 적합하다.

#### 2. 게시글 내용과 카드 데이터에 링크 저장

같은 파일의 `buildMailPostContent()`는 게시글 마크다운 끝에 `원본 메일 열기` 링크를 추가한다. `buildMailCardData()`도 카드 메타데이터에 다음 값을 별도로 저장한다.

- `messageId`
- `tenantId`
- `targetLanguage`
- `deepLink`

`src/features/mail/MailToPostDialog.jsx`는 새 게시글 등록 시 이 데이터를 `mail-card` 마커에 포함한다. 따라서 화면 표시용 마크다운이 일부 편집되더라도 구조화된 카드 데이터로 원본 메일 정보를 유지할 수 있다.

#### 3. 게시판 카드의 원본 메일 열기 버튼

`src/components/mail/MailSummaryCard.jsx`에는 이미 `원본 메일 열기` 버튼이 있다. 버튼을 클릭하면 일반 페이지 이동 대신 `easy-mail-open-link` 이벤트를 발생시켜 앱 내부의 메일 화면을 연다.

`src/App.jsx`도 이 이벤트와 URL 딥링크를 처리하여 다음 동작을 수행한다.

- 게시판에서 메일 화면으로 전환
- `messageId`와 `tenantId`로 원본 메일 선택
- URL에 남은 딥링크 파라미터 정리

즉, 원본 메일로 이동하는 기술적 기반은 대부분 갖춰져 있다.

### 현재 화면에서 링크가 없는 것처럼 보이는 이유

현재 `MailSummaryCard`에서 `원본 메일 열기` 버튼은 카드의 가장 마지막에 배치되어 있다.

표시 순서는 다음과 같다.

1. 메일 제목과 발신자
2. 일정
3. 중요 포인트
4. 중요 내용 요약
5. 액션 아이템
6. 메일 본문 전체
7. 원본 메일 열기 버튼

메일 본문과 요약이 길면 버튼은 상세 패널의 맨 아래로 밀린다. 첨부된 화면처럼 사용자가 카드 상단과 요약 내용을 보고 있는 상태에서는 버튼이 보이지 않기 때문에, 실제로 기능이 있어도 없는 것처럼 인식된다.

또한 게시글 목록의 축약 카드에서는 상세 카드의 하단 버튼이 노출되지 않는다. 사용자는 상세 패널을 열고 아래까지 스크롤해야만 원본 이동 기능을 발견할 수 있다.

### 권장 UX

원본 메일 링크는 부가 정보가 아니라 게시글의 **출처 이동 기능**이다. 따라서 카드 맨 아래가 아니라 제목과 발신자 정보가 있는 상단 헤더에 항상 보여야 한다.

권장 배치는 다음과 같다.

- 위치: 메일 카드 제목 오른쪽 또는 발신자/날짜 행 오른쪽
- 형태: 메일 아이콘 + `원본 메일로 가기`
- 스타일: 인디고 계열의 명확한 보조 버튼
- 동작: 현재 탭에서 앱 내부 메일 화면으로 전환하고 해당 메일을 바로 선택
- 접근성: `button` 요소와 명확한 `aria-label` 사용

카드 폭이 좁은 경우에는 제목 아래 별도 행에 배치한다. 모바일에서는 아이콘만 표시하기보다 `원본 메일` 텍스트를 유지하는 편이 발견하기 쉽다.

기존 하단 버튼은 중복되므로 다음 두 안 중 하나를 선택할 수 있다.

1. 상단 버튼만 남기고 하단 버튼 제거 — 화면이 간결하므로 권장
2. 상단과 하단 모두 유지 — 긴 본문을 끝까지 읽은 뒤에도 바로 이동할 수 있음

사용 편의성만 보면 상단에 항상 표시하고, 긴 본문 카드에서는 하단에도 동일 기능을 유지하는 방안이 가장 좋다. 다만 동일 버튼이 과도하게 반복된다는 의견이 있으면 상단만 유지한다.

### 게시글 목록에서도 표시할지에 대한 의견

게시글 목록 카드에도 작은 `원본 메일` 배지를 제공하면 상세 화면을 열지 않고 바로 메일로 이동할 수 있다. 하지만 목록 카드 전체 클릭, 댓글 열기, 첨부파일 클릭과 상호작용이 겹칠 수 있다.

따라서 단계적으로 적용하는 것을 권장한다.

#### 1단계

- 게시글 상세 패널의 메일 카드 상단에 버튼 표시
- 새 게시글과 기존 게시글 댓글 모두 지원
- 현재 구현된 앱 내부 딥링크 재사용

#### 2단계

- 사용성 요구가 확인되면 게시글 목록 카드 우측 상단에 작은 출처 배지 추가
- 배지 클릭 시 게시글 상세를 열지 않고 원본 메일로 이동
- 배지 클릭 이벤트가 게시글 카드 클릭으로 전파되지 않도록 처리

### 새 게시글과 댓글 등록의 차이

현재 새 게시글은 구조화된 `mail-card` 데이터를 포함하지만, 기존 게시글에 댓글로 등록할 때는 마크다운 내용만 저장한다.

마크다운에는 이미 원본 메일 URL이 들어가므로 일반 링크로 이동할 수는 있다. 그러나 댓글에서도 새 게시글 카드와 동일하게 안정적인 앱 내부 이동을 제공하려면 다음을 고려해야 한다.

- 댓글의 마크다운 링크 클릭을 앱 내부 딥링크 처리와 연결
- 또는 댓글에도 `messageId`, `tenantId`를 구조화된 메타데이터로 보존
- 게시글 본문 편집 과정에서 링크가 삭제되어도 출처 정보가 유지되게 설계

최소 구현은 기존 마크다운 링크를 그대로 활용하는 것이다. 장기적으로는 새 게시글과 댓글 모두 동일한 `sourceType: mail`, `sourceMessageId`, `sourceTenantId` 구조를 사용하는 편이 데이터 추적과 UI 일관성에 유리하다.

### 링크 생성 및 저장 권장 방식

원본 메일의 핵심 식별자는 화면 URL 문자열이 아니라 다음 구조화된 값이다.

```text
sourceType: mail
messageId: 원본 메일 내부 ID
tenantId: 메일 tenant ID
targetLanguage: 선택 사항
```

화면에 표시할 URL은 이 값으로 필요할 때 생성한다. 완성된 절대 URL만 저장하면 도메인, 포트 또는 배포 경로가 바뀌었을 때 오래된 링크가 깨질 수 있다.

현재 `mail-card`는 구조화된 ID와 `deepLink`를 모두 저장하고 있으며, 버튼 클릭 시 구조화된 ID를 우선 사용한다. 이 방식은 적절하므로 유지하는 것을 권장한다.

### 클릭 동작

`원본 메일로 가기`를 클릭하면 다음 순서로 처리한다.

1. 게시판 상세 패널을 닫거나 메일 화면 전환에 방해되지 않게 정리한다.
2. 메일 서비스를 활성화한다.
3. `tenantId`에 해당하는 메일 계정 범위에서 `messageId`를 조회한다.
4. 원본 메일이 속한 실제 폴더를 확인한다.
5. 해당 폴더와 메시지를 선택하고 메일 상세를 연다.
6. 필요하면 브라우저 히스토리에 딥링크 상태를 남겨 뒤로 가기로 게시판에 복귀할 수 있게 한다.

특히 게시판으로 돌아오는 흐름도 중요하다. 단순히 화면 상태를 덮어쓰기보다 브라우저 뒤로 가기 또는 앱 내부 `게시글로 돌아가기` 기능을 제공하면 메일 확인 후 원래 작업으로 자연스럽게 복귀할 수 있다.

### 예외 및 오류 처리

#### 원본 메일이 삭제된 경우

- `원본 메일을 찾을 수 없습니다.` 안내 표시
- 휴지통에 있으면 휴지통의 메일을 열 수 있는지 정책에 따라 처리
- 게시판에 저장된 요약과 본문 스냅샷은 그대로 유지

#### 메일 계정 연결이 해제된 경우

- `메일 계정 연결이 해제되어 원본을 열 수 없습니다.` 안내
- 계정 관리 화면으로 이동하는 버튼은 권한이 있는 사용자에게만 제공

#### 게시글 열람자에게 원본 메일 권한이 없는 경우

게시판 글을 볼 수 있다고 해서 원본 메일까지 볼 수 있는 것은 아니다. 서버에서 `tenantId`, 사용자, 메일 계정 소유권 및 공유 정책을 다시 검증해야 한다.

- 권한 없음: `원본 메일을 열 권한이 없습니다.` 표시
- URL의 `messageId`만으로 다른 사용자의 메일이 노출되어서는 안 됨
- 게시판 카드에 저장된 본문 스냅샷의 공개 범위도 채널 권한 정책에 맞는지 별도 검토 필요

#### 메일이 다른 폴더로 이동된 경우

폴더 경로가 아니라 `messageId` 중심으로 조회해야 한다. 현재 딥링크가 이 원칙을 사용하므로 유지한다.

### 테스트 시나리오

1. 메일을 새 게시글로 등록하면 상세 카드 상단에 `원본 메일로 가기`가 즉시 보인다.
2. 버튼 클릭 시 메일 메뉴를 직접 찾지 않아도 원본 메일 상세가 열린다.
3. 받은편지함, 보낸편지함, 사용자 폴더의 메일 모두 정확히 열린다.
4. 원본 메일이 다른 폴더로 이동된 뒤에도 `messageId`로 찾아 열린다.
5. 기존 게시글의 댓글로 등록한 메일에서도 원본 링크가 정상 동작한다.
6. 한국어·영어·일본어 UI에서 버튼 레이블이 올바르게 표시된다.
7. 긴 제목과 좁은 화면에서도 버튼이 카드 밖으로 밀리거나 숨지 않는다.
8. 버튼 클릭이 게시글 더블클릭, 댓글 열기 또는 카드 선택 이벤트로 전파되지 않는다.
9. 메일을 열고 뒤로 가기를 수행하면 원래 게시판·채널·게시글 상세로 돌아온다.
10. 원본 메일 삭제 시 빈 화면 대신 명확한 오류 안내가 표시된다.
11. 계정 연결 해제 시 적절한 안내가 표시된다.
12. 권한이 없는 다른 사용자가 딥링크를 열어도 원본 메일 내용이 노출되지 않는다.
13. 과거에 생성된 `mail-card` 게시글도 기존 `messageId`, `tenantId`를 이용해 버튼이 표시된다.
14. 사용자가 게시글 마크다운 내용을 편집해도 구조화된 출처 정보가 유지되는 정책을 확인한다.

### 완료 기준

- 게시판의 메일 카드 상단에서 원본 메일 이동 기능을 스크롤 없이 발견할 수 있다.
- 클릭 한 번으로 앱 내부 메일 화면과 정확한 원본 메시지가 열린다.
- 새 게시글과 댓글 등록 흐름에서 동일하게 동작한다.
- 메일 이동 후 원래 게시글로 복귀할 수 있다.
- 삭제, 계정 해제, 권한 부족 상황에서 안전하고 이해 가능한 안내를 제공한다.
- 게시판 열람 권한과 원본 메일 열람 권한을 별도로 검증한다.

### 최종 의견

원본 메일 딥링크의 생성·저장·앱 내부 열기 기능은 이미 상당 부분 구현되어 있으므로 새로운 링크 체계를 다시 만드는 것은 필요하지 않다.

현재 문제의 핵심은 버튼이 긴 카드의 맨 아래에 있어 사용자가 발견하기 어렵다는 점이다. 가장 효과적인 개선은 기존 `MailSummaryCard`의 `원본 메일 열기` 기능을 카드 헤더 우측으로 올려 항상 보이게 하고, 메일 확인 후 게시글로 돌아오는 흐름을 보강하는 것이다.

우선 상세 카드 상단 버튼을 1차 범위로 적용하고, 이후 실제 사용성을 확인한 뒤 게시글 목록 배지와 댓글 구조화 메타데이터를 2차로 확장하는 방안을 권장한다.

## 메일 삭제 실패 진단 로그 추가 방안

### 문제

메일 일괄 삭제 중 일부 항목이 실패하면 화면에는 `일부 메일을 삭제하지 못했습니다.`라는 공통 문구만 표시된다. 서버의 `/mail/messages/bulk` 응답에는 개별 메일의 `error`가 포함되지만, 현재 서버 로그에는 이 값이 남지 않고 프론트도 상세 사유를 사용자 메시지나 개발자 콘솔에 기록하지 않는다.

그 결과 IMAP UID 누락, 원본 메일함 탐색 실패, 휴지통 탐색 실패, Gmail 권한 부족 또는 원격 MOVE 실패 중 어느 단계가 원인인지 사후 확인하기 어렵다.

### 권장 로그 위치

#### 1. 서버 bulk 삭제 처리

`server/routes/mail.js`의 `PATCH /messages/bulk` 처리에서 `action === 'delete'`인 개별 메일이 예외로 실패할 때 구조화된 경고 로그를 남긴다.

기록 필드:

- 작업명: `mail_delete`
- 결과: `failed`
- `tenantId`
- `userId`
- `messageId`
- 오류 메시지
- 오류 코드가 있으면 `code`
- stack은 개발 환경에서만 선택적으로 기록

또한 예외가 발생하지 않았지만 삭제 함수가 `null`을 반환해 `ok: false`가 된 경우에도 `message_not_found_or_not_deleted`와 같은 명시적 사유를 기록한다.

#### 2. 프로바이더 이동 단계

`server/mail/providerMove.js`에서는 IMAP/Gmail 처리 결과를 개별 메일별로 반환한다. 여기서 이미 구체적인 오류를 만들고 있으므로 bulk route가 해당 오류를 잃지 않고 로그에 남기는 것이 우선이다.

필요하면 후속 단계에서 다음 진단 정보를 추가할 수 있다.

- provider 종류
- account ID
- source folder ID/type
- target trash folder ID
- provider message ID 존재 여부
- IMAP UID 존재 여부
- 실패 단계: `connect`, `resolve_source`, `resolve_trash`, `find_uid`, `move`

단, 이 상세 로그는 계정 비밀번호, OAuth access/refresh token, 메일 본문 또는 첨부 내용을 절대로 포함하지 않는다.

#### 3. 프론트 개발자 콘솔

`src/features/mail/MailPage.jsx`에서 bulk 응답의 실패 항목을 `console.warn`으로 기록한다.

기록 필드:

- `messageId`
- 서버의 `error`
- 현재 선택 개수와 실패 개수

사용자 화면에는 기존 공통 문구를 유지하되, 실패가 한 건이면 서버의 안전한 오류 메시지를 함께 보여주는 것도 가능하다. 다만 원격 서버 내부 정보가 사용자에게 과도하게 노출될 수 있으므로 1차 구현은 콘솔과 서버 로그 중심으로 한다.

### 권장 로그 형식

한 줄 검색이 쉬운 prefix와 JSON 객체를 함께 사용한다.

```text
[mail delete] failed { tenantId, userId, messageId, code, error }
```

여러 건 삭제 결과는 요청 마지막에 요약 로그를 남긴다.

```text
[mail delete] bulk completed { tenantId, userId, requested, succeeded, failed }
```

성공한 단일 삭제를 모두 기록하면 로그가 과도해질 수 있으므로 다음 원칙을 권장한다.

- 실패 항목: 항상 `console.warn`
- bulk 요청 요약: 실패가 있을 때 `console.warn`, 전부 성공이면 기록 생략 또는 debug 수준
- 예외 stack: 운영 환경에서는 기본적으로 제외

### 개인정보 및 보안 기준

로그에 포함하지 않을 정보:

- 메일 제목
- 발신자와 수신자 주소
- 메일 본문과 요약
- 첨부파일 이름과 내용
- IMAP 비밀번호
- OAuth access token 및 refresh token
- 세션 쿠키와 Authorization 헤더

`providerMessageId`는 원격 UID를 포함할 수 있으므로 기본 로그에서는 값 자체 대신 `hasProviderMessageId`만 기록한다. 정밀 진단이 꼭 필요하면 일시적인 debug 설정에서만 마스킹된 값을 사용한다.

### 구현 대상

| 파일 | 변경 방향 |
|---|---|
| `server/routes/mail.js` | 개별 삭제 예외·null 결과 경고, 실패가 포함된 bulk 요청 요약 로그 추가 |
| `src/features/mail/MailPage.jsx` | bulk 응답의 실패 ID와 안전한 오류 사유를 개발자 콘솔에 기록 |
| 메일 route 테스트 | 예외 실패와 null 실패 시 응답 및 로그 호출 검증 |

### 테스트 시나리오

1. 정상 삭제는 기존처럼 성공하고 불필요한 개별 성공 로그를 남기지 않는다.
2. IMAP UID 확인 실패 시 서버 로그에 message ID와 오류 사유가 남는다.
3. 원본 또는 휴지통 메일함 탐색 실패 사유가 보존된다.
4. Gmail 권한 부족 오류가 일반 오류로 덮이지 않는다.
5. 삭제 함수가 `null`을 반환한 경우에도 실패 로그가 남는다.
6. 여러 건 중 일부만 실패하면 개별 실패 로그와 요청 요약 로그가 모두 남는다.
7. 프론트 콘솔에서 실패한 message ID와 서버 오류를 확인할 수 있다.
8. 로그에 메일 본문, 제목, 이메일 주소, 인증 토큰 및 비밀번호가 포함되지 않는다.

### 완료 기준

- 다음 삭제 실패부터 백엔드 로그만으로 실패한 message ID와 직접적인 오류 사유를 확인할 수 있다.
- 브라우저 개발자 콘솔에서도 서버가 반환한 개별 실패 사유를 확인할 수 있다.
- 기존 삭제 성공·부분 복원 동작과 사용자 안내 문구는 유지된다.
- 민감한 메일 내용과 인증 정보는 로그에 기록되지 않는다.

## IMAP 삭제 시 메일함 탐색 실패 해결 방안

### 확인된 오류

삭제 실패 로그에서 다음 직접 원인이 확인되었다.

```text
IMAP 이동 대상 메일함을 찾지 못했습니다.
```

메일 삭제는 원본 메일을 계정의 IMAP 휴지통으로 MOVE하는 방식이다. 로컬 DB에는 시스템 폴더를 `TRASH`, `SENT` 같은 논리 ID로 저장하지만 실제 IMAP 서버는 `Deleted Messages`, `INBOX/Trash`처럼 서로 다른 경로를 반환할 수 있다. Special-Use 속성이 없거나 폴더가 중첩되어 있으면 기존의 완전 일치 검색만으로 실제 휴지통을 찾지 못할 수 있다.

### 구현 방안

#### 1. 실제 IMAP 메일함 속성으로 시스템 폴더 탐색

휴지통 탐색 우선순위:

1. `specialUse === '\\Trash'`
2. flags/attributes Set에 `\\Trash` 포함
3. 전체 path 또는 name이 알려진 휴지통 이름과 일치
4. 중첩 path의 마지막 segment가 알려진 이름과 일치
5. 로컬 `provider_folder_id`가 실제 서버 목록에 존재할 때만 사용

알려진 휴지통 이름에는 `Trash`, `Deleted Messages`, `Deleted Items`, `Deleted`, `휴지통`, `지운 편지함`을 포함한다. 문자열 비교는 대소문자와 앞뒤 공백을 무시한다.

#### 2. 원본과 휴지통 탐색 오류 분리

기존의 하나의 오류 대신 다음 코드와 문구를 구분한다.

- `IMAP_SOURCE_MAILBOX_NOT_FOUND`: 원본 메일함을 찾지 못함
- `IMAP_TRASH_MAILBOX_NOT_FOUND`: 휴지통을 찾지 못함
- `IMAP_MESSAGE_NOT_FOUND`: 메일함은 찾았지만 원격 메시지가 없음

이렇게 하면 로그만으로 재동기화, 휴지통 설정, 고아 레코드 정리 중 필요한 조치를 선택할 수 있다.

#### 3. 오래된 원본 경로 보정

저장된 원본 경로를 찾지 못하고 Message-ID가 있으면 선택 가능한 IMAP 메일함을 검색하여 실제 위치와 UID를 찾는다. 발견된 위치에서 휴지통으로 이동한다.

전체 메일함 검색은 비용이 크므로 정상 경로 탐색이 실패한 삭제 요청에서만 실행한다. `\\Noselect` 폴더는 제외하고, 메일함별 오류는 다음 후보 탐색을 방해하지 않게 처리한다.

#### 4. 원격에서 사라진 고아 메일의 로컬 정리

실제 서버 메일함을 확인했지만 Message-ID로도 원격 메일을 찾지 못한 경우에는 이미 외부 클라이언트에서 삭제된 고아 레코드로 판정할 수 있다. 이 경우 원격 MOVE를 반복하지 않고 로컬 삭제 처리로 폴백한다.

단순 폴더 매칭 실패나 연결 오류는 원격 부재의 증거가 아니므로 로컬 삭제로 폴백하지 않는다. `IMAP_MESSAGE_NOT_FOUND`처럼 원격 검색으로 부재가 확인된 경우에만 허용한다.

### 테스트 및 완료 기준

- Special-Use, flags 및 중첩 폴더 이름으로 휴지통을 찾을 수 있다.
- 존재하지 않는 로컬 경로 문자열을 실제 경로로 오인하지 않는다.
- 원본과 휴지통 탐색 실패가 서로 다른 코드로 기록된다.
- 오래된 원본 폴더 경로는 Message-ID 검색으로 복구된다.
- 원격 부재가 확인된 고아 메일은 로컬에서 정리된다.
- 연결 실패나 휴지통 탐색 실패 시에는 데이터 보호를 위해 로컬 메일을 임의 삭제하지 않는다.

## 원격 식별정보가 없는 불완전한 고아 메일의 로컬 정리 정책

### 확인된 사례

삭제 실패 로그에서 다음 상태가 확인되었다.

```text
code: IMAP_SOURCE_MAILBOX_NOT_FOUND
error: IMAP 원본 메일함을 찾지 못했습니다.
```

해당 로컬 메일 레코드는 다음 특성을 가진다.

- 저장된 원본 IMAP 폴더 경로가 현재 서버의 메일함 목록과 일치하지 않음
- `internet_message_id`가 없어 다른 메일함을 검색할 수 없음
- 화면의 날짜가 `-`로 표시되는 등 일반적인 동기화 메타데이터가 불완전함
- 사용자가 명시적으로 삭제를 요청했지만 원격 MOVE 가능 여부를 확인할 수 없음

현재 구현은 원격 서버에서 메일 부재가 확인된 경우에만 로컬 삭제로 폴백한다. 이 사례는 Message-ID가 없어 원격 검색 자체가 불가능하므로 부재를 확정할 수 없고, 오삭제 방지를 위해 `IMAP_SOURCE_MAILBOX_NOT_FOUND`로 중단된다.

이 상태의 레코드는 일반 삭제를 반복해도 해결되지 않으므로, 엄격한 조건을 만족하는 경우에만 실행되는 별도의 **로컬 고아 메일 정리 정책**이 필요하다.

### 기본 원칙

- 정상 메일 삭제는 기존처럼 원격 IMAP 휴지통 이동을 우선한다.
- 네트워크 오류, 인증 오류 또는 일시적인 IMAP 장애를 고아 메일로 간주하지 않는다.
- 원격 식별정보가 충분한 메일은 로컬 전용 삭제 대상이 아니다.
- 사용자의 명시적인 삭제 요청이 있어야 한다.
- 자동 동기화 작업이나 백그라운드 정리 작업이 임의로 고아 메일을 삭제하지 않는다.
- 로컬 정리는 원격 서버의 메일을 삭제하지 않으며 EasyDocStation의 로컬 메일 목록에서만 제거한다.

### 고아 후보 판정 조건

다음 조건을 모두 만족할 때만 `LOCAL_ORPHAN_CANDIDATE`로 판정하는 것을 권장한다.

1. 메일 provider가 IMAP 계열(`imap`, `other`, `naver`, `apple`)이다.
2. 계정 연결과 IMAP 로그인은 성공했다.
3. IMAP 서버의 메일함 목록 조회도 성공했다.
4. 로컬에 저장된 원본 폴더를 실제 서버 목록에서 찾지 못했다.
5. `internet_message_id`가 비어 있어 전체 메일함 재검색이 불가능하다.
6. `provider_message_id`가 없거나, 그 안의 원본 폴더 식별자가 현재 서버 목록에 존재하지 않는다.
7. 사용자가 해당 메일을 직접 선택해 삭제를 요청했다.
8. 해당 메일이 이미 로컬 휴지통 또는 soft-deleted 상태가 아니다.

다음 상황은 고아 후보로 판정하지 않는다.

- IMAP 연결 실패 또는 timeout
- 비밀번호 오류, OAuth 오류 또는 재인증 필요
- 휴지통 폴더만 찾지 못한 경우
- 원본 폴더는 존재하지만 UID만 찾지 못한 경우
- Message-ID가 있어 원격 재검색이 가능한 경우
- Gmail API 계정
- 일시적인 서버 오류 여부를 판단할 수 없는 경우

### 권장 삭제 흐름

#### 1차: 정상 원격 삭제

기존과 동일하게 원본 메일함과 휴지통을 찾고 IMAP MOVE를 시도한다.

#### 2차: 원본 위치 복구

저장된 원본 폴더가 없지만 Message-ID가 있으면 선택 가능한 모든 메일함에서 원본을 검색한다. 발견하면 해당 위치에서 정상적으로 휴지통으로 이동한다.

#### 3차: 고아 후보 응답

원본 폴더를 찾지 못했고 Message-ID도 없어 검색할 수 없으면 즉시 로컬 삭제하지 않고 API가 다음과 같은 구분 가능한 결과를 반환한다.

```text
code: LOCAL_ORPHAN_CANDIDATE
messageId: 대상 메일 ID
canDeleteLocally: true
```

일반적인 `일부 메일을 삭제하지 못했습니다.`만 보여주지 말고, 사용자가 상황을 이해하고 선택할 수 있게 해야 한다.

#### 4차: 사용자 확인 후 로컬 정리

프론트는 다음 취지의 확인창을 표시한다.

```text
원본 메일함 정보를 확인할 수 없는 불완전한 메일입니다.
메일 서버의 원본은 변경하지 않고 이 앱의 목록에서만 제거할까요?
```

버튼:

- `로컬 목록에서 제거`
- `취소`

사용자가 확인한 경우에만 별도의 로컬 정리 요청을 보낸다. 일반 삭제 요청에 암묵적으로 포함하지 않는 것이 안전하다.

### API 설계 권장안

일반 삭제 API에 위험한 자동 폴백을 넣기보다 명시적인 복구 API 또는 옵션을 사용한다.

예시:

```text
DELETE /api/mail/messages/:id/local-orphan
```

또는 기존 bulk API에 다음 옵션을 추가한다.

```json
{
  "action": "delete_local_orphan",
  "messageIds": ["..."],
  "confirmation": "LOCAL_ONLY"
}
```

서버는 프론트가 보낸 `canDeleteLocally` 값을 신뢰하지 않고 요청 시점에 고아 조건을 다시 검사해야 한다. 조건이 하나라도 맞지 않으면 `409 NOT_LOCAL_ORPHAN`으로 거부한다.

### 로컬 정리 방식

권장 기본 동작은 즉시 DB에서 hard delete하는 것이 아니라 로컬 soft delete다.

- `deleted_at` 설정
- 일반 메일 목록과 통합 목록에서 제외
- 폴더/안 읽음/스마트 폴더 집계 갱신
- 첨부파일과 저장된 raw 원본은 즉시 물리 삭제하지 않고 기존 보존 정책에 따름
- 일정 기간 후 별도 정리 작업에서 영구 삭제 가능

로컬 휴지통에 표시하는 방식도 가능하지만, 이 레코드는 원격 휴지통과 연결되지 않으므로 사용자에게 `로컬에서만 제거됨` 상태를 구분해 보여줘야 한다. UI 복잡도를 줄이려면 우선 soft delete하여 일반 목록에서 숨기는 방안을 권장한다.

### 재동기화 시 재등장 방지

로컬에서만 제거한 메일이 이후 동기화에서 다시 만들어질 가능성을 검토해야 한다.

이 사례는 원격 UID와 Message-ID가 모두 없어 안정적인 deduplication 키가 부족하다. 따라서 다음 중 하나를 사용한다.

- 로컬 레코드의 기존 provider key가 있으면 tombstone으로 일정 기간 보존
- raw object hash나 제한된 헤더 fingerprint가 있으면 해시 tombstone 사용
- 식별값이 전혀 없으면 원격에서 다시 수집될 가능성이 낮은 고아 데이터로 기록하고, 재생성 시 새 메일로 취급

tombstone에는 메일 제목이나 주소 같은 개인정보 대신 해시된 식별값과 삭제 시각만 보관한다.

### 권한 및 보안

- 메일 소유자 또는 해당 tenant의 허용된 관리자만 로컬 정리를 요청할 수 있다.
- 서버에서 `tenantId`, `userId`, `messageId` 소유권을 다시 확인한다.
- 다른 사용자의 로컬 메일을 ID만으로 삭제할 수 없어야 한다.
- 확인용 문자열 또는 별도 action을 요구해 일반 삭제 API의 실수 호출과 구분한다.
- 메일 제목, 본문, 주소, 인증정보는 감사 로그에 기록하지 않는다.

### 감사 로그

로컬 고아 정리는 원격 삭제와 의미가 다르므로 별도 로그를 남긴다.

```text
[mail delete] local orphan removed {
  tenantId,
  userId,
  messageId,
  reason: "missing_source_mailbox_and_message_id",
  remoteChanged: false
}
```

거부된 요청도 다음과 같이 남긴다.

```text
[mail delete] local orphan rejected {
  tenantId,
  userId,
  messageId,
  reason
}
```

### 프론트 상태 처리

- 최초 일반 삭제 실패 때 낙관적으로 제거했던 메일을 현재처럼 목록에 복원한다.
- `LOCAL_ORPHAN_CANDIDATE`만 별도 확인창 대상으로 분류한다.
- 사용자가 취소하면 메일 선택과 목록 상태를 유지한다.
- 로컬 제거 성공 시 목록, 선택 상태, 폴더 개수와 안 읽음 개수를 갱신한다.
- 여러 메일 중 일부만 고아 후보이면 정상 삭제 성공분은 유지하고 고아 후보만 확인창에 표시한다.
- 고아 후보가 아닌 일반 실패는 기존 오류 안내와 상세 로그를 유지한다.

### 테스트 시나리오

1. 원본 폴더와 Message-ID가 모두 없는 불완전한 IMAP 메일이 고아 후보로 반환된다.
2. 사용자가 취소하면 메일이 목록에 그대로 남는다.
3. 사용자가 확인하면 원격 서버를 변경하지 않고 로컬 목록에서 제거된다.
4. 원본 폴더가 정상인 메일에는 로컬 제거 확인창이 나타나지 않는다.
5. Message-ID가 있는 메일은 전체 메일함 검색을 먼저 수행한다.
6. 네트워크 장애와 인증 실패는 고아 후보로 오판하지 않는다.
7. 휴지통만 찾지 못한 경우 로컬 제거를 제안하지 않는다.
8. 변조된 요청으로 정상 메일을 로컬 고아 삭제하려 하면 서버가 `409`로 거부한다.
9. 다른 사용자의 메일 ID로 요청하면 `403` 또는 `404`로 거부한다.
10. 여러 건 중 정상 삭제와 고아 후보가 섞여 있어도 각 결과가 정확히 반영된다.
11. 로컬 제거 후 폴더, 안 읽음, 스마트 폴더 개수가 일치한다.
12. 감사 로그에 원격 미변경 사실과 사유가 남는다.
13. 로그에 제목, 주소, 본문, 토큰 또는 비밀번호가 포함되지 않는다.
14. 동기화 후 제거한 고아 레코드가 즉시 반복 생성되지 않는지 확인한다.

### 완료 기준

- 사용자가 삭제를 요청한 불완전한 고아 메일을 안전한 확인 절차를 거쳐 로컬에서 제거할 수 있다.
- 정상 메일, 일시적인 연결 오류 및 인증 오류는 로컬 삭제 대상이 되지 않는다.
- 서버가 요청 시점에 고아 조건과 소유권을 재검증한다.
- 원격 IMAP 서버의 데이터는 변경되지 않았음을 사용자와 로그에 명확히 표시한다.
- 부분 성공, 취소 및 오류 상황에서도 메일 목록과 카운트가 일관되게 유지된다.
